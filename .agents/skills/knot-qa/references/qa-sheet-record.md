# QA 체크리스트 기록 규칙

실행 단계(2-4)에서 판정과 E2E 결과를 노션 QA 체크리스트에 적는 규칙이다. 이번 범위는 QA를 돌린
에이전트가 직접 적는 방식이다. GitHub이 머지 때 E2E 결과를 자동으로 적는 방식은 아직 없어서, E2E
결과도 에이전트가 PR 관문 결과 댓글을 근거로 적는다(아래 「E2E 결과」).

## 쓰기 전에 확인받기

QA 체크리스트는 팀 공용 DB다. 쓰기 전에 아래 표를 사용자에게 보여 주고 한 번 확인받는다.
확인은 이 목록에만 해당한다. 목록이 바뀌면 다시 묻는다.

```md
| 동작 | 행 ID | 확인할 항목 | 판정 | 이전 수행 | QA 회차 | 근거 요약 |
| --- | --- | --- | --- | --- | --- | --- |
| 새 수행 행 | STT-R28 | 녹음 탭 닫기 후 재접속 | Pass | <원래 행 주소> | v2 녹음 1차 | 탭 닫기 뒤 종료 요청 200, 재접속 홈 카드 「문서 정리 중」 |
| 원래 행 갱신 | STT-R28 | 녹음 탭 닫기 후 재접속 | (그대로) | | | 검증 상태 검증 완료, 수정 반영 빌드 |
| 자동 확인 갱신 | STT-R25 | 종료 확인 창 표시 | (판정 안 씀) | | | 자동 확인 통과, PR #850 관문 댓글 |
```

- 노션 연결이 없거나 쓰기가 실패하면 같은 내용을 열 이름과 값으로 풀어 `/tmp/knot-qa/<slug>-record.md`에
  마크다운으로 남기고 멈춘다. 일부만 썼으면 쓴 행과 못 쓴 행을 나눠 알린다.

## E2E 결과

E2E는 가짜 응답(mock)으로 돌아서 실제 서버 판정을 대신하지 않는다. 그래서 E2E 결과는 `판정`이 아니라
아래 세 칸에 적는다(2026-10-19 QA 체크리스트에 추가).

| 열 | 값 |
| --- | --- |
| `자동 확인` | `통과`, `실패`, `없음` 중 하나. PR 관문 댓글의 관련 QA 표 결과를 그대로 옮긴다. 재시도 후 통과는 `통과`다. 계획 표의 E2E 행인데 관문 댓글에 그 ID의 E2E 결과가 없으면(E2E 제외 포함) `없음` |
| `E2E 테스트` | 테스트 이름과 파일. 예: `[STT-R25] 독의 마이크로 녹음을 시작하고 끝내기를 확정하면 문서 정리 화면으로 간다, recordingPage.test.ts` |
| `자동 확인 일시` | 근거로 삼은 관문 실행(또는 로컬 실행)의 시각(KST) |

- **어느 행에 적나**: 한 행 ID에 행이 여러 개면 그 E2E가 확인하는 `확인할 항목`의 행에만 적고 나머지는
  비운다. 어느 행인지는 준비 단계의 QA 계획 표에서 행 단위로 정한 것을 따르고, 실행 단계에서 다시 고르지
  않는다. 그 행이 재수행 사슬이면 최신 행(`후속 재검증`이 빈 행)이다.
- **새 행을 만들지 않는다**: 세 칸은 그 행의 마지막 자동 확인 상태라서 새 수행 행 없이 그 행에서 갱신한다.
  `판정`, `증거`, `사유·비고` 같은 다른 칸은 건드리지 않는다.
- **`판정`은 실제 서버에서 확인한 결과만**: 에이전트 QA와 사람 QA의 결과다. E2E가 통과했다고 `판정`을
  Pass로 적지 않고, E2E가 실패했다고 Fail로 적지 않는다.
- **근거**: GitHub이 머지 때 자동으로 적는 방식은 아직 없다. 실행 단계에서 에이전트가 PR 관문 결과 댓글을
  근거로 적는다. 관문이 아직 돌지 않았으면 `frontend`에서 `pnpm test:e2e -g "<행 ID>"`를 돌린 로컬 결과를
  근거로 쓰고, `E2E 테스트` 끝에 `(로컬)`을 붙인다.
- 쓰기 전 확인 표에는 `자동 확인 갱신` 행으로 함께 올린다.

## 새 행인가, 그 행인가

2026-10-19에 기존 데이터로 확인한 관례다. 10/18 재수행 12건이 모두 이 방식이다.

- 판정이 비었거나 `Not Run`인 행: 그 행에 바로 쓴다.
- 판정이 있는 행: 덮어쓰지 않는다. 새 행을 만들고 `이전 수행`에 사슬의 최신 행을 잇는다.
  `후속 재검증`은 `이전 수행`의 반대쪽 관계라서 직접 쓰지 않는다.
- 원래 행은 판정, 증거, 비고를 그대로 두고 `검증 상태`와 `수정 반영 빌드`만 기존 관례대로 갱신한다.

| 새 행 판정 | 새 행 `검증 상태` | 원래 행이 Fail이었을 때 |
| --- | --- | --- |
| Pass | 해당 없음 | `검증 상태`를 검증 완료로, `수정 반영 빌드`에 `#<PR> (<커밋>, <머지일> 머지), 확인 빌드 <커밋>` |
| Fail | 수정 대기 | `검증 상태`를 재현됨으로 |
| Blocked, 판정 비움 | 해당 없음 | 그대로 |

원래 행이 Fail이 아니면 원래 행은 건드리지 않는다.

## 채우는 열

| 구분 | 열 | 값 |
| --- | --- | --- |
| 원래 행에서 복사 | `확인할 항목`, `요구사항 ID`, `요구사항`, `요구사항 바로가기`, `테스트 케이스`, `도메인`, `도메인 1`, `화면`, `우선순위`, `순서`, `피그마 화면`, `담당 영역`, `담당자` | 원래 행 값 그대로 |
| 이번 수행 | `판정` | 판정 규칙의 값. 관찰이나 판정이 갈린 행은 비움 |
| | `수행일` | 실행한 날짜(KST) |
| | `수행자` | 에이전트를 돌린 팀원의 노션 사용자 |
| | `실행 에이전트` | Claude, Codex, 기타 에이전트. 판정의 핵심 동작을 사람이 했으면 사람 |
| | `QA 회차` | 아래 「QA 회차 이름」 |
| | `FE 빌드`, `BE 빌드` | 아래 「값 형식」 |
| | `브라우저·OS·기기` | 아래 「값 형식」 |
| | `테스트 URL` | 실제로 연 주소 |
| | `안 본 조건` | 기대 결과 중 이번에 보지 않은 조건. 없으면 비움 |
| | `기준 의심` | 기대 결과가 정본과 다르다고 본 근거(파일:줄, 노션 주소), 또는 같은 조건에서 갈린 두 판정 |
| | `사유·비고` | 재현 → 실제. 변경 범위 실행이면 첫 줄에 `변경 범위 실행 #<Issue 번호>` |
| | `증거`, `증거 링크` | 아래 「증거」 |
| | `이전 수행` | 사슬의 최신 행. 그 행에 바로 쓰면 비움 |
| | `검증 상태` | 위 표 |
| | `세션 ID` | 녹음 세션을 만들었으면 그 ID |
| Fail일 때 | `이슈(FE)` 또는 `이슈(BE)` | 담당자가 볼 「재현 → 실제」 한 줄 |
| | `심각도` | 노션 선택지 이름 그대로. 서비스 불가와 데이터 유실 선택지, `주요 기능 실패`, `경미` 중 하나 |
| E2E 행 | `자동 확인`, `E2E 테스트`, `자동 확인 일시` | 위 「E2E 결과」. 새 수행 행이 아니라 계획에서 고른 행에 적는다 |

`수정 반영 빌드`(새 행), `시연 점검 메모`, `GitHub Issue`는 비운다.

## QA 회차 이름

- 재수행 행은 원래 행의 `QA 회차`를 그대로 쓴다. 10/18 재수행은 모두 `v2 문서 1차`, `v2 녹음 1차`를 유지했다.
- 새 회차는 QA 책임자가 정한 이름을 쓴다. 기존 꼴은 `v2 <도메인> <N>차`다.
- 변경 범위 실행은 회차를 새로 만들지 않는다. 원래 행의 회차를 쓰고 `사유·비고` 첫 줄로 구분한다.
- 원래 행의 회차가 비었으면 쓰기 전 확인 표에서 QA 책임자에게 회차 이름을 묻는다.

## 값 형식

- `FE 빌드`: `<커밋 8자리> (<브랜치>, <배포 출처>, <날짜> <시각> KST 배포)`.
  예: `3ab67951 (develop, Frontend Dev CD #39082983301, 2026-10-18 09:30 KST 배포)`.
  PR 전 로컬이면 `<커밋 8자리> (로컬 PR 브랜치 <브랜치>, localhost:3000)`.
- `BE 빌드`: 배포 커밋을 알면 커밋, 모르면 `배포 커밋 확인 불가, API 응답 확인 <날짜> <시각> KST`.
- `브라우저·OS·기기`: `<브라우저와 버전>(<자동화 여부와 세션 메모>), <OS>, <창 크기> CSS px`.
  예: `Chrome 155 헤드리스(Playwright, 녹음용 별도 세션), macOS, 1440×1024 CSS px`.
- `사유·비고`: 무엇을 했는지 → 실제로 본 것. API는 `GET /api/v1/workspaces/33/recordings/current → 204`처럼
  메서드, 경로, status를 적고 오류 코드와 콘솔 오류 문구를 붙인다.

## 증거

- 화면 캡처는 `증거` 파일 열에 올린다. 파일 이름은 `<순서>-<짧은 설명>.png`이다(예: `60190-doc71-popover.png`).
- 캡처를 올리지 못하면 `증거 링크`에 PR 관문 댓글이나 CI artifact 주소를 적는다.
- API 응답과 콘솔은 `사유·비고`에 글로 적는다. 응답 본문의 개인정보, 토큰, 쿠키, 초대 코드는 지운다.

## 쓴 뒤

- 쓴 행을 다시 읽어 판정, `이전 수행`, `QA 회차`가 들어갔는지 확인한다. 자동 확인을 갱신한 행은
  `자동 확인`, `E2E 테스트`, `자동 확인 일시`가 들어갔고 `판정`이 그대로인지 확인한다.
- 보고에 쓴 행의 노션 주소를 붙인다.

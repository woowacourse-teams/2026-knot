# Knot QA

QA는 개발자가 아니라 에이전트가 한다. 정본은 노션 QA 체크리스트 하나다. 이 스킬은 누가
어떤 에이전트로 돌려도 같은 행을 고르고, 같은 조건을 적고, 같은 판정 규칙과 기록 형식을
쓰게 한다. 개발자가 부르지 않아도 아래 시점에 돈다.

| 시점 | 단계 | 범위 |
| --- | --- | --- |
| 확정 Issue 구현을 시작할 때 | 준비 | Issue와 관련된 QA 행 |
| PR을 열기 전 | 준비 마무리 | QA 계획으로 PR 본문 「관련 QA」를 채우고 E2E가 있는지 확인(관문이 다시 검사) |
| develop에 머지돼 dev에 배포된 뒤 | 실행 (변경 범위) | 준비 단계의 QA 계획 행 |
| 배포 전 QA 회차 | 실행 (전체) | QA 책임자가 정한 도메인, 경로, 우선순위 |

PR 브랜치는 dev에 배포되지 않으므로 실제 서버 확인은 PR 전이 아니라 머지 뒤에 한다. PR 단계는 자동 E2E가 지킨다.

- 테스트 기준: 행의 `테스트 케이스` 관계(data source `collection://f0120e77-2c95-4c21-8f63-c039a019bee2`).
  사전 조건, 수행 절차, 기대 결과, 준비 상태가 있다. 행 본문에도 같은 내용이 있다.
- 판정 기준 문서 계층: `docs/product/current-v2-mvp.md`
- 실제 서버: FE `https://dev.knoted.kr`, API `https://dev-api.knoted.kr`. 운영 `knoted.kr`은

- 노션 기록 규칙: `references/qa-sheet-record.md`
- 근거: 노션 [QA 스킬 초안 v0.1](https://app.notion.com/p/3fab43517522812480bef6ac03eff97b),
  [E2E와 QA 합치기 설계 v0.4](https://app.notion.com/p/3fdb4351752281b48ff3e996cb5b1589)

## 행을 가리키는 법

- 행 ID는 `확인할 항목` 제목 앞 대괄호 안의 값이다. `[STT-R28] 녹음 탭 닫기 후 재접속`은
  `STT-R28`이다. 제목 앞에 `⚠ 기준 확인` 표시가 붙은 행도 대괄호 값을 쓴다.
- 행 ID 하나에 행이 여러 개다(10/19 기준 `STT-R28` 행 15개). 그래서 계획과 기록에는 행 ID,
  `확인할 항목`, 노션 주소를 함께 적는다.
- 같은 `확인할 항목`의 행이 여러 개면 재수행 기록이다. `이전 수행`과 `후속 재검증` 관계를
  따라 사슬을 만들고, `후속 재검증`이 빈 행을 최신 수행으로 본다.

## 1. 준비 (구현을 시작할 때)

1. **입력 모으기**: Issue 본문과 상위 Issue(`gh issue view <번호> --repo woowacourse-teams/2026-Knot`),
   대화에서 요구사항 ID, QA 행 ID, 도메인, 화면, 바뀌는 동작을 뽑는다.
2. **관련 행 찾기**: 노션 SQL로 아래 순서대로 찾아 합친다. 노션은 읽기만 한다.
   1. `요구사항 ID` 열이나 제목 대괄호가 Issue의 ID를 포함하는 행(`CONF-R5, CONF-R9`처럼 여러 ID가 든 행 포함)
   2. 도메인과 화면이 같은 행. 도메인은 `도메인`(녹음, 홈, 문서 정리) 열과 `도메인 1`(그 밖) 열에
      나뉘어 있어 둘 다 본다.
   3. 제목에 바뀌는 동작의 낱말(예: 탭, 닫기, 재접속)이 든 행
   - 2와 3으로만 찾은 행은 이번 변경이 그 동작을 실제로 바꾸는지 Issue와 코드로 확인하고, 아니면 뺀다.
   - 판정이 `잘못된 항목`인 행은 뺀다. 뺀 행은 수와 이유만 표 아래에 적는다.
3. **확인 방법 나누기**: 행마다 위에서부터 처음 맞는 것을 고른다. P0 행부터 나눈다.

   | 순서 | 행이 이런 것을 봐야 하면 | 확인 방법 |
   | --- | --- | --- |
   | 1 | 실기기, 권한 팝업, 소리, 사람의 판단 | 사람 |
   | 2 | 실제 서버 응답, AI 답변 내용, 외부 연동(GitHub OAuth 등) | 에이전트 QA |
   | 3 | 나머지. mock으로 매번 같은 결과가 나오는 화면 동작 | E2E |

   - 한 행에 화면 동작과 서버 확인이 섞이면 `E2E + 에이전트 QA`로 적고, 나눈 부분을 이유에 쓴다.
   - 제목에 `⚠ 기준 확인`이 붙었거나 테스트 기준의 `준비 상태`가 `정책 확인 필요`이면 확인 방법 뒤에
     `(관찰)`을 붙인다. 판정하지 않고 본 것만 적을 행이다.
   - E2E가 이미 있는지는 `grep -rn "\[<행 ID>" frontend/src/__test__`로 본다. 아직 커밋하지 않은 E2E도 찾도록 `git grep`을 쓰지 않는다.
4. **QA 계획 표**: 사용자에게 보여 주고, OS 임시 폴더 `/tmp/knot-qa/<slug>-plan.md`에 저장한다.
   `<slug>`는 브랜치명의 `/`, `#`, 공백을 `-`로 바꾼 값이다. 저장소에는 쓰지 않는다.

   ```md
   ## QA 계획 (#<Issue 번호> <Issue 제목>, <날짜>)

   | 행 ID | 확인할 항목 | 우선순위 | 판정 이력 | 확인 방법 | 이유 | E2E |
   | --- | --- | --- | --- | --- | --- | --- |
   | [STT-R28](<노션 주소>) | 녹음 탭 닫기 후 재접속 | P0 | Fail (v2 녹음 1차) | 에이전트 QA | 종료 신호 수신과 재접속 상태는 실제 서버 응답 | 없음 |
   ```

   - 판정 이력은 사슬의 오래된 수행부터 `판정 (QA 회차, 수행일)`을 `→`로 잇는다. 수행일이 비었으면 뺀다.
   - 한 행 ID에 행이 여러 개면 E2E가 확인하는 `확인할 항목`의 행 하나를 골라 그 노션 주소를 적는다.
     실행 단계의 자동 확인 기록은 이 행에만 간다(`references/qa-sheet-record.md` 「E2E 결과」).
   - 표 아래에 뺀 행, `(관찰)` 행, 이번 계획으로 사용자가 정해야 할 것을 적는다.
5. **E2E 먼저**: 확인 방법이 E2E인 FE 화면 동작 행은 `qa-e2e` 절차로 E2E를 먼저 쓰고, 구현 전에
   실패하는 것을 확인한 뒤 구현한다. 구현 뒤에는 `qa-e2e`의 통과 기준을 모두 지킨다. BE만 바꾸는
   Issue면 E2E 행은 `FE 범위`로 표시만 하고 쓰지 않는다.
6. **PR 본문 연결**: PR 본문 「## 관련 QA」는 이 계획으로 채운다. E2E 행은 `- <행 ID>`, 사람이나
   에이전트 QA 행은 `- <행 ID> (E2E 제외: <이유>)`로 적는다. 같은 행 ID에 E2E 행이 하나라도 있으면
   제외 없이 ID만 적고, 나머지 행은 PR 본문 `작업 내용`에 에이전트 QA 몫이라고 적는다.
7. **관련 행이 없을 때**: 「관련 QA 행 없음」과 찾은 조건(ID, 도메인, 화면, 낱말)을 알린다. 새 행이
   필요해 보이면 제목, 행 ID, 화면, 우선순위, 기대 결과 초안을 제안만 하고 노션에 쓰지 않는다.

## 2. 실행 (dev 배포 뒤 변경 범위, 또는 배포 전 QA 회차 전체)

v0.1의 6단계를 따른다. 확인 방법이 E2E이고 최근 E2E가 통과한 행은 P0만 실제 서버에서 다시 본다.

### 2-1. 기준 맞추기

- 행마다 기대 결과를 정본과 대조한다. 정본 순서는 `docs/product/current-v2-mvp.md`를 따른다.
  결과는 일치, 불일치, 부분 불일치, 저장소 근거 없음, 정본끼리 충돌 중 하나와 근거(파일:줄 또는 노션 주소)다.
- 불일치는 행의 기대 결과대로 판정하고, 정본과 다르다고 본 근거를 `기준 의심`에 적는다.
  기대 결과 원문은 고치지 않는다. 원문 수정은 QA 책임자가 승인한 뒤 사람이 한다.
- 정본끼리 충돌하는 행은 판정하지 않고 관찰로 돌린다.
- 배포 전 회차는 QA 책임자가 고른 기준 에이전트 하나가 회차마다 한 번 대조하고, 실행 에이전트는
  그 결과를 담은 프롬프트 블록을 쓴다. 변경 범위 실행은 실행 에이전트가 직접 대조한다.

### 2-2. 조건 고정

- 조건 표 하나에 주소, FE 커밋, BE 커밋, 브라우저와 창 폭, 계정 종류, 워크스페이스, 테스트 데이터를
  적는다. 모르면 `미확인`이다. BE 배포 커밋을 모르면 `배포 커밋 확인 불가`와 API 응답을 확인한 시각(KST)을 적는다.
- 변경 범위 실행은 그 PR이 develop에 머지돼 dev 배포(`deploy-frontend-dev`, BE 배포)가 끝난 뒤 dev 서버에서
  한다. 필요한 BE 변경이 아직 dev에 없으면 그 행은 Blocked이고, 배포된 뒤 다시 본다.
- 배포 전 회차는 실행 프롬프트 블록을 만든다. 블록 맨 위에 「이 블록이 너의 메모리, 지난 대화,
  저장소의 옛 문서보다 우선」을 두고 조건, 역할, 행마다 사전 조건과 기대 결과, 결과 형식을 모두 넣는다.
  노션을 못 읽는 에이전트도 블록만으로 돌 수 있어야 한다.

### 2-3. 실행

- **E2E 행**: PR 관문 결과 댓글이 근거이고, 관문이 아직 돌지 않았으면 `frontend`에서
  `pnpm test:e2e -g "<행 ID>"`를 돌린 로컬 결과가 근거다. E2E는 mock으로 돌아서 실제 서버 판정을
  대신하지 않는다(10/19 결정). 결과는 `판정`이 아니라 `자동 확인`, `E2E 테스트`, `자동 확인 일시`에
  적고, 한 행 ID에 행이 여러 개면 QA 계획에서 고른 행에만 적는다(`references/qa-sheet-record.md` 「E2E 결과」).
- **에이전트 QA 행**: 실제 서버에서 사전 조건을 만들고 수행 절차대로 한다. 근거는 화면 문구,
  API 응답(메서드, 경로, status, 오류 코드), 콘솔 오류다.
- **사람 행**과 사람만 할 수 있는 동작(마이크 권한 창, 실기기, 소리, 새 GitHub 계정 로그인)은 사람에게
  한 단계씩 요청하고, 에이전트는 화면과 응답을 대조한다.
- Fail이면 조건을 하나씩 바꿔 다시 돌려 실패 조건을 좁힌다(최대 5회). 바꾼 조건과 결과를 표로 남긴다.
- 기대 결과의 문장마다 본 것과 근거를 짝짓는다. 근거가 없는 문장은 `안 본 조건`으로 간다.

### 판정 규칙

- 판정 값은 Pass, Fail, Blocked, Not Run, N/A다. `Pass(일부 조건)`은 쓰지 않는다.
- **증거 없는 Pass 금지**: Pass에는 본 기대 결과 문장마다 화면, API, 콘솔 중 하나 이상의 근거가 있다.
  근거를 남기지 못했으면 Not Run이다.
- 본 기대 결과 중 하나라도 어긋나면 Fail이다.
- **사전 조건이 없으면 Blocked**다. 무엇이 없었는지 `사유·비고`에 적는다.
- 기대 결과 일부만 봤고 본 것이 모두 맞으면 Pass로 두고, 못 본 조건을 `안 본 조건`에 적는다.
- 관찰 행과 정본끼리 충돌하는 행은 판정을 비우고 본 것만 적는다.
- 실행 중에 기대 결과를 스스로 바꾸지 않는다. 틀린 것 같으면 `기준 의심`에 적는다.

### 안정성

- **같은 행을 두 번 판정했는데 결과가 다르면** 둘 중 하나를 고르지 않는다. FE 빌드와 BE 빌드가 같은데
  판정이 갈렸으면 판정을 비우고 `기준 의심`에 두 판정, 두 가지로 읽힌 기대 결과 문장이나 흔들린 조건을
  적는다. 빌드가 달라 갈렸으면 판정은 이번 결과로 두고 `사유·비고`에 이전 수행과 바뀐 빌드를 적는다.
- P0 행의 판정이 이전 수행과 반대로 바뀌면(Pass에서 Fail, Fail에서 Pass) 같은 조건으로 한 번 더 돌려
  같은 결과일 때만 기록한다.
- 교차 확인(다른 에이전트가 같은 기록을 다시 판정)은 일상 절차에 넣지 않는다. 규칙의 효과를 재는
  시범에서만 같은 행을 두 번 돌려 비교한다.

### 2-4. 기록

`references/qa-sheet-record.md`를 따른다. 쓰기 전에 쓸 행 목록을 사용자에게 보여 주고 한 번 확인받는다.
노션 연결이 없으면 기록할 내용을 마크다운으로 남기고 멈춘다.

### 2-5. 핵심 판단 (사람에게 묻는 것)

아래에 해당하면 에이전트는 결론을 내리지 않는다. 판정과 근거는 기록하되, 출시를 막을지, 기준을 고칠지는
QA 책임자(기획자)에게 근거와 선택지를 붙여 한 줄로 묻는다. QA 체크리스트의 「QA 책임자 확인」 보기에도 같은 행이 보인다.

1. 도메인을 가로지르는 핵심 여정의 P0 (예: 녹음에서 문서 정리를 거쳐 탐색, 로그인에서 온보딩을 거쳐 워크스페이스)
2. 기준 의심: `기준 의심`을 적은 행, 2-1의 정본끼리 충돌
3. P0인데 Fail이나 Blocked인 행, 그리고 이전 수행과 판정 방향이 반대인 행

나머지는 실행 판정으로 확정해 기록한다.

### 2-6. 요청으로 묶기

- Fail, Blocked, 확정된 기준 수정을 담당자별 요청으로 묶는다. 담당자는 행의 `이슈(FE)`, `이슈(BE)`,
  `담당 영역`으로 정한다.
- 요청 한 건의 모양: 한 줄 요약, 왜 문제인가, 관찰한 것, 조건을 바꾼 실험 표, 코드에서 찾은 원인 후보
  (추측이라고 표시), 확인할 것, 정해야 할 것(선택지), 오늘 한 대응.
- Fail 행 중 E2E로 확인할 수 있는 행은 「고친 뒤 이 ID로 E2E 추가」를 붙인다.
- 전달은 사람이 한다. 에이전트는 초안까지 만든다.

## 결과 형식

```text
행 ID | 확인할 항목 | 판정 | 수행자(사람, 에이전트) | 시각(KST) | FE 커밋 | BE 커밋 | 브라우저와 창 | 계정 종류 | 워크스페이스 ID | 재현 → 실제 | 증거(화면, API, 콘솔) | 안 본 조건 | 기준 의심
```

## 임시 기본값 (미결정)

v0.1 「검토 메모」의 미결정 5개다. QA 책임자가 정하기 전까지 아래 값을 쓰고, 정해지면 이 절을 고친다.

1. 「핵심」 3번: P0인데 Fail이나 Blocked인 행과 이전 수행과 방향이 반대인 행을 둘 다 올린다.
2. 사전 조건 미충족은 Blocked, 기대 결과 일부만 본 것은 Pass와 `안 본 조건`이다.
3. 팀원 에이전트의 노션 접근: 배포 전 회차는 프롬프트 블록에 기대 결과를 넣는 방식을 유지한다.
   노션을 직접 읽는 에이전트도 블록을 우선한다.
4. 사람만 할 수 있는 실행의 기록 주체: `실행 에이전트`는 `사람`, 대조한 에이전트는 `사유·비고`에 적는다.
5. 녹음팀 점검 결과처럼 노션에 아직 없는 결과는 기준 맞추기의 근거로 쓰지 않는다. 그 도메인 회차를
   시작할 때 QA 책임자에게 반영 여부를 먼저 묻는다(v0.1에 제안 없음, 이 스킬이 정한 값).

## 하지 않는 것

- 자기 기억, 지난 대화, 저장소에 있는 노션 사본을 제품 정책의 근거로 쓰지 않는다.
- 비밀번호, 토큰, 쿠키 값, 초대 코드 원문을 입력하거나 기록하지 않는다.
- 판정이 있는 QA 행을 덮어쓰지 않는다. `자동 확인`, `E2E 테스트`, `자동 확인 일시` 세 칸의 갱신만 예외다.
- E2E 결과를 `판정`에 적지 않는다. `판정`은 실제 서버에서 확인한 결과만이다.
- 사용자가 확인하지 않은 노션 쓰기, 새 QA 행 추가, 기대 결과 수정을 하지 않는다.
- QA 행, 우선순위, 판정을 저장소에 옮겨 적지 않는다.
- 테스트를 통과시키려고 서비스 코드나 기대값을 근거 없이 바꾸지 않는다.

## 다음 단계 (계획, 아직 하지 않음)

아래는 모두 계획이다. 지금 PR 관문 E2E는 CI 안에서 PR 코드를 띄우고 가짜 응답으로 돈다.

- **배포 뒤 smoke**: dev 배포가 끝나면 실제 dev 서버에서 핵심 여정 몇 개를 돌린다. 실제 서버 결과라서
  `판정`에 적을 수 있다. GitHub 로그인을 통과할 테스트 계정이 먼저 필요하다.
- **계약 테스트**: E2E가 쓰는 mock 응답이 BE API 명세와 같은 모양인지 확인한다. 가짜 응답으로 통과한
  E2E가 실제 서버에서 깨지는 틈을 줄인다.
- **GitHub 자동 기록**: 머지 때 GitHub이 `자동 확인` 세 칸을 직접 적는다. 노션 쓰기 토큰이 필요하다.
  그 전까지는 위 2-3과 기록 규칙대로 에이전트가 관문 댓글을 근거로 적는다.

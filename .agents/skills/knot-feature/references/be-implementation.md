# BE 구현 절차 (입구 스킬이 직접 수행)

한 문장 책임: 이슈, 도메인 규칙, API 명세를 직접 읽어 백엔드를 구현하고, 단위 테스트와 통합
테스트를 만든 뒤 PR을 올려 CI 결과를 확인한다. 컨벤션은 기존 백엔드 rules와 스킬에서 가져온다.

| 읽기 | 쓰기 |
| --- | --- |
| 이슈, 도메인 규칙, API 명세, QA 시트 | `backend` 코드, PR |

## 누가 수행하나

서브 에이전트가 아니라 입구 스킬(메인 세션)이 이 절차를 직접 수행한다. FE 절차와 같은 이유이며,
기존 백엔드 스킬(`knot-commit`, `knot-pr`)은 `backend/`에서 시작해야 발견되므로 메인 세션이 경로로
직접 읽는다. 기준 문서의 「BE 구현 하네스」 객체가 이 절차다.

## 시작 조건

- 완료 조건이 「개발까지」이고 영역이 백엔드일 때. 입구가 이슈 URL을 들고 「구현해라」로 시작한다.
- 기존 이슈 URL로 흐름을 시작한 경우도 같다.
- 끝나면 입구는 같은 반환 규약 모양(`changed`에 `kind: pr`)으로 상태 파일에 기록한다.

## 규칙

- 다른 단계에 메시지를 보내 정보를 받지 않는다. GitHub 이슈, 노션 도메인 규칙, API 명세, QA
  시트에 직접 접근해 스스로 처리한다.
- 이슈 본문의 「노션 변경 사항」 링크가 정본 위치다. 백엔드는 이슈, 도메인 규칙, API 명세로
  구현한다. 순서는 도메인 규칙, API 명세, 소스 코드다. 관련 원문을 찾는 절차는
  `backend/docs/notion-context.md`를 따른다.
- 기존 백엔드 하네스를 그대로 쓴다. `backend/`에서 시작하고 `backend/.agents/skills/knot-commit`,
  `knot-pr`, `knot-api-spec`의 `SKILL.md`를 경로로 직접 읽는다. 코드 규칙은 `CONTRIBUTING.md`의
  Java 가독성 규칙과 Spotless를 따른다. 브랜치는 `be/<type>/#<이슈 번호>`이고 워크트리에서
  작업한다.
- 테스트는 반드시 있다. 단위 테스트는 함수 단위로, 통합 테스트는 구현에 필요한 것을 알아서 만들고
  돌린다. TDD 적용 여부와 세부 방식은 이 절차 안에서 정하고 강제하지 않는다. 테스트는 QA 시트의
  시나리오를 근거로 고르되 E2E는 프론트 길이 맡는다.
- 완료 조건 「개발까지」가 `knot-commit`과 `knot-pr`가 요구하는 commit, push, PR 생성의 명시
  요청이다. 두 스킬에 이 예외가 적혀 있다. 커밋에 co-author와 AI 생성 표시를 붙이지 않는다.
- PR은 루트 `AGENTS.md` 「기능 구현 요청 파이프라인」의 PR 공통 규칙을 따른다. 첫 섹션
  `## 노션 변경 사항`에 이슈의 링크를 끌어와 적고, 그 아래는 `knot-pr`의 본문 규칙과 PR
  템플릿을 따른다. 백엔드 PR은 사람이 아니라 AI가 보는 PR이라 내용이 더 많아도 된다.
- 담당자, 라벨, 리뷰어는 `python3 harness/team_roles.py review --area backend --author <implementer>`
  결과로 정한다. 1차 컨펌을 받은 작업이거나 구현 중 기획을 바꿨으면 `--plan-changed`를 붙인다.
  assignee와 이름 라벨은 결과대로, 작업 성격 라벨은 이슈에서 가져오고, `reviewers`에 리뷰를
  요청한다. 구현 중 기획을 바꿨으면 무엇을 왜 바꿨는지 PR 본문에 적는다. BE 팀원 한 명 이상(기획이
  바뀌었으면 기획 컨펌 담당도)이 승인하면 PR을 연 사람이 직접 머지한다.
- PR을 올린 뒤 Backend CI 결과를 확인한다. 실패하면 실패 루프 규칙대로 고쳐 다시 푸시하고,
  통과한 뒤에야 끝난다.
- ADR이 필요한 이슈(`메모`에 ADR 결정과 예정 경로)는 구현 브랜치에서
  `python3 harness/materialize_adr.py <snapshot.json> --issue-number <번호> --implementation --pretty`
  로 `Proposed` ADR을 만들어 같은 PR에 넣는다.
- 실패 루프: 테스트 실패 수정은 3회까지 시도하고, 그래도 실패하면 멈추고 원인과 시도 내역을
  보고한다. 구현 중 요구사항이나 명세 문제를 발견하면 문서 단계로 되돌리지 않고 멈춰 사용자에게
  묻는다.
- `backend` 밖의 코드는 고치지 않는다. 프론트 변경이 필요하면 멈추고 사용자에게 알린다.

## 하지 않는 것

- 노션 문서를 고치지 않는다. 명세와 코드가 어긋나면 명세를 고치지 않고 멈춰 알린다. merge 하지
  않는다.

# Knot Feature 입구 스킬

「○○ 기능 구현해 줘」 한 문장이 기능 요구사항 갱신, QA 시트, 이슈, 구현, 테스트, PR까지 끝까지
가고, 사람은 PR에서 한 번 컨펌한다. 이 스킬은 그 흐름의 입구다.

한 문장 책임: 요청을 받아 작업 범위와 완료 조건을 정하고, 서브 에이전트를 순서대로 실행해 결과를 넘기며,
사용자에게 물을 일을 대신 묻는다. 읽기는 전부, 쓰기는 상태 파일만.

## 정본과 금지

- 노션과 Figma가 정본이다. 위치는 `references/sources.md`에 있다. 문서 내용을 저장소 Markdown으로
  옮기지 않는다.
- 기획서는 읽기만 한다. 요청이 기획서 수정을 필요로 하면 거부하고 유월에게 컨펌받으라고 안내한
  뒤 끝낸다.
- 스프린트 시트의 이슈(태스크)는 다루지 않는다. 상위 이슈는 만들지 않는다. 처음 요청이 상위 이슈
  역할을 한다.
- 디자인이 먼저 바뀌어 얽힌 문서를 따라 고치는 역방향 흐름은 범위 밖이다. 새 디자인도 만들지 않는다.
- 입구는 모든 판단을 떠안는 무거운 오케스트레이터가 되지 않는다. 어느 문서를 다음에 갱신할지는
  각 서브 에이전트가 `next`로 판단하고 입구는 실행한다.
- 명령은 저장소에서 터미널(Claude Code, Codex)로 내린다.

## 역할과 권한 (2026-10-22 결정)

도메인 팀(녹음팀, 문서팀, 탐색 등)이 자기 도메인의 기획 권한(기능 요구사항, 도메인 규칙,
API 명세, QA 시나리오)과 디자인 권한(Figma)을 가진다. 흐름 도중의 도메인 판단은 그 팀이
내린다. 유월은 올라온 PR을 최종 컨펌하고(모든 도메인), 도메인을 가로지르는 전체 제품 플로우
QA와 제품 기획 기준(전체 스펙) 변경 승인을 맡는다.

| 결정 지점 | 누가 결정하나 |
| --- | --- |
| 시작: 영역, 완료 조건 | 요청한 팀원 |
| 요구사항이 기존과 충돌 | 그 도메인 팀 |
| 디자인 필요(기존 화면 없음) | 그 도메인 팀 (디자인 권한) |
| 이슈 GitHub 게시 허용 | 요청한 팀원 |
| 테스트 3회 실패, 문서 문제 | 요청한 팀원 (멈춤 보고) |
| 프론트와 백엔드 동시 변경 | 두 도메인 팀 합의. PR은 `[FE]`, `[BE]`로 나눠 각각 올린다 |
| 제품 기획 기준(전체 스펙) 변경 | 유월 승인. 하네스는 거부한다 |
| 최종 PR 컨펌 | 유월 |

입구가 흐름 도중에 사용자에게 묻는 지점은 모두 「요청한 팀원」에게 간다. 유월에게만 가는 것은
제품 기획 기준 변경 승인과 최종 PR 컨펌이다.

## 1. 시작: 요청 분류와 두 질문

1. 요청에 기존 GitHub Issue URL이 있으면 문서 단계를 건너뛰고 5절 구현 단계부터 시작한다.
2. 요청만으로 알 수 없을 때만 다음 두 가지를 이 순서로 묻는다. 요청으로 알 수 있으면 묻지 않는다.
   1. 영역: 프론트만 / 백엔드만 / 둘 다. 기본은 프론트와 백엔드가 각자의 파이프라인으로 간다.
      「둘 다」(풀스택)는 열어만 두고, 해당 영역 담당자의 컨펌과 PR 어프루브를 모두 받아야 한다.
   2. 완료 조건: 이슈까지만 / 개발까지.
3. 그 밖의 순서 판단(백엔드가 선행돼야 하는지 등)은 AI가 한다. 문제가 생기면 그때 규칙을 더한다.
4. 상태 파일을 만든다(2절). 기획자용과 개발자용 흐름을 나누지 않는다.

## 2. 실행 모델 (Claude Code와 Codex 공통)

### 제약과 대응

| 제약 | 대응 |
| --- | --- |
| 서브 에이전트는 다른 서브 에이전트를 호출할 수 없다 | 입구(메인 세션)가 서브 에이전트를 순서대로 부르고 앞 서브 에이전트의 결과를 다음 서브 에이전트의 입력으로 넘긴다. 각 서브 에이전트는 반환값 `next`에 「다음에 부를 서브 에이전트와 넘길 메시지」를 넣는다. 서브 에이전트가 다음 협력자를 판단하고 실행은 입구가 맡는다. |
| 서브 에이전트는 작업 도중 사용자에게 질문할 수 없다 | 서브 에이전트는 질문이 생기면 `needs_user_input` 상태와 질문, 예상 사이드 이펙트를 반환하고 끝난다. 입구가 사용자에게 묻고 답을 붙여 같은 서브 에이전트를 다시 부른다. |
| 서브 에이전트는 매번 빈 컨텍스트에서 시작한다 | 실행마다 상태 파일을 두고, 문서 내용 대신 노션 페이지 URL, Figma URL, 이슈 번호를 넘긴다. |
| 에이전트 팀은 비용이 크고 실험 기능이다 | 문서 단계와 구현 단계 모두 입구와 서브 에이전트로만 만든다. 에이전트 팀은 쓰지 않는다. |

### 상태 파일

- 위치: `${TMPDIR:-/tmp}/knot-feature/<기능-slug>/state.json`. 저장소 밖이며 커밋하지 않는다.
  디렉터리는 `700`, 파일은 `600`으로 현재 사용자만 읽게 한다.
- 내용: 요청 원문, 영역, 완료 조건, 사용자 답변, 서브 에이전트별 반환값(반환 규약 그대로), 이슈 URL, PR URL.
  구조는 `references/return-contract.md`에 있다. 문서 본문, 토큰, 비밀번호, 개인정보는 넣지 않는다.
- 서브 에이전트를 부를 때는 상태 파일 경로와 메시지 문장, 필요한 사용자 답변만 넘긴다. 서브 에이전트가 돌아오면
  반환값을 상태 파일에 덧붙인다.
- 흐름이 끝나 보고까지 마치면 삭제한다. `needs_user_input`이나 `blocked`로 멈췄으면 재개를 위해
  남긴다. 이슈 서브 에이전트가 쓰는 Issue 계약 snapshot은 기존 규칙대로 판정 직후 삭제한다.

### 서브 에이전트와 정의 파일

| 서브 에이전트 | 정본 | Claude Code 진입점 | 부르는 조건 |
| --- | --- | --- | --- |
| 기능 요구사항 | `subagents/requirements.md` | `knot-feature-requirements` | 항상 먼저 |
| 도메인 규칙 | `subagents/domain-rules.md` | `knot-feature-domain-rules` | 백엔드 길에서 기능 요구사항이 `next`로 지목할 때 |
| API 명세 | `subagents/api-spec.md` | `knot-feature-api-spec` | 도메인 규칙이 `next`로 지목할 때 |
| 디자인 | `subagents/design.md` | `knot-feature-design` | 프론트 길에서 Figma 링크가 없을 때만 |
| QA 시트 | `subagents/qa-sheet.md` | `knot-feature-qa-sheet` | 기능 요구사항이 바뀌면 반드시 |
| 이슈 | `subagents/issue.md` | `knot-feature-issue` | 문서 갱신이 끝났을 때 |

서브 에이전트가 아닌 것은 다음과 같다.

- 기획서: 읽기 전용 참조 문서다. 기능 요구사항 서브 에이전트가 직접 읽는다. 규칙은
  `references/sources.md`의 「기획서는 읽기만」에 있다.
- FE 구현 하네스, BE 구현 하네스: 입구(메인 세션)가 직접 수행하는 절차다. 기존 프론트 하네스가
  Agent 도구와 대화형 스킬을 쓰는데 서브 에이전트 안에서는 그것을 쓸 수 없기 때문이다. 절차는
  `references/fe-implementation.md`, `references/be-implementation.md`에 있다.
- QA (E2E): FE 구현 절차 안에서 그대로 수행하는 절차다. 사람도 입구도 따로 부르지 않는다. 절차는
  `references/qa-e2e.md`에 있다.

### 서브 에이전트를 부르는 방법

- Claude Code: `.claude/agents/knot-feature-*.md`를 Agent 도구로 한 번에 하나씩 실행한다. 프롬프트에는
  상태 파일 경로, 메시지 문장, 사용자 답변(있으면)만 넣는다.
- Codex: 서브 에이전트를 띄울 수단이 있으면 같은 `subagents/*.md`로 띄운다. 없으면 입구 세션이 해당
  정의 파일을 읽고 그 서브 에이전트로서 한 단계만 수행한 뒤 같은 반환 규약으로 상태 파일에 기록한다.
  이때도 서브 에이전트 규칙(다른 서브 에이전트를 부르지 않기, 사용자에게 묻지 않기, 쓰기 권한 안에서만)은 그대로다.
- 모든 서브 에이전트는 `references/return-contract.md`의 JSON 하나를 돌려준다. 입구는
  `python3 harness/feature_pipeline.py result <file>`로 검증한 뒤 이 값만 보고 다음 행동을 정하고,
  이슈와 PR의 「노션 변경 사항」은 같은 스크립트의 `render`로 만든다. 노션 MCP나 Figma MCP가 없는 세션에서는 해당 서브 에이전트가 `blocked`로 돌아온다.

### 반환값 처리

| `status` | 입구가 하는 일 |
| --- | --- |
| `done` | `changed`를 상태 파일에 모으고 `next`의 서브 에이전트를 적힌 메시지로 순서대로 부른다. `next`가 비어 있으면 그 갈래는 끝이다. |
| `needs_user_input` | `question`과 `side_effects`를 그대로 사용자에게 보여 주고 답을 받는다. 답을 상태 파일에 적고 같은 서브 에이전트를 같은 메시지로 다시 부른다. |
| `blocked` | 권한, 접근 실패, 정본 부재처럼 사람이 환경을 손봐야 하는 경우다. 추측으로 우회하지 않고 원인과 손볼 것을 보고하고 멈춘다. |

## 3. 메시지: 언제 누구를 부르나

아래 문장을 그대로 쓴다. 화살표는 직접 호출이 아니라 입구가 중계하는 결과 전달이다.

| 보내는 쪽 | 받는 쪽 | 메시지 | 조건 |
| --- | --- | --- | --- |
| 사용자 | 입구 스킬 | 「○○ 기능 구현해 줘」 | 항상 |
| 입구 스킬 | 기능 요구사항 | 요청 전달, 「기존과 대조해 업데이트해라」 | 항상 먼저 들른다. 바로 구현으로 가지 않는다. |
| 기능 요구사항 | 입구 스킬 | 충돌 보고와 사이드 이펙트 브리핑 | 기존 요구사항과 충돌할 때. 작업을 멈추고 답을 기다린다. |
| 기능 요구사항 | 도메인 규칙 | 바뀐 기능 요구사항 전달, 「업데이트해라」 | 백엔드 길이고 도메인 규칙이 바뀌어야 할 때만 |
| 도메인 규칙 | API 명세 | 변경 사항 전달, 「업데이트해라」 | 도메인 규칙이 바뀌었을 때 |
| 기능 요구사항 | 디자인 | 「업데이트해라」 | 프론트 길이고 화면 요구가 바뀌었는데 Figma 링크가 없을 때 |
| 기능 요구사항 | QA 시트 | 「시나리오 뽑아 업데이트해라」 | 기능 요구사항이 바뀌면 반드시 |
| 기능 요구사항 또는 API 명세 | 이슈 | 「이슈 생성해」 | 문서 갱신이 끝났을 때 |
| 이슈 | 입구 스킬 | 생성된 이슈 번호와 URL | 항상 |
| 입구 스킬 | FE 또는 BE 구현 하네스 | 이슈 URL 전달, 「구현해라」 | 완료 조건이 「개발까지」일 때만 |
| 구현 하네스 | 입구 스킬 | PR URL | 구현과 PR이 끝났을 때 |

## 4. 문서 단계와 이슈

1. 기능 요구사항 서브 에이전트에 요청을 전달하며 「기존과 대조해 업데이트해라」로 시작한다. 바로 구현으로
   가지 않는다.
2. 기능 요구사항이 충돌을 보고하면(`needs_user_input`) 사이드 이펙트 브리핑을 사용자에게 그대로
   보여 주고 답을 받아 다시 부른다. 답 없이 진행하지 않는다.
3. 각 서브 에이전트의 `next`를 따라 도메인 규칙과 API 명세(백엔드 길), 디자인(프론트 길, 링크 없을 때),
   QA 시트(바뀌면 항상)를 부른다. 위쪽 길(도메인 규칙, API 명세)은 백엔드만 가고, 규칙과 명세가
   이미 있으면 기능 요구사항에서 바로 이슈로 간다. 디자인은 이슈 생성에 영향을 주지 않으므로
   디자인 결과가 없어도 이슈는 만든다.
4. 문서 갱신이 끝나면 이슈 서브 에이전트를 「이슈 생성해」로 부르며 상태 파일의 `changed` 목록을 넘긴다.
   이슈 서브 에이전트는 기존 `$knot-issue-planning` 하네스를 그대로 쓴다.
   - 인터뷰, Grill, 담당자 확인처럼 사용자에게 물을 것이 생기면 이슈 서브 에이전트가 `needs_user_input`으로
     돌아온다. 입구가 한 질문씩 묻고 답을 붙여 다시 부른다.
   - 실제 GitHub 게시는 사용자가 현재 요청에서 명시적으로 허용했을 때만 한다. 허용이 없으면
     dry-run 본문을 보여 주고 게시 여부를 한 번 묻는다. `--publish` 권한은 이 답에서만 나온다.
5. 이슈 번호와 URL을 받는다. 완료 조건이 「이슈까지만」이면 여기서 끝내고 보고한다. 생성된 이슈를
   확인하도록 권하되 필수로 막지 않는다.

## 5. 구현 단계 (입구가 직접 수행)

- 완료 조건이 「개발까지」일 때만 시작한다. 프론트는 `references/fe-implementation.md`, 백엔드는
  `references/be-implementation.md`의 절차를 입구(메인 세션)가 직접 수행한다. 기준 문서의 FE, BE
  구현 하네스가 이 절차다. 「구현해라」와 이슈 URL이 시작 입력이다.
- 서브 에이전트로 띄우지 않는 이유: 기존 프론트 하네스는 `code-reviewer` 에이전트와 `review`
  스킬의 파일별 에이전트(Agent 도구), `create-pr-content`(대화형)를 쓰는데, 서브 에이전트 안에서는
  Agent 도구와 사용자 질문을 쓸 수 없다. 기존 FE, BE 하네스를 그대로 쓰라는 요구를 지키려면
  메인 세션이 해야 한다.
- 둘 다면 워크트리를 둘로 나눠 차례로 하고 PR도 둘이다. 한 사람이 프론트와 백엔드를 모두
  구현해도 PR은 `[FE]`, `[BE]`로 나눠 각각 올린다. 백엔드 선행 여부 같은 순서는 AI가 정한다.
- 기존 이슈 URL로 시작한 경우도 같다. 이슈 본문의 「노션 변경 사항」이 읽을 정본 위치다.
- 기존 스킬이 사람에게 확인받는 단계(`create-story`의 목록 확인, `create-pr-content`의 안내 문구
  받기와 PR 열기 확인, 프론트 `commit` 스킬과 백엔드 `knot-commit`, `knot-pr`의 승인)는 완료 조건
  「개발까지」가 대신한다. 각 스킬에 이 예외가 적혀 있다. 결과(스토리 목록, 안내 문구)는 PR 본문에
  적는다.
- 구현 뒤에는 QA가 온다. QA를 하는 수단은 E2E 테스트이고, PR을 올린 뒤 PR CI의 E2E 결과를
  확인한다. 실패하면 실패 루프 규칙대로 고치고, 통과한 뒤에야 끝난다. E2E 통과와 시나리오 설명이
  PR에 보이고 사람은 설명만 읽는다.
- 요구사항이나 명세 문제를 발견하면 문서 단계로 되돌리지 않고 멈춰 사용자에게 묻는다. 테스트 실패
  수정 3회를 넘기면 멈추고 원인과 시도 내역을 보고한다.
- 끝나면 같은 반환 규약 모양으로 상태 파일에 기록하고(`changed`에 PR) PR URL을 보고한다.

## 6. 끝내기와 보고

보고에는 다음만 담는다.

- 만든 이슈 번호와 URL, PR URL(FE, BE 각각).
- 「노션 변경 사항」: 상태 파일의 `changed` 목록을 링크로.
- 사람이 할 일: PR 최종 컨펌(유월, 모든 도메인), 풀스택이면 두 도메인 팀의 컨펌과 어프루브, 멈춘 지점이
  있으면 그 원인과 재개 조건.
- 기본값으로 처리한 미결 사항.

## 완료 기준

- 두 질문 외에는 요청으로 알 수 있는 것을 묻지 않았다.
- 기능 요구사항 서브 에이전트를 항상 먼저 불렀고, 충돌은 사용자 답 없이 진행하지 않았다.
- 모든 서브 에이전트 반환값이 규약 JSON이고 상태 파일에 있다.
- 이슈와 PR 맨 위에 「노션 변경 사항」 링크가 있다.
- 사용자가 허용한 이슈 게시와 PR 생성 외에 원격을 바꾸지 않았고 merge는 하지 않았다.
- 기획서를 고치지 않았고, 노션과 Figma 문서를 저장소로 옮기지 않았다.
- 상태 파일과 snapshot은 저장소 밖에 있고 커밋되지 않았다.

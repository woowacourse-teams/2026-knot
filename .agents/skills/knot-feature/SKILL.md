# Knot Feature 입구 스킬

「○○ 기능 구현해 줘」 한 문장이 기능 요구사항 갱신, QA 시트, 이슈, 구현, 테스트, PR까지 끝까지
가고, 사람은 PR에서 한 번 컨펌한다. 이 스킬은 그 흐름의 입구다.

한 문장 책임: 요청을 받아 작업 범위와 완료 조건을 정하고, 스크립트가 정한 순서대로 서브 에이전트를
실행해 결과를 넘기며, 사용자에게 물을 일을 시작에 모아 대신 묻는다. 읽기는 전부, 쓰기는 상태 파일만.

## 정본과 금지

- 노션과 Figma가 정본이다. 위치는 `references/sources.md`에 있다. 문서 내용을 손으로 저장소
  Markdown에 옮기지 않는다.
- 기획서는 읽기만 한다. 요청이 기획서 수정을 필요로 하면 거부하고 유월에게 컨펌받으라고 안내한
  뒤 끝낸다.
- 스프린트 시트의 이슈(태스크)는 다루지 않는다. 상위 이슈는 만들지 않는다. 처음 요청이 상위 이슈
  역할을 한다.
- 디자인이 먼저 바뀌어 얽힌 문서를 따라 고치는 역방향 흐름은 범위 밖이다. 새 디자인도 만들지 않는다.
- 입구는 모든 판단을 떠안는 무거운 오케스트레이터가 되지 않는다. 어느 서브 에이전트를 다음에
  부를지는 `harness/feature_pipeline.py next`가 상태 파일만 보고 정하고, 입구는 그 결과를 실행한다.
  서브 에이전트는 사실(`flags`)만 돌려준다.
- 명령은 저장소에서 터미널(Claude Code, Codex)로 내린다.

## 이 흐름 밖의 작업

모든 작업이 이 흐름을 타는 것이 아니다. 기준은 「사용자가 보는 동작이 바뀌는가」다.

| 요청 | `kind` | 경로 |
| --- | --- | --- |
| 새 기능, 기존 동작 변경 | `feature` | 문서 단계 → 이슈 → 구현 |
| 깨진 것을 고침: 버그, 오타, 스타일 어긋남, 동작은 그대로 | `fix` | 이슈 → 구현. 문서 단계를 건너뛰고 노션을 읽지 않는다 |
| 코드 내부만: 리팩터링, 의존성, 설정 | `chore` | 이슈 → 구현. 문서 단계를 건너뛴다 |
| 하네스 경로 수정 (`harness/`, `.agents/`, `.claude/`, `docs/harness/`, `frontend/.claude/`, `backend/.agents/`, `backend/.claude/`) | 해당 없음 | 이 스킬과 Issue 계약을 거치지 않는다. `docs/harness/harness-verification.md`의 하네스 수정 경로를 따른다 |

`fix`와 `chore`는 기존 FE, BE 하네스(`frontend/CLAUDE.md`, `backend/.agents/skills`)만으로도 할 수
있다. 사용자가 이 스킬을 불렀을 때만 `kind`를 적고 이슈부터 간다. 고치다가 동작이 바뀌어야 한다는
것을 알게 되면 멈추고 `feature`로 다시 시작할지 묻는다.

## 역할과 권한 (2026-10-22 결정)

도메인 팀(녹음팀, 문서팀, 탐색 등)이 자기 도메인의 기획 권한(기능 요구사항, 도메인 규칙,
API 명세, QA 시나리오)과 디자인 권한(Figma)을 가진다. 흐름 도중의 도메인 판단은 그 팀이
내린다. 유월은 올라온 PR을 최종 컨펌하고(모든 도메인), 도메인을 가로지르는 전체 제품 플로우
QA와 제품 기획 기준(전체 스펙) 변경 승인을 맡는다.

| 결정 지점 | 누가 결정하나 |
| --- | --- |
| 시작: 종류, 영역, 완료 조건, 게시 허용 | 요청한 팀원 |
| 요구사항이 기존과 충돌 | 그 도메인 팀 |
| 디자인 필요(기존 화면 없음) | 그 도메인 팀 (디자인 권한) |
| 테스트 3회 실패, 문서 문제 | 요청한 팀원 (멈춤 보고) |
| 프론트와 백엔드 동시 변경 | 두 도메인 팀 합의. PR은 `[FE]`, `[BE]`로 나눠 각각 올린다 |
| 제품 기획 기준(전체 스펙) 변경 | 유월 승인. 하네스는 거부한다 |
| 최종 PR 컨펌 | 유월 |

입구가 사용자에게 묻는 지점은 모두 「요청한 팀원」에게 간다. 유월에게만 가는 것은
제품 기획 기준 변경 승인과 최종 PR 컨펌이다.

## 1. 시작: 요청 분류와 질문 한 번

사람이 불려 오는 지점은 시작과 끝(PR)이다. 중간에 끊지 않으려고 물을 것을 시작에 모은다.

1. 요청에 기존 GitHub Issue URL이 있으면 문서 단계를 건너뛰고 구현 단계부터 시작한다.
2. 요청을 분류한다(「이 흐름 밖의 작업」 표). 요청만으로 알 수 없으면 `kind`도 질문에 넣는다.
3. 요청만으로 알 수 없는 것만 아래 순서로 한 번에 묶어 묻는다. 요청으로 알 수 있으면 묻지 않는다.
   1. 종류: 동작이 바뀌는가(feature) / 깨진 것을 고치는가(fix) / 코드 내부만인가(chore).
   2. 영역: 프론트만 / 백엔드만 / 둘 다. 기본은 프론트와 백엔드가 각자의 파이프라인으로 간다.
      「둘 다」(풀스택)는 열어만 두고, 해당 영역 담당자의 컨펌과 PR 어프루브를 모두 받아야 한다.
   3. 완료 조건: 이슈까지만 / 개발까지.
   4. 이슈 게시 허용: 「개발까지」면 이슈 게시 없이는 갈 수 없으므로 여기서 받는다. 「이슈까지만」도
      dry-run으로 끝낼지 게시까지 할지 여기서 받는다. 이 답이 `remote_write_authorized`가 된다.
4. 묻기 전에 읽기만으로 알 수 있는 것은 미리 읽어 질문에 붙인다. 기존 요구사항과 겹치는 ID가 있는지,
   화면이면 Figma 링크가 노션 화면 정책에 있는지. 읽기만 하고 아무것도 고치지 않는다.
5. 그 밖의 순서 판단(백엔드가 선행돼야 하는지 등)은 `implementation_order`로 상태 파일에 적는다.
   기본은 백엔드 먼저다.
6. 상태 파일을 만든다(2절). 기획자용과 개발자용 흐름을 나누지 않는다.

## 2. 실행 모델 (Claude Code와 Codex 공통)

### 제약과 대응

| 제약 | 대응 |
| --- | --- |
| 서브 에이전트는 다른 서브 에이전트를 호출할 수 없다 | 입구(메인 세션)가 서브 에이전트를 한 번에 하나씩 부르고 앞 단계의 결과를 상태 파일로 넘긴다. 다음에 누구를 부를지는 `python3 harness/feature_pipeline.py next <state.json>`이 정한다. 서브 에이전트는 사실(`flags`)만 돌려주고 분기를 판단하지 않는다. |
| 서브 에이전트는 작업 도중 사용자에게 질문할 수 없다 | 서브 에이전트는 질문이 생기면 `needs_user_input` 상태와 질문, 예상 사이드 이펙트를 반환하고 끝난다. 입구는 4절의 두 등급 기준으로 사용자에게 묻거나 기본값으로 진행한다. |
| 서브 에이전트는 매번 빈 컨텍스트에서 시작한다 | 실행마다 상태 파일을 두고, 문서 내용 대신 노션 페이지 URL, Figma URL, 이슈 번호를 넘긴다. |
| 에이전트 팀은 비용이 크고 실험 기능이다 | 문서 단계와 구현 단계 모두 입구와 서브 에이전트로만 만든다. 에이전트 팀은 쓰지 않는다. |
| AI는 지침 문장을 무시할 수 있다 | 지켜져야 하는 규칙은 도구 제한(`.claude/agents/*.md`의 `disallowedTools`), 검증기, CI 중 하나에 둔다. 문장은 의도를 설명하는 용도다. 아직 문장뿐인 규칙은 `docs/harness/improvement-log.md`에 적어 둔다. |

### 상태 파일

- 위치: `${TMPDIR:-/tmp}/knot-feature/<기능-slug>/state.json`. 저장소 밖이며 커밋하지 않는다.
  디렉터리는 `700`, 파일은 `600`으로 현재 사용자만 읽게 한다.
- 내용: 요청 원문, 종류, 영역, 완료 조건, 사용자 답변, 기본값으로 처리한 미결, 서브 에이전트별
  반환값(반환 규약 그대로), 이슈 URL, PR URL. 구조는 `references/return-contract.md`에 있다. 문서
  본문, 토큰, 비밀번호, 개인정보는 넣지 않는다.
- 서브 에이전트를 부를 때는 상태 파일 경로와 메시지 문장, 필요한 사용자 답변만 넘긴다. 서브 에이전트가 돌아오면
  반환값을 검증해 상태 파일에 덧붙이고 다시 `next`를 실행한다.
- 작업을 끊었다 돌아오면 `python3 harness/feature_pipeline.py status <state.json>`을 먼저 실행한다.
  끝난 단계, 다음 단계, 기다리는 답, 기본값으로 처리한 것이 나온다.
- 흐름이 끝나 보고까지 마치면 삭제한다. `needs_user_input`이나 `blocked`로 멈췄으면 재개를 위해
  남긴다. 이슈 서브 에이전트가 쓰는 Issue 계약 snapshot은 기존 규칙대로 판정 직후 삭제한다.

### 서브 에이전트와 정의 파일

| 서브 에이전트 | 정본 | Claude Code 진입점 | `next`가 부르는 조건 |
| --- | --- | --- | --- |
| 기능 요구사항 | `subagents/requirements.md` | `knot-feature-requirements` | `feature`면 항상 먼저 |
| 도메인 규칙 | `subagents/domain-rules.md` | `knot-feature-domain-rules` | 백엔드 길이고 `backend_rules_affected` |
| API 명세 | `subagents/api-spec.md` | `knot-feature-api-spec` | 도메인 규칙이 `domain_rules_changed` |
| 디자인 | `subagents/design.md` | `knot-feature-design` | 프론트 길이고 `screen_changed`인데 `figma_url`이 없을 때 |
| QA 시트 | `subagents/qa-sheet.md` | `knot-feature-qa-sheet` | `requirements_changed` |
| 이슈 | `subagents/issue.md` | `knot-feature-issue` | 문서 단계가 끝났을 때. `fix`, `chore`는 바로 |

진입점 파일의 `disallowedTools`가 각 서브 에이전트의 쓰기 범위를 도구 수준에서 막는다. 노션 문서
서브 에이전트는 Figma와 저장소 파일을 못 고치고, 디자인은 노션을 못 고치며, 이슈는 코드를 못 고친다.

서브 에이전트가 아닌 것은 다음과 같다.

- 기획서: 읽기 전용 참조 문서다. 기능 요구사항 서브 에이전트가 직접 읽는다. 규칙은
  `references/sources.md`의 「기획서는 읽기만」에 있다.
- FE 구현 하네스, BE 구현 하네스: 입구(메인 세션)가 직접 수행하는 절차다. 기존 프론트 하네스가
  Agent 도구와 대화형 스킬을 쓰는데 서브 에이전트 안에서는 그것을 쓸 수 없기 때문이다. 절차는
  `references/fe-implementation.md`, `references/be-implementation.md`에 있다.
- QA (E2E): FE 구현 절차 안에서 그대로 수행하는 절차다. 사람도 입구도 따로 부르지 않는다. 절차는
  `references/qa-e2e.md`에 있다.

### 서브 에이전트를 부르는 방법

- Claude Code: `.claude/agents/knot-feature-*.md`를 Agent 도구로 한 번에 하나씩 실행한다. 프롬프트에는
  상태 파일 경로, 메시지 문장, 사용자 답변(있으면)만 넣는다.
- Codex: 서브 에이전트를 띄울 수단이 있으면 같은 `subagents/*.md`로 띄운다. 없으면 입구 세션이 해당
  정의 파일을 읽고 그 서브 에이전트로서 한 단계만 수행한 뒤 같은 반환 규약으로 상태 파일에 기록한다.
  이때도 서브 에이전트 규칙(다른 서브 에이전트를 부르지 않기, 사용자에게 묻지 않기, 쓰기 권한 안에서만)은 그대로다.
- 모든 서브 에이전트는 `references/return-contract.md`의 JSON 하나를 돌려준다. 입구는
  `python3 harness/feature_pipeline.py result <file>`로 검증한 뒤 상태 파일에 붙이고
  `python3 harness/feature_pipeline.py next <state.json>`이 가리키는 서브 에이전트를 부른다.
  이슈와 PR의 「노션 변경 사항」은 같은 스크립트의 `render`로 만든다. 노션 MCP나 Figma MCP가 없는
  세션에서는 해당 서브 에이전트가 `blocked`로 돌아온다.

### 반환값 처리

| `status` | 입구가 하는 일 |
| --- | --- |
| `done` | 반환값을 상태 파일에 붙이고 `next`를 실행해 가리키는 서브 에이전트를 부른다. `finished`면 그 갈래는 끝이다. |
| `needs_user_input` | 4절의 두 등급으로 나눈다. 멈춰야 하는 등급이면 `question`과 `side_effects`를 그대로 사용자에게 보여 주고 답을 `answers`에 적은 뒤 `next`가 가리키는 대로 같은 서브 에이전트를 다시 부른다. 기본값으로 갈 수 있는 등급이면 `assumptions`에 적고 답으로 붙여 다시 부른다. |
| `blocked` | 권한, 접근 실패, 정본 부재처럼 사람이 환경을 손봐야 하는 경우다. 추측으로 우회하지 않고 원인과 손볼 것을 보고하고 멈춘다. |

## 3. 분기: 언제 누구를 부르나

아래 표는 `harness/feature_pipeline.py`의 `next_stage`와 같은 규칙이다. 둘이 다르면 코드가 정본이고
이 표를 고친다. 메시지 문장은 그대로 쓴다.

| 받는 쪽 | 메시지 | `next`가 부르는 조건 |
| --- | --- | --- |
| 기능 요구사항 | 요청 전달, 「기존과 대조해 업데이트해라」 | `feature`면 항상 먼저. 바로 구현으로 가지 않는다. |
| 도메인 규칙 | 바뀐 기능 요구사항 전달, 「업데이트해라」 | 백엔드 길이고 기능 요구사항이 `backend_rules_affected: true` |
| API 명세 | 변경 사항 전달, 「업데이트해라」 | 도메인 규칙이 `domain_rules_changed: true` |
| 디자인 | 「업데이트해라」 | 프론트 길이고 `screen_changed: true`인데 `figma_url`이 없을 때 |
| QA 시트 | 「시나리오 뽑아 업데이트해라」 | `requirements_changed: true` |
| 이슈 | 「이슈 생성해」 | 위 단계가 모두 끝났을 때. `fix`, `chore`는 문서 단계 없이 바로. 기존 이슈 URL이 있으면 건너뛴다 |
| FE 또는 BE 구현 하네스 | 이슈 URL 전달, 「구현해라」 | 완료 조건이 「개발까지」일 때만. 둘 다면 `implementation_order` 순서 |

서브 에이전트가 입구에 돌려주는 것은 반환 규약 JSON뿐이다. 충돌 보고와 사이드 이펙트 브리핑은
`needs_user_input`과 `side_effects`로, 이슈 번호와 PR URL은 `changed`로 온다.

## 4. 문서 단계와 중간 미결의 두 등급

1. `feature`는 기능 요구사항 서브 에이전트에 요청을 전달하며 「기존과 대조해 업데이트해라」로
   시작한다. 바로 구현으로 가지 않는다.
2. 중간에 `needs_user_input`이 오면 두 등급으로 나눈다.
   - 멈춰서 묻는다: 기존 동작을 바꾸는 요구사항 충돌(사이드 이펙트 브리핑을 그대로 보여 준다),
     원격 쓰기 권한(이슈 게시, PR), 디자인이 필요한데 화면이 없는 경우, 유월 승인이 필요한 기획서
     변경. 답 없이 진행하지 않는다.
   - 기본값으로 가고 적는다: 위치, 표현, 순서, 이름처럼 되돌리기 쉬운 미결. 서브 에이전트의
     `question`에 적힌 권장안을 답으로 삼아 `assumptions`에 「무엇을 왜 가정했나」를 적고 같은
     서브 에이전트를 다시 부른다. 끝내기 보고와 PR 본문에 전부 올린다.
   사람이 중간에 불려 오는 것은 첫 번째 등급뿐이다.
3. `next`를 따라 도메인 규칙과 API 명세(백엔드 길), 디자인(프론트 길, 링크 없을 때), QA 시트(바뀌면
   항상)를 부른다. 디자인은 이슈 생성에 영향을 주지 않으므로 디자인 결과가 없어도 이슈는 만든다.
4. 문서 갱신이 끝나면 이슈 서브 에이전트를 「이슈 생성해」로 부르며 상태 파일의 `changed` 목록을 넘긴다.
   이슈 서브 에이전트는 기존 `$knot-issue-planning` 하네스를 그대로 쓴다.
   - 인터뷰, Grill, 담당자 확인처럼 사용자에게 물을 것이 생기면 이슈 서브 에이전트가 `needs_user_input`으로
     돌아온다. 인터뷰와 Grill은 멈춰서 묻는 등급이고, 담당자와 라벨은 기본값 등급이다(공통 라벨 규칙).
   - 실제 GitHub 게시는 시작에서 받은 `remote_write_authorized`가 `true`일 때만 한다. 허용이 없으면
     dry-run 본문을 보여 주고 끝낸다. `--publish` 권한은 시작의 답에서만 나온다.
5. 이슈 번호와 URL을 받는다. 완료 조건이 「이슈까지만」이면 여기서 끝내고 보고한다. 생성된 이슈를
   확인하도록 권하되 필수로 막지 않는다.

## 5. 구현 단계 (입구가 직접 수행)

- 완료 조건이 「개발까지」일 때만 시작한다. 프론트는 `references/fe-implementation.md`, 백엔드는
  `references/be-implementation.md`의 절차를 입구(메인 세션)가 직접 수행한다. 기준 문서의 FE, BE
  구현 하네스가 이 절차다. 「구현해라」와 이슈 URL이 시작 입력이다.
- 서브 에이전트로 띄우지 않는 이유: 기존 프론트 하네스는 `code-reviewer` 에이전트와 `review`
  스킬의 파일별 에이전트(Agent 도구), `create-pr-content`(대화형)를 쓰는데, 서브 에이전트 안에서는
  Agent 도구와 사용자 질문을 쓸 수 없다. 기존 FE, BE 하네스를 그대로 쓰라는 요구를 지키려면
  메인 세션이 해야 한다.
- 둘 다면 워크트리를 둘로 나눠 `implementation_order` 순서로 하고 PR도 둘이다. 한 사람이 프론트와
  백엔드를 모두 구현해도 PR은 `[FE]`, `[BE]`로 나눠 각각 올린다.
- 기존 이슈 URL로 시작한 경우도 같다. 이슈 본문의 「노션 변경 사항」이 읽을 정본 위치다.
- 기존 스킬이 사람에게 확인받는 단계(`create-story`의 목록 확인, `create-pr-content`의 안내 문구
  받기와 PR 열기 확인, 프론트 `commit` 스킬과 백엔드 `knot-commit`, `knot-pr`의 승인)는 완료 조건
  「개발까지」가 대신한다. 각 스킬에 이 예외가 적혀 있다. 결과(스토리 목록, 안내 문구)는 PR 본문에
  적는다.
- 구현 뒤에는 QA가 온다. QA를 하는 수단은 E2E 테스트이고, PR을 올린 뒤 PR CI의 E2E 결과를
  확인한다. 실패하면 실패 루프 규칙대로 고치고, 통과한 뒤에야 끝난다. E2E 통과와 시나리오 설명이
  PR에 보이고 사람은 설명만 읽는다.
- 요구사항이나 명세 문제를 발견하면 문서 단계로 되돌리지 않고 멈춰 사용자에게 묻는다. 테스트 실패
  수정 3회를 넘기면 멈추고 원인과 시도 내역을 보고한다.
- 끝나면 같은 반환 규약 모양으로 상태 파일에 기록하고(`changed`에 PR) PR URL을 보고한다.

## 6. 끝내기와 보고

보고에는 다음만 담는다.

- 만든 이슈 번호와 URL, PR URL(FE, BE 각각).
- 「노션 변경 사항」: 상태 파일의 `changed` 목록을 링크로.
- 사람이 할 일: PR 최종 컨펌(유월, 모든 도메인), 풀스택이면 두 도메인 팀의 컨펌과 어프루브, 멈춘 지점이
  있으면 그 원인과 재개 조건.
- 기본값으로 처리한 미결 사항: 상태 파일의 `assumptions` 전부. PR 본문에도 같은 목록을 넣는다.

## 완료 기준

- 시작의 질문 한 번 외에는 요청으로 알 수 있는 것을 묻지 않았고, 중간에 사람을 부른 것은 4절의
  첫 번째 등급뿐이다.
- 다음 서브 에이전트는 매번 `feature_pipeline.py next`가 정했고 입구가 임의로 고르지 않았다.
- `feature`는 기능 요구사항 서브 에이전트를 항상 먼저 불렀고, 충돌은 사용자 답 없이 진행하지 않았다.
- 모든 서브 에이전트 반환값이 규약 JSON이고 상태 파일에 있다.
- 이슈와 PR 맨 위에 「노션 변경 사항」 링크가 있고, PR에 기본값으로 처리한 미결 사항이 있다.
- 사용자가 허용한 이슈 게시와 PR 생성 외에 원격을 바꾸지 않았고 merge는 하지 않았다.
- 기획서를 고치지 않았고, 노션과 Figma 문서를 손으로 저장소에 옮기지 않았다.
- 상태 파일과 snapshot은 저장소 밖에 있고 커밋되지 않았다.

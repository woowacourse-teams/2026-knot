# Knot Feature 입구 스킬

「○○ 기능 구현해 줘」 한 문장이 기능 요구사항 갱신, QA 시트, 이슈, 구현, 테스트, PR까지 끝까지
가고, 사람은 PR에서 컨펌한다. 기능을 추가, 수정, 삭제하는 요청만 노션 정본과 이슈를 고치기 전에
제안을 만들어 1차 컨펌을 한 번 더 받는다. 이 스킬은 그 흐름의 입구다.

한 문장 책임: 요청을 받아 작업 범위와 완료 조건을 정하고, 서브 에이전트를 순서대로 실행해 결과를 넘기며,
사용자에게 물을 일을 대신 묻는다. 읽기는 전부, 쓰기는 상태 파일만.

## 정본과 금지

- 노션과 Figma가 정본이다. 위치는 `references/sources.md`에 있다. 문서 내용을 저장소 Markdown으로
  옮기지 않는다.
- 기획서는 기능 요구사항 서브 에이전트가 읽고, 기능에 필요하면 함께 고친다. 규칙은
  `references/sources.md`의 「기획서 고치기」에 있다.
- 정본(기능 요구사항, 기획서, QA 시트)에는 확정된 것만 둔다. 기능 추가, 수정, 삭제는 노션 「기능
  요구사항 검토」 DB에 제안 페이지로 먼저 쓰고, 확정 뒤에 정본에 반영한다. 제안 페이지는 구현
  근거로 읽지 않는다. 위치와 규칙은 `references/sources.md`의 「기능 요구사항 검토」에 있다.
- 스프린트 시트의 이슈(태스크)는 다루지 않는다. 상위 이슈는 만들지 않는다. 처음 요청이 상위 이슈
  역할을 한다.
- 디자인이 먼저 바뀌어 얽힌 문서를 따라 고치는 역방향 흐름은 범위 밖이다. 새 디자인도 만들지 않는다.
- 입구는 모든 판단을 떠안는 무거운 오케스트레이터가 되지 않는다. 어느 문서를 다음에 갱신할지는
  각 서브 에이전트가 `next`로 판단하고 입구는 실행한다.
- 명령은 저장소에서 터미널(Claude Code, Codex)로 내린다.

## 역할과 권한 (2026-10-22 결정, 2026-10-26 팀 회의 반영)

도메인 팀(녹음팀, 문서팀, 탐색 등)이 자기 도메인의 기획(기능 요구사항, 도메인 규칙, API 명세,
QA 시나리오, 기획서)을 정한다. 평소에는 FE는 FE, BE는 BE 작업을 하고, 기능을 추가하거나 바꾸려는
팀원은 누구든 기획부터 디자인, 개발까지 맡을 수 있다(풀스택). 이때도 PR은 `[FE]`, `[BE]`로 나눈다.
도메인을 가로지르는 전체 제품 플로우 QA와 main 머지는 유월이 맡는다.

기획 컨펌 담당(`harness/team.json`의 `plan_confirmers`, 지금은 유월)이 언제 보는지는 작업 종류로
정해진다. 입구는 요청을 아래 셋 중 하나로 나누고 그대로 따른다.

| 작업 종류 | 개발 전 | PR 승인 |
| --- | --- | --- |
| 확정된 기획대로 개발하거나 피드백을 반영한다 (기능 요구사항이 바뀌지 않음) | 없음 | 같은 영역 팀원 한 명 이상 |
| 개발하다가 기존 기획을 조금 바꿨다 (디자인은 그대로) | 없음 | 같은 영역 팀원 한 명 이상, 그리고 기획 컨펌 담당. PR에 무엇을 왜 바꿨는지 적는다 |
| 기능을 추가, 수정, 삭제한다 (디자인이 바뀌는 변경 포함) | 「기능 요구사항 검토」 DB에 제안 페이지를 만들어 기획 컨펌 담당에게 1차 컨펌. 컨펌 전에는 노션 정본, Figma Design 페이지, 이슈를 바꾸지 않는다 | 같은 영역 팀원 한 명 이상, 그리고 기획 컨펌 담당(2차 컨펌) |

세 번째 경우의 디자인은 1차 컨펌에 함께 보낸다. Figma 편집이 되는 요청자는 「실험 · 반영 전 시안」
페이지에 디자인 초안을 만들어 제안에 붙이고, 편집이 안 되는(플랜 제한) 요청자는 제안에 디자인
요청을 넣어 컨펌 뒤 기획 컨펌 담당이 만든 디자인을 받는다. 기능 추가, 수정, 삭제를 이스타와도 함께
의논하자는 안(사용자 데이터 분석을 맡고 있어 사용 수치를 보고 함께 판단)은 2026-10-26 회의에서
논의 중이다. 정해지면 `plan_confirmers`에 `Eastar-DS`를 더한다.

| 결정 지점 | 누가 결정하나 |
| --- | --- |
| 시작: 영역, 완료 조건, 구현할 사람 | 요청한 팀원 |
| 기능 추가, 수정, 삭제의 방향 (1차 컨펌) | 기획 컨펌 담당. 방향(할지, 범위, 디자인 방향)만 보고, 제안 페이지 `상태`를 확정, 반려, 보류로 바꾼다. 요구사항 문장, 예외 처리, QA 세부는 그 도메인 팀이 정한다 |
| 요구사항이 기존과 충돌 | 그 도메인 팀 |
| 새 디자인 | 1차 컨펌에서 기획 컨펌 담당이 본다. 초안은 Figma 편집이 되는 요청자가, 안 되면 기획 컨펌 담당이 만든다 |
| 이슈 GitHub 게시 허용 | 요청한 팀원 |
| 테스트 3회 실패, 문서 문제 | 요청한 팀원 (멈춤 보고) |
| 프론트와 백엔드 동시 변경 | 두 도메인 팀 합의. PR은 `[FE]`, `[BE]`로 나눠 각각 올린다 |
| 기획서(제품 기획 기준) 변경 | 요청한 팀원. 다른 도메인의 기존 요구사항과 충돌하면 그 도메인 팀. 기능 추가, 수정, 삭제에 딸린 변경이면 1차 컨펌 제안에 넣는다 |
| PR 승인 | 같은 영역 팀원 한 명 이상. 다른 영역 팀원의 승인만으로는 머지하지 않는다. 기획이나 디자인이 바뀌었으면 기획 컨펌 담당도 |
| PR 머지 | PR을 연 사람. 따로 부탁하지 않았으면 승인 조건을 채운 뒤 직접 머지한다. AI는 머지하지 않는다 |
| main 머지 (릴리즈) | 유월. hotfix는 예외 |

이슈와 PR의 담당자(assignee)와 이름 라벨은 실제로 구현하는 사람이다. 이슈를 쓴 사람이나 그
도메인의 평소 담당자로 정하지 않는다. 입구는 시작에서 구현할 사람의 GitHub 계정을 상태 파일
`implementer`에 적고, PR의 담당자, 이름 라벨, 리뷰어, 승인 조건은
`python3 harness/team_roles.py review`로 정한다.

입구가 흐름 도중에 사용자에게 묻는 지점은 모두 「요청한 팀원」에게 간다. 기획 컨펌 담당에게 가는
것은 1차 컨펌(기능 추가, 수정, 삭제)과 PR 리뷰(기획이나 디자인이 바뀐 경우)이고, 입구는 요청자가
바로 보낼 수 있게 제안 페이지와 리뷰어 요청을 준비한다.

## 1. 시작: 요청 분류와 두 질문

1. 요청에 기존 GitHub Issue URL이 있으면 문서 단계를 건너뛰고 5절 구현 단계부터 시작한다.
   요청에 「기능 요구사항 검토」 제안 페이지 URL이 있으면(「이 제안 이어서 해 줘」) 「제안 페이지로
   다시 시작하기」를 따른다.
   「○○ 기능 제안해 줘」처럼 제안만 원하는 요청은 완료 조건을 묻지 않고 제안 페이지를 만든 뒤
   멈춘다. 확정되면 같은 제안 페이지 URL로 다시 시작한다.
2. 요청만으로 알 수 없을 때만 다음 두 가지를 이 순서로 묻는다. 요청으로 알 수 있으면 묻지 않는다.
   1. 영역: 프론트만 / 백엔드만 / 둘 다. 기본은 프론트와 백엔드가 각자의 파이프라인으로 간다.
      「둘 다」(풀스택)는 열어만 두고, 영역마다 그 영역 팀원의 PR 승인을 받아야 한다.
   2. 완료 조건: 이슈까지만 / 개발까지.
3. 구현할 사람을 상태 파일 `implementer`에 적는다. 「개발까지」면 하네스를 실행한 요청자이므로
   `gh api user --jq .login`으로 확인하고 묻지 않는다. 「이슈까지만」이면 누가 구현할지 묻는다.
   `python3 harness/team_roles.py member <계정>`이 실패하면(명단에 없음) `harness/team.json`을
   고치도록 알리고 멈춘다.
4. 그 밖의 순서 판단(백엔드가 선행돼야 하는지 등)은 AI가 한다. 문제가 생기면 그때 규칙을 더한다.
5. 상태 파일을 만든다(2절). 기획자용과 개발자용 흐름을 나누지 않는다.

### 제안 페이지로 다시 시작하기

1차 컨펌은 며칠이 걸릴 수 있고, 그사이 상태 파일이 지워졌거나 다른 기기에서 다시 시작할 수 있다.
그래서 제안 페이지 URL 하나로 이어서 할 수 있게 한다.

1. 제안 페이지를 읽어 `상태`를 본다.
   - 작성 중, 검토 요청, 보류: 아직 컨펌 전이라고 알리고 끝낸다. 보류면 「컨펌 기록」의 보완 요청을
     함께 보여 준다.
   - 반려: 반려 이유를 보여 주고 끝낸다. 정본을 건드리지 않았으므로 되돌릴 것이 없다.
   - 확정: 다음 단계로 간다.
2. 같은 기능의 상태 파일이 있으면 그대로 쓰고, 없으면 제안 페이지로 새로 만든다. `request`는 제안
   제목과 한 줄 요약, `area`는 제안의 「영향」에 적힌 영역, `implementer`는 지금 요청자의 GitHub
   계정이다. 완료 조건이 정해져 있지 않으면 이때 묻는다.
3. `plan_confirmation`을 `confirmed`로 적고(`proposal_url`, `confirmed_by`, `evidence`), 기능
   요구사항을 「기존과 대조해 업데이트해라」로 부른다. 그 뒤는 4절의 3번부터 같다.

## 2. 실행 모델 (Claude Code와 Codex 공통)

### 제약과 대응

| 제약 | 대응 |
| --- | --- |
| 서브 에이전트는 다른 서브 에이전트를 호출할 수 없다 | 입구(메인 세션)가 서브 에이전트를 순서대로 부르고 앞 서브 에이전트의 결과를 다음 서브 에이전트의 입력으로 넘긴다. 각 서브 에이전트는 반환값 `next`에 「다음에 부를 서브 에이전트와 넘길 메시지」를 넣는다. 서브 에이전트가 다음 협력자를 판단하고 실행은 입구가 맡는다. |
| 서브 에이전트는 작업 도중 사용자에게 질문할 수 없다 | 서브 에이전트는 질문이 생기면 `needs_user_input` 상태와 질문, 예상 사이드 이펙트를 반환하고 끝난다. 입구가 사용자에게 묻고 답을 붙여 같은 서브 에이전트를 다시 부른다. |
| 서브 에이전트는 매번 빈 컨텍스트에서 시작한다 | 실행마다 상태 파일을 두고, 문서 내용 대신 노션 페이지 URL, Figma URL, 이슈 번호를 넘긴다. |
| 에이전트 팀은 비용이 크고 실험 기능이다 | 문서 단계와 구현 단계 모두 입구와 서브 에이전트로만 만든다. 에이전트 팀은 쓰지 않는다. |

### 상태 파일

- 위치: `${TMPDIR:-/tmp}/knot-feature/<기능-slug>/state.json`. 저장소 밖이며 커밋하지 않는다.
  디렉터리는 `700`, 파일은 `600`으로 현재 사용자만 읽게 한다.
- 내용: 요청 원문, 영역, 완료 조건, 구현할 사람(`implementer`), 1차 컨펌 상태(`plan_confirmation`),
  사용자 답변, 서브 에이전트별 반환값(반환 규약 그대로), 이슈 URL, PR URL.
  구조는 `references/return-contract.md`에 있다. 문서 본문, 토큰, 비밀번호, 개인정보는 넣지 않는다.
- 서브 에이전트를 부를 때는 상태 파일 경로와 메시지 문장, 필요한 사용자 답변만 넘긴다. 서브 에이전트가 돌아오면
  반환값을 상태 파일에 덧붙인다.
- 흐름이 끝나 보고까지 마치면 삭제한다. `needs_user_input`이나 `blocked`로 멈췄으면 재개를 위해
  남긴다. 이슈 서브 에이전트가 쓰는 Issue 계약 snapshot은 기존 규칙대로 판정 직후 삭제한다.

| QA 시트 | `subagents/qa-sheet.md` | `knot-feature-qa-sheet` | 기능 요구사항이 바뀌면 반드시 |
| 이슈 | `subagents/issue.md` | `knot-feature-issue` | 문서 갱신이 끝났을 때 |

서브 에이전트가 아닌 것은 다음과 같다.

- 기획서: 따로 서브 에이전트를 두지 않는다. 기능 요구사항 서브 에이전트가 읽고, 기능에 필요하면
  함께 고친다. 규칙은 `references/sources.md`의 「기획서 고치기」에 있다.
- FE 구현 하네스, BE 구현 하네스: 입구(메인 세션)가 직접 수행하는 절차다. 기존 프론트 하네스가
  Agent 도구와 대화형 스킬을 쓰는데 서브 에이전트 안에서는 그것을 쓸 수 없기 때문이다. 절차는
  `references/fe-implementation.md`, `references/be-implementation.md`에 있다.
- QA (E2E): FE 구현 절차 안에서 그대로 수행하는 절차다. 사람도 입구도 따로 부르지 않는다. 절차는
  `references/qa-e2e.md`에 있다.

### 서브 에이전트를 부르는 방법

- Claude Code: `.claude/agents/knot-feature-*.md`를 Agent 도구로 한 번에 하나씩 실행한다. 프롬프트에는
  상태 파일 경로, 메시지 문장, 사용자 답변(있으면)만 넣는다.
- Codex: 서브 에이전트를 띄울 수단이 있으면 같은 `subagents/*.md`로 띄운다. 없으면 입구 세션이 해당
  정의 파일을 읽고 그 서브 에이전트로서 한 단계만 수행한 뒤 같은 반환 규약으로 상태 파일에 기록한다.
  이때도 서브 에이전트 규칙(다른 서브 에이전트를 부르지 않기, 사용자에게 묻지 않기, 쓰기 권한 안에서만)은 그대로다.
- 모든 서브 에이전트는 `references/return-contract.md`의 JSON 하나를 돌려준다. 입구는
  `python3 harness/feature_pipeline.py result <file>`로 검증한 뒤 이 값만 보고 다음 행동을 정하고,
  이슈와 PR의 「노션 변경 사항」은 같은 스크립트의 `render`로 만든다. 노션 MCP나 Figma MCP가 없는 세션에서는 해당 서브 에이전트가 `blocked`로 돌아온다.

### 반환값 처리

| `status` | 입구가 하는 일 |
| --- | --- |
| `done` | `changed`를 상태 파일에 모으고 `next`의 서브 에이전트를 적힌 메시지로 순서대로 부른다. `next`가 비어 있으면 그 갈래는 끝이다. |
| `needs_user_input` | `question`과 `side_effects`를 그대로 사용자에게 보여 주고 답을 받는다. 답을 상태 파일에 적고 같은 서브 에이전트를 같은 메시지로 다시 부른다. 기능 제안은 예외로, 1차 컨펌 결과를 받은 뒤 「기존과 대조해 업데이트해라」로 다시 부른다(4절). |
| `blocked` | 권한, 접근 실패, 정본 부재처럼 사람이 환경을 손봐야 하는 경우다. 추측으로 우회하지 않고 원인과 손볼 것을 보고하고 멈춘다. |

## 3. 메시지: 언제 누구를 부르나

아래 문장을 그대로 쓴다. 화살표는 직접 호출이 아니라 입구가 중계하는 결과 전달이다.

| 보내는 쪽 | 받는 쪽 | 메시지 | 조건 |
| --- | --- | --- | --- |
| 사용자 | 입구 스킬 | 「○○ 기능 구현해 줘」 | 항상 |
| 입구 스킬 | 기능 요구사항 | 요청 전달, 「기존과 대조해 제안해라」 | 항상 먼저 들른다. 정본을 고치지 않고 바로 구현으로 가지 않는다. |
| 기능 요구사항 | 입구 스킬 | 제안 페이지 URL (`needs_user_input`) | 기능 추가, 수정, 삭제일 때. 「기능 요구사항 검토」 DB에 제안 페이지를 만들고, 1차 컨펌을 받을 때까지 흐름을 멈춘다. |
| 기능 요구사항 | 기능 요구사항 | 「기존과 대조해 업데이트해라」 (`next`) | 확정된 기획 안에서 끝나는 요청이라 1차 컨펌이 필요 없을 때 |
| 입구 스킬 | 기능 요구사항 | 제안 페이지 URL 전달, 「기존과 대조해 업데이트해라」 | 제안 페이지 `상태`가 확정일 때 |
| 기능 요구사항 | 입구 스킬 | 충돌 보고와 사이드 이펙트 브리핑 | 기존 요구사항과 충돌할 때. 작업을 멈추고 답을 기다린다. |
| 기능 요구사항 | 도메인 규칙 | 바뀐 기능 요구사항 전달, 「업데이트해라」 | 백엔드 길이고 도메인 규칙이 바뀌어야 할 때만 |
| 도메인 규칙 | API 명세 | 변경 사항 전달, 「업데이트해라」 | 도메인 규칙이 바뀌었을 때 |
| 기능 요구사항 | 디자인 | 「업데이트해라」 | 프론트 길이고 화면 요구가 바뀌었는데 Figma 링크가 없을 때 |
| 기능 요구사항 | QA 시트 | 「시나리오 뽑아 업데이트해라」 | 기능 요구사항이 바뀌면 반드시 |
| 기능 요구사항 또는 API 명세 | 이슈 | 「이슈 생성해」 | 문서 갱신이 끝났을 때 |
| 이슈 | 입구 스킬 | 생성된 이슈 번호와 URL | 항상 |
| 입구 스킬 | FE 또는 BE 구현 하네스 | 이슈 URL 전달, 「구현해라」 | 완료 조건이 「개발까지」일 때만 |
| 구현 하네스 | 입구 스킬 | PR URL | 구현과 PR이 끝났을 때 |

## 4. 문서 단계와 이슈

1. 기능 요구사항 서브 에이전트에 요청을 전달하며 「기존과 대조해 제안해라」로 시작한다. 이 단계는
   정본을 고치지 않는다. 바로 구현으로 가지 않는다.
2. 제안 결과로 1차 컨펌이 필요한지 정한다.
   - 확정된 기획 안에서 끝나는 요청(`done`, `next`에 「기존과 대조해 업데이트해라」)이면
     `plan_confirmation`을 `{"required": false, "status": "not_needed"}`로 적고 그 메시지로 다시 부른다.
   - 기능 추가, 수정, 삭제(`needs_user_input`, `question`에 제안 페이지 URL)이면 `plan_confirmation`을
     `{"required": true, "status": "pending", "proposal_url": "<제안 페이지>"}`로 적고 흐름을 멈춘다.
     제안 페이지 링크와 세 줄 요약을 보여 주고, 요청자가 팀 채널에 올려 기획 컨펌 담당
     (`python3 harness/team_roles.py confirmers`)에게 1차 컨펌을 받으라고 안내한다. 제안에 새
     디자인이 필요하다고 적혀 있으면 요청자에게 Figma 편집이 되는지 묻고, 되면 「실험 · 반영 전
     시안」 페이지에 초안을 만들어 제안 페이지 「디자인」에 링크하게 하고, 안 되면 제안의 디자인
     요청을 그대로 두게 한다. 상태 파일은 재개를 위해 남긴다.
   - `pending`인 동안에는 노션 정본, Figma Design 페이지, 이슈, PR을 바꾸지 않는다.
     `feature_pipeline.py state`가 이를 검사한다.
   - 다시 시작하면 제안 페이지를 읽어 `상태`를 본다. 사람의 말이 아니라 이 칸이 1차 컨펌의 근거다.
     - 확정: `plan_confirmation`을 `confirmed`로 바꾸고 `confirmed_by`(`컨펌한 사람`)와 `evidence`
       (`컨펌 날짜`와 「컨펌 기록」에서 바뀐 점)를 적는다. 기능 요구사항을 「기존과 대조해
       업데이트해라」로 다시 부르며 제안 페이지 URL을 넘긴다. 컨펌에서 방향이 바뀌었으면 바뀐 쪽을
       따른다.
     - 반려: `rejected`로 적고 흐름을 끝낸다. 정본, 이슈, PR을 건드리지 않았으므로 되돌릴 것이 없다.
       반려 이유를 보고하고 상태 파일을 지운다.
     - 검토 요청, 보류: 아직 기다린다. 상태 파일을 그대로 두고 멈춘다.
3. 기능 요구사항이 충돌을 보고하면(`needs_user_input`) 사이드 이펙트 브리핑을 사용자에게 그대로
   보여 주고 답을 받아 다시 부른다. 답 없이 진행하지 않는다.
4. 각 서브 에이전트의 `next`를 따라 도메인 규칙과 API 명세(백엔드 길), 디자인(프론트 길, 링크 없을 때),
   QA 시트(바뀌면 항상)를 부른다. 위쪽 길(도메인 규칙, API 명세)은 백엔드만 가고, 규칙과 명세가
   이미 있으면 기능 요구사항에서 바로 이슈로 간다. 디자인은 이슈 생성에 영향을 주지 않으므로
   디자인 결과가 없어도 이슈는 만든다. 1차 컨펌에서 디자인을 기획 컨펌 담당에게 맡겼고 아직
   받지 못했으면 이슈 `메모`에 「디자인 대기」를 적는다.
5. 문서 갱신이 끝나면 이슈 서브 에이전트를 「이슈 생성해」로 부르며 상태 파일의 `changed` 목록을 넘긴다.
   이슈 서브 에이전트는 기존 `$knot-issue-planning` 하네스를 그대로 쓴다.
   - 인터뷰, Grill처럼 사용자에게 물을 것이 생기면 이슈 서브 에이전트가 `needs_user_input`으로
     돌아온다. 입구가 한 질문씩 묻고 답을 붙여 다시 부른다. 담당자는 묻지 않고 `implementer`를 쓴다.
   - 실제 GitHub 게시는 사용자가 현재 요청에서 명시적으로 허용했을 때만 한다. 허용이 없으면
     dry-run 본문을 보여 주고 게시 여부를 한 번 묻는다. `--publish` 권한은 이 답에서만 나온다.
6. 이슈 번호와 URL을 받는다. 완료 조건이 「이슈까지만」이면 여기서 끝내고 보고한다. 생성된 이슈를
   확인하도록 권하되 필수로 막지 않는다.

## 5. 구현 단계 (입구가 직접 수행)

- 완료 조건이 「개발까지」일 때만 시작한다. 프론트는 `references/fe-implementation.md`, 백엔드는
  `references/be-implementation.md`의 절차를 입구(메인 세션)가 직접 수행한다. 기준 문서의 FE, BE
  구현 하네스가 이 절차다. 「구현해라」와 이슈 URL이 시작 입력이다.
- 서브 에이전트로 띄우지 않는 이유: 기존 프론트 하네스는 `code-reviewer` 에이전트와 `review`
  스킬의 파일별 에이전트(Agent 도구), `create-pr-content`(대화형)를 쓰는데, 서브 에이전트 안에서는
  Agent 도구와 사용자 질문을 쓸 수 없다. 기존 FE, BE 하네스를 그대로 쓰라는 요구를 지키려면
  메인 세션이 해야 한다.
- 둘 다면 워크트리를 둘로 나눠 차례로 하고 PR도 둘이다. 한 사람이 프론트와 백엔드를 모두
  구현해도 PR은 `[FE]`, `[BE]`로 나눠 각각 올린다. 백엔드 선행 여부 같은 순서는 AI가 정한다.
- 기존 이슈 URL로 시작한 경우도 같다. 이슈 본문의 「노션 변경 사항」이 읽을 정본 위치다. 이슈
  `메모`에 「디자인 대기」가 있는데 Figma Design 페이지 링크가 아직 없으면 시작하지 않고 멈춘다.
- PR을 만들 때 `python3 harness/team_roles.py review --area <frontend|backend> --author <implementer>`로
  담당자, 이름 라벨, 리뷰어, 승인 조건을 받는다. 1차 컨펌을 받은 작업이거나 구현 중 기획을 바꿨으면
  `--plan-changed`, 디자인이 새로 생기거나 바뀌었으면 `--design-changed`를 붙인다. 담당자와 이름
  라벨은 이 결과를 따르고(이슈 라벨을 복사할 때 이름 라벨이 다르면 이 결과로 바꾼다), 작업 성격
  라벨(`Feature`, `BugFix` 등)은 이슈에서 가져오며, `reviewers`에 리뷰를 요청한다. 구현 중 기획을
  바꿨으면 무엇을 왜 바꿨는지 PR 본문에 적는다.
- 기존 스킬이 사람에게 확인받는 단계(`create-story`의 목록 확인, `create-pr-content`의 안내 문구
  받기와 PR 열기 확인, 프론트 `commit` 스킬과 백엔드 `knot-commit`, `knot-pr`의 승인)는 완료 조건
  「개발까지」가 대신한다. 각 스킬에 이 예외가 적혀 있다. 결과(스토리 목록, 안내 문구)는 PR 본문에
  적는다.
- 구현 뒤에는 QA가 온다. QA를 하는 수단은 E2E 테스트이고, PR을 올린 뒤 PR CI의 E2E 결과를
  확인한다. 실패하면 실패 루프 규칙대로 고치고, 통과한 뒤에야 끝난다. E2E 통과와 시나리오 설명이
  PR에 보이고 사람은 설명만 읽는다.
- 요구사항이나 명세 문제를 발견하면 문서 단계로 되돌리지 않고 멈춰 사용자에게 묻는다. 테스트 실패
  수정 3회를 넘기면 멈추고 원인과 시도 내역을 보고한다.
- 머지는 하지 않는다. 승인 조건을 채우면 PR을 연 사람이 직접 머지한다.
- 끝나면 같은 반환 규약 모양으로 상태 파일에 기록하고(`changed`에 PR) PR URL을 보고한다.

## 6. 끝내기와 보고

보고에는 다음만 담는다.

- 만든 이슈 번호와 URL, PR URL(FE, BE 각각).
- 「노션 변경 사항」: 상태 파일의 `changed` 목록을 링크로.
- 사람이 할 일: 1차 컨펌을 기다리며 멈췄으면 제안 페이지 링크와 컨펌할 사람, `team_roles.py review`가 정한 PR
  승인 조건(같은 영역 팀원, 필요하면 기획 컨펌 담당)과 「승인을 받으면 PR을 연 사람이 직접 머지」,
  멈춘 지점이 있으면 그 원인과 재개 조건.
- 기본값으로 처리한 미결 사항.

## 완료 기준

- 두 질문(「이슈까지만」이면 구현할 사람까지 세 질문) 외에는 요청으로 알 수 있는 것을 묻지 않았다.
- 기능 요구사항 서브 에이전트를 「제안해라」로 항상 먼저 불렀고, 충돌은 사용자 답 없이 진행하지 않았다.
- 기능 추가, 수정, 삭제는 제안 페이지 `상태`가 확정이고 1차 컨펌 기록(`confirmed_by`, `evidence`)이
  생긴 뒤에야 노션 정본과 이슈를 바꿨다. 반려된 제안은 정본을 건드리지 않고 끝냈다.
- 이슈와 PR의 담당자와 이름 라벨이 `implementer`이고, PR 리뷰어와 승인 조건은 `team_roles.py review`
  결과다.
- 모든 서브 에이전트 반환값이 규약 JSON이고 상태 파일에 있다.
- 이슈와 PR 맨 위에 「노션 변경 사항」 링크가 있다.
- 사용자가 허용한 이슈 게시와 PR 생성 외에 원격을 바꾸지 않았고 merge는 하지 않았다.
- 기획서를 고쳤다면 「노션 변경 사항」에 있고, 노션과 Figma 문서를 저장소로 옮기지 않았다.
- 상태 파일과 snapshot은 저장소 밖에 있고 커밋되지 않았다.

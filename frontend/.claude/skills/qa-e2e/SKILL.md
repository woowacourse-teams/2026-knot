# QA 행을 E2E로 잇기

QA 체크리스트 한 장을 기준으로 두고, 그중 매번 같은 결과가 나오는 화면 동작을 E2E로 옮긴다. 옮긴 행은 PR마다 자동으로 지켜지고, 배포 전 QA는 실제 서버가 필요한 행에 집중한다.

개발자가 따로 부르는 도구가 아니다. PR 본문을 만드는 `create-pr-content` 스킬이 관련 QA를 채운 뒤 `pnpm qa:link`를 돌리고, 실패하면 이 절차를 따른다. PR 관문(`.github/workflows/frontend-e2e.yml`)도 같은 검사를 돌려 어긋나면 이 스킬로 고치라고 알린다.

QA 시트의 정본은 노션 하나다. 우선순위와 판정은 노션에만 있고, 저장소에는 사본을 두지 않는다. 관문은 노션을 읽지 않고 PR 본문의 ID와 E2E 이름의 ID만 맞춰 본다. 그래서 ID가 노션에 실제로 있는지는 에이전트가 노션에서 직접 확인한다.

E2E는 msw mock으로 돈다. 실제 서버, AI 답변 내용, 녹음 소리는 확인하지 못한다. 그건 에이전트 QA와 사람 QA의 몫이다.

## 언제 쓰나

공용 `knot-qa` 스킬(`../.agents/skills/knot-qa/SKILL.md`) 준비 단계에서 불리는 하위 절차다. 준비 단계가 QA 계획에서 확인 방법이 E2E로 나온 FE 화면 동작 행을 넘기면, 이 절차로 E2E를 먼저 쓰고 구현 전에 실패하는지 확인한 뒤 구현한다. 이때는 QA 계획의 확인 방법을 그대로 쓰고 아래 「확인 방법 나누기」를 다시 하지 않는다. 구현 전에 실패를 확인했어도 통과 기준의 「일부러 망가뜨리기」는 구현 뒤에 따로 한다.

그 밖에 이럴 때도 쓴다.

- `create-pr-content` 스킬의 관련 QA 단계에서 `pnpm qa:link`가 실패했을 때
- PR 관문의 qa-link 검사가 실패했을 때. 메시지 종류별 할 일은 아래 「qa-link 실패 고치기」
- 핵심 여정 E2E(`@core`)를 더하거나 고칠 때

## 관련 QA 절

PR 본문의 선택 절이다. QA 시트 행을 고치거나 구현한 PR이면 채운다. 행 ID를 한 줄에 하나씩, 여러 ID는 쉼표로 적는다.

```md
## 관련 QA

- STT-R25
- CONF-R2, CONF-R3
- STT-R28 (E2E 제외: 실제 서버 응답 필요)
```

- 「E2E 제외」가 아닌 ID는 그 ID를 이름 앞 대괄호에 붙인 E2E가 있어야 한다.
- 「E2E 제외」에는 이유가 있어야 한다.
- 주석(`<!-- -->`) 안의 줄은 읽지 않는다. 템플릿 예시만 남아 있으면 관련 QA가 없는 것으로 본다.
- 관련 QA가 없으면 PR 관문은 핵심 여정(`@core`)만 돌린다. 있으면 `@core`에 관련 QA의 E2E를 더해 돌린다.

## 입력

- QA 행 ID. 노션 [QA 체크리스트](https://app.notion.com/p/40291cc013ea43a0854771144e94d014)의 행 제목 앞 대괄호 안의 값이다. 예: `STT-R25`, `ONB-QA-004`, `CONF-R2, CONF-R3`
- 노션 QA 체크리스트에서 그 ID의 행을 직접 찾는다. 행이 없으면 오타인지 이슈 작성자에게 확인한다. 관문은 ID가 노션에 있는지 보지 않으므로, 확인하지 않은 ID를 관련 QA에 적지 않는다.
- 노션 행을 읽어 확인할 항목, 연결된 요구사항, 기대 결과를 확인한다. 노션을 읽지 못하면 멈추고 알린다. 코드를 보고 기대 동작을 지어내지 않는다.

## 확인 방법 나누기

위에서부터 처음 맞는 것을 고른다.

| 순서 | 행이 이런 것을 봐야 하면 | 확인 방법 |
| --- | --- | --- |
| 1 | 실기기, 권한 팝업, 소리, 사람의 판단 | 사람 |
| 2 | 실제 서버 응답, AI 답변 내용, 외부 연동(GitHub OAuth 등) | 에이전트 QA |
| 3 | 나머지. mock으로 매번 같은 결과가 나오는 화면 동작 | E2E |

- E2E로 나온 행만 E2E를 쓴다.
- 사람이나 에이전트 QA로 나온 행은 관련 QA에 `- ID (E2E 제외: 이유)`로 적는다. 이유는 위 표의 말로 짧게 쓴다(예: `실제 서버 응답 필요`, `실기기 필요`). 이유 없는 제외는 qa-link가 실패시킨다.
- 한 행에 E2E로 볼 부분과 서버로 볼 부분이 섞여 있으면, 화면 동작만 E2E로 쓰고 나머지는 에이전트 QA 몫이라고 PR 본문 `작업 내용`에 적는다. 예: 워크스페이스 생성은 화면 이동만 E2E, OWNER 권한 부여는 에이전트 QA. 이때 관련 QA에는 제외 없이 ID만 적는다.

## 쓰는 규칙

먼저 `.claude/rules/test-strategy.md`를 읽는다(「QA 시트와 E2E 잇기」 포함). 그다음 같은 폴더의 기존 E2E(`src/__test__/*.test.ts`)를 열어 헬퍼와 주석 밀도를 맞춘다.

- **위치**: `src/__test__/<페이지이름>.test.ts`. 페이지 이름은 `pages/` 컴포넌트 이름에서 가져온다(`ChatPage` → `chatPage.test.ts`). 여정이 여러 화면을 지나면 여정의 중심 화면 파일에 둔다.
- **이름**: 테스트 이름 앞에 `[QA ID]`를 붙이고, 뒤는 사용자 행동 문장으로 쓴다. 여러 ID는 쉼표로 나눈다(`[CONF-R2, CONF-R3]`). 맞는 행이 없으면 ID 없이 쓴다.
- **태그**: 핵심 여정이면 `@core`를 단다. 우선순위 태그는 달지 않는다. 우선순위는 노션에만 둔다.

```ts
test(
  "[STT-R25] 독의 마이크로 녹음을 시작하고 끝내기를 확정하면 문서 정리 화면으로 간다",
  { tag: ["@core"] },
  async ({ page }) => {
    // ...
  },
);
```

- **기대값**: 문자열로 박지 않고 `shared/api/mock/responses`의 mock 응답을 응답 DTO로 바꾼 값에서 가져온다. 버튼 이름 같은 화면 문구는 그대로 써도 된다.
- **실패 상태**: `page.route`로 만들되 MSW와 겹치지 않게 한다. mock 워커가 먼저 받는 요청은 `page.route`가 잡지 못하므로, 그 요청만 닿지 않는 주소로 보내는 방법을 쓴다(`dockLayout.test.ts`의 `openHomeWithoutRecording`).
- **모션**: 시간을 기다리지 않고 진행도를 고정한다(`dockLayout.test.ts`의 `measureExpand`).
- **로그인 상태**: 기본은 `playwright.config.ts`의 회원 쿠키다. 온보딩이나 비로그인은 `test.use({ storageState })`로 바꾼다.
- **마이크**: 설정의 가짜 장치로 권한 창 없이 녹음된다. 권한 창 자체는 사람 QA 몫이다.
- **정상 경로 먼저**: 핵심 여정은 정상 경로를 적게 쓴다. 실패와 경계 상황은 그 행이 따로 있을 때 쓴다.
- **mock**: 여정에 꼭 필요한 만큼만 `src/shared/api/mock`에 더한다. 기본 응답(`responses`)은 다른 테스트의 기대값이라 바꾸지 않는다.

## 통과 기준

넷 다 통과해야 끝난다.

1. **단독 1회**: `pnpm exec playwright test src/__test__/<파일> -g "<QA ID>"`
2. **반복 10회**: `pnpm exec playwright test src/__test__/<파일> -g "<QA ID>" --repeat-each=10`가 모두 통과한다. 한 번이라도 실패하면 고정할 상태를 다시 찾는다. 시간 대기(`waitForTimeout`)로 덮지 않는다.
3. **일부러 망가뜨리기**: 그 테스트가 지키는 동작을 서비스 코드나 mock 응답에서 잠깐 바꿔 테스트가 실패하는지 본다. 실패를 확인하면 바로 되돌리고 `git diff`로 되돌린 것을 확인한다. 실패하지 않으면 테스트가 아무것도 지키지 않는 것이니 고친다.
4. **qa-link**: PR 본문 초안을 파일로 두고 `frontend`에서 `PR_BODY="$(cat <본문 파일>)" pnpm qa:link`가 통과한다. 출력 표와 고칠 것은 PR 관문과 같다.

3000번 포트에 다른 dev 서버가 떠 있으면 끄거나 재사용하지 않는다. 커밋하지 않을 임시 설정에서 `webServer` 포트만 바꿔 돌리고 끝나면 지운다. qa-link가 E2E 목록을 읽을 때 그 설정을 쓰려면 `PLAYWRIGHT_CONFIG=<임시 설정>`을 함께 준다.

## qa-link 실패 고치기

로컬 `pnpm qa:link` 출력의 「고칠 것」이나, PR 관문 댓글의 「고칠 것」에 메시지가 나온다.

| 메시지 | 할 일 |
| --- | --- |
| 관련 QA `ID`: 이 ID를 붙인 E2E가 없어요 | 확인 방법을 나눈다. E2E면 이 절차로 쓴다. 아니면 관련 QA를 `- ID (E2E 제외: 이유)`로 고친다 |
| 줄에 E2E 제외 이유가 없어요 | 확인 방법 표의 말로 이유를 적는다 |
| 줄에서 QA ID를 읽지 못했어요 | 관련 QA 줄을 위 형식으로 고친다 |

PR 본문을 고치면 관문이 다시 돈다.

## 개발자가 결과 보는 법

관문은 결과를 세 곳에 남긴다. 개발자가 에이전트를 거치지 않고 직접 확인할 수 있다.

- **PR 댓글**: 관문이 PR에 댓글 하나를 달고, 다시 돌면 같은 댓글을 고친다. 관련 QA ID별 E2E 결과(통과, 실패, 재시도 후 통과, E2E 제외 이유), 핵심 여정(`@core`) 테스트별 결과, 고칠 것, 직접 보는 법이 들어 있다. job summary에도 같은 내용이 나온다.
- **보고서 artifact**: 댓글의 artifact 링크에서 「playwright-report」를 내려받아 압축을 풀고 `npx playwright show-report <푼 폴더>`로 연다. 통과해도 7일 동안 남는다. CI에서 실패한 테스트는 스크린샷과 영상이, 재시도한 테스트는 트레이스가 함께 들어 있다.
- **로컬**: `frontend`에서 `pnpm test:e2e:ui`로 화면을 보며 돌리고, `pnpm test:e2e -g "STT-R25"`로 그 ID의 E2E만 돌린다. 로컬 보고서는 `pnpm test:e2e:report`로 연다.

## 결과

- PR 본문 「## 관련 QA」에 다룬 ID를 모두 적는다. E2E로 쓴 ID는 그대로, 쓰지 않은 ID는 「E2E 제외」와 이유를 함께 적는다.
- 관문 댓글의 관련 QA 표(관련 QA ID, E2E 테스트, 결과)는 공용 `knot-qa` 실행 단계가 QA 체크리스트의 「자동 확인」, 「E2E 테스트」, 「자동 확인 일시」 칸에 적을 근거다. 「판정」에는 적지 않는다. 「판정」은 실제 서버에서 확인한 결과만 받는다.
- 한 QA ID에 행이 여러 개면 `knot-qa` 준비 단계의 QA 계획에서 고른 행에만 적고 나머지는 비운다. 이 스킬은 노션에 쓰지 않고, 기록은 `knot-qa`의 `references/qa-sheet-record.md`를 따른다.

## 실행

| 명령 | 범위 | 언제 |
| --- | --- | --- |
| PR 관문 | `@core`와 관련 QA의 E2E | PR을 열거나, 푸시하거나, 본문을 고칠 때 자동으로 |
| `pnpm test:e2e:core` | `@core` 핵심 여정 | 로컬에서 관문과 같은 핵심 여정만 |
| `pnpm test:e2e` | 전체 E2E | 화면 공통 코드를 크게 바꿨을 때 |
| `pnpm qa:link` | qa-link 검사만 | PR 본문 관련 QA를 고친 뒤 |

## 하지 않을 것

- 서비스 코드를 고쳐 테스트를 통과시키지 않는다. 테스트가 실패하면 구현이 기존 동작을 깨뜨렸는지, 요구사항이 바뀌었는지 먼저 보고한다.
- 실제 API로 확인하지 않는다. 실제 서버 확인은 에이전트 QA 몫이다.
- 기존 테스트의 기대값을 지금 화면에 맞춰 바꾸지 않는다. 바꿔야 하면 이유를 먼저 보고한다.
- qa-link를 통과시키려고 근거 없이 「E2E 제외」를 적지 않는다. 제외는 확인 방법 표에서 사람이나 에이전트 QA로 나온 행만이다.
- 노션 QA 체크리스트의 행, 우선순위, 판정을 저장소에 옮겨 적지 않는다. 노션은 읽기만 한다.

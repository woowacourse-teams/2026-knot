# Knot 코드 분석: 이력서에 쓸 만한 문제와 현재 성과의 한계

분석일: 2026-10-23 · 대상: 로컬 작업 트리 전체 · 관점: 백엔드 개발자 이력서

## 1. 판단부터

**새로운 기술을 추가하기보다, 이미 드러난 장애와 성능 문제 하나를 끝까지 해결하는 편이 이력서 가치가 높다.** 이 프로젝트에는 비동기 작업, 외부 AI 서버, 데이터 정합성, 커서 조회, 스트리밍, 배포와 관측 코드가 이미 있다. “기능을 구현했다”를 넘길 재료는 충분하다. 부족한 부분은 실제 문제, 원인 검증, 대안 선택, 개선 후 결과를 하나의 증거로 연결하는 일이다.

추천 순서는 다음과 같다. 순위는 장애 심각도만이 아니라, 현재 증거의 강도와 백엔드 역량을 설명하기 좋은 정도를 함께 반영한다.

| 순위 | 문제 | 현재 근거 | 이력서 가치와 남은 일 |
| --- | --- | --- | --- |
| 1 | 문서 조회의 DB 연결 대기와 실행 계획 편차 | Dev 부하 기록, 요청별 JDBC 기록, 로컬 SQL 전후 비교 | 가장 빨리 완성할 수 있는 성능 개선 사례. SQL 개선이 API 지연과 처리 안정성으로 이어지는지 확인해야 한다. |
| 2 | 공유 LLM의 동시 실행 실패와 잘못된 실패 분류 | 실패 작업 24개 복구 기록, 동일 입력의 병렬 실패·단독 성공, 현재 오류 매핑 코드 | 실제 장애 해결과 자원 제어를 설명하기 좋다. 순차 복구를 넘어 재발 방지와 혼합 부하 검증이 필요하다. |
| 3 | 검색 응답 시간·검색 품질·입력 예산의 충돌 | 실제 모델 지연 실험, 반복 도구 호출 실패 기록, 현재 FAST_PATH 코드 | 차별화 가능성이 크다. 빠른 경로의 품질을 독립 평가하고 긴 문서·후속 질문 실패를 줄여야 한다. |
| 4 | STT 단일 슬롯의 재시작·다중 인스턴스 복구 | 시작 시 전역 PROCESSING 실패 처리, 메모리 작업 슬롯, 배포 스크립트 | 동시성·복구 설계 소재로 좋다. 현재는 코드에서 도출한 위험이며 실제 장애 재현이 먼저다. |
| 5 | 녹음 업로드 실패 후 클라이언트 원본 폐기 | 업로드 성공 여부와 무관한 정리 코드, 실패 후 홈 이동을 기대하는 테스트 | 사용자 피해가 가장 직접적이다. 백엔드 지원자라면 업로드 완료·재시도 계약까지 연결해야 한다. |
| 6 | SSE 연결마다 반복되는 DB 스냅샷 조회 | 기본 100ms 폴링, 연결별 조회, 기본 스트림 동시성 8 | 측정하기 좋은 확장성 후보. 현재 병목이라고 입증된 상태는 아니다. |

**지금 바로 사용할 수 있는 성과로는 CodeBuild 캐시 검증이 가장 정리되어 있다.** 동일 소스와 실제 테스트 실행을 유지한 반복 비교에서 작업군별 전체 빌드 시간 중앙값이 25.5%, 32.4% 줄었다. 문서 SQL 최적화도 로컬·특정 실행 계획이라는 범위를 명시하면 사용할 수 있다. 반면 “400 RPS 안정 처리”, “검색 정확도 99.75%”, “무중단 배포 완성”은 현재 확인한 증거로 쓰면 과장이다.

## 2. 분석 범위와 증거를 읽는 방법

기준 브랜치는 `be/refactor/#715`, HEAD는 `cb08773abffd4dc11f06d8232550d82e9fd2a538`이다. 작업 트리에 문서 조회, 검색, JDBC 계측, 배포·관측 설정 등 기존 미커밋 변경이 많다. 이 보고서는 해당 변경을 포함한 현재 로컬 코드를 평가한다. 원격 최신 브랜치나 현재 배포된 프로그램과 같다는 뜻은 아니다.

실제 이력서와 개인별 기여 내역은 제공되지 않았다. 따라서 아래 성과는 **프로젝트에 존재하는 근거**이며, 본인이 맡은 설계·구현·검증 범위를 확인한 뒤 개인 성과로 써야 한다.

저장소 구조와 파일 목록을 조사하고 주요 사용자 흐름의 구현, 관련 테스트, 마이그레이션, 운영·실험 문서를 대조했다. 모든 파일을 한 줄씩 정독한 전수 감사나 보안 감사는 아니다. `node_modules`, 빌드 산출물, Notion 전체 캐시를 제품 구현 문맥으로 읽지 않았다.

| 조사 범위 | 파일 규모 | 깊이와 확인 대상 |
| --- | --- | --- |
| 백엔드 production Java | 553개 | document, recording, search 중심으로 서비스·상태 전이·저장소·외부 어댑터를 추적. auth, workspace, global은 주요 보호 장치와 경계를 확인 |
| 백엔드 test Java | 347개 | 후보 문제와 연결되는 테스트 및 기존 실험의 검증 범위 확인. 전체 테스트 정독·재실행은 아님 |
| AI 서버 Java | main 22개, test 11개 | 단일 작업 슬롯, 재시도 식별자, 결과 보관, 종료 동작 확인 |
| AI runner | TypeScript·Python | 실행 구조와 입력·결과 처리 경계 조사. 실모델 정확도와 GPU 상태는 이번에 측정하지 않음 |
| 프론트엔드 | TS/TSX 656개 | 테스트·스토리·목 포함. 녹음→업로드→종료, 인증 갱신, 검색 스트림 등 백엔드 계약에 영향을 주는 흐름 집중 확인 |
| DB·운영 | SQL 마이그레이션 46개 및 CI·배포·관측 자료 | 인덱스·제약, 작업 복구, 캐시 실험, 부하·장애 기록 대조. 실제 클라우드 설정 재조회는 하지 않음 |

제품 해석에는 [현재 V2 MVP 기준](../product/current-v2-mvp.md)과 [백엔드 Notion 근거 안내](../notion-context.md)를 적용했다. 과거 V1 코드·스키마의 존재를 V2에서 실제 사용하는 기능으로 해석하지 않았다.

이 보고서의 증거는 세 종류다.

- **이번에 확인한 코드·테스트:** 현재 파일에서 직접 확인한 동작과 이번에 실행한 로컬 테스트 결과.
- **기존 실험·운영 기록:** 저장소에 남아 있는 과거 측정 결과. 이번 세션에서 AWS·운영 DB·모델 서버를 다시 관측한 것은 아니다.
- **검증할 가설:** 코드로 설명 가능한 실패 조건이나 성능 비용. 발생 빈도·실제 피해·개선율을 아직 측정하지 않았다.

## 4. 우선순위 1 — 문서 조회: SQL 개선을 API 성능 개선으로 완결하기

### 확인된 문제

[Dev 부하·GC 진단 기록](../operations/dev-gc-allocation-diagnosis.md)은 목표 400 RPS·15분 시험이 약 256.5초에 통신 오류로 조기 종료됐다고 기록한다. 실제 도달률은 약 385.21 RPS였고, dropped iteration은 1,069건, 응답 상태를 받지 못한 요청은 목록 155건·상세 74건이었다. HTTP 5xx가 0이라는 사실을 전체 성공으로 읽으면 안 된다.

목록 p95는 853.88ms, 상세 p95는 837.68ms였다. Hikari active는 10, pending 최대값은 178이었다. 개별 느린 목록 요청에서는 서버 처리 910.56ms 중 연결 획득이 866.49ms, 연결 사용이 42.86ms, SQL 실행 합계가 26.06ms로 관측됐다. 평균적 관계로 일반화할 수는 없지만, 적어도 그 요청의 대부분은 쿼리 실행 자체보다 연결 대기였다.

GC 총시간 비율은 약 1.657%였고 Full GC는 없었다. 따라서 “GC 튜닝으로 해결할 문제”라고 먼저 정하는 것도 근거가 부족하다. 연결 점유 시간, 쿼리 비용, 트랜잭션 범위, 동시 요청량을 나눠 봐야 한다. 커넥션 풀 크기를 늘리는 것만으로 해결된다고 단정할 수 없다.

### 현재까지 된 일과 한계

[DocumentListService](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/document/application/DocumentListService.java:19)는 `REPEATABLE_READ` 안에서 멤버십·주제 집계·페이지 조회를 수행한다. [DocumentListJpaRepository](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/document/infrastructure/persistence/DocumentListJpaRepository.java:80)에는 이미 PENDING 전용 후보 제한 쿼리가 로컬 변경으로 들어 있다. 페이지 후보를 `size + 1`개로 먼저 제한하고 녹음 정보를 결합한다.

[로컬 페이지 비교 기록](/Users/yongtae/Desktop/knot/backend/output/document-pending-page/report.md)은 PostgreSQL 18의 합성 데이터에서 14개 조건의 전체 반환 값·순서 동등성을 확인했다. 문서 10,000개·미확인 8,000개인 첫 페이지의 강제 generic plan 중앙값은 **24.609ms → 1.182ms, 약 95.2% 감소**였다. 녹음 조인 전 후보를 101개로 제한하는 실행 계획 변화가 있다.

다만 같은 조건의 custom plan은 0.916ms → 0.876ms로 차이가 작고, 결과가 없는 조건 일부는 느려졌다. 실험은 7회 중 초기 2회를 제외한 5회 중앙값이며, 강제 실행 계획·로컬 합성 데이터 결과다. 이것을 “전체 API가 95% 빨라졌다”로 쓰면 안 된다.

[주제 집계 비교 기록](/Users/yongtae/Desktop/knot/backend/output/document-pending-topics/report.md)의 12개 조건도 동등성은 확인됐다. 하지만 많은 미확인 문서 조건의 generic plan은 10.800ms → 10.292ms에 그쳤고, 확인 대상 반복 조회 비용도 남았다. 페이지 쿼리 개선율을 주제 집계까지 확장할 수 없다.

### 끝내야 할 작업

1. 현재 로컬 변경을 기준으로 기존·개선 버전의 동일 데이터·동일 요청 분포 비교를 만든다. 크기, 커서 위치, 미확인 비율, 녹음 필터, 없는 결과를 포함한다.
2. SQL 시간뿐 아니라 요청 p50/p95/p99, 연결 획득·점유 시간, 처리율, 타임아웃, dropped iteration을 같이 수집한다. 계측 비용도 확인한다.
3. 목표 부하를 충분한 시간 유지해 완료한다. 실패·조기 종료도 표본으로 남긴다. 필요하면 DB CPU·I/O와 애플리케이션 CPU를 함께 대조한다.
4. 스냅샷 일관성, 커서 누락·중복, 다른 회원·Workspace 경계가 유지되는지 검증한다. 성능 때문에 격리 수준을 변경한다면 현재 일관성 계약부터 확인한다.

**이력서 가치:** 실행 계획을 읽고, 읽는 행 수를 줄이고, 풀 대기와 요청 지연을 분리해 설명할 수 있다. 일반 백엔드 면접에서 가장 전달하기 쉽고 현재 완료까지의 거리가 짧다.

현재 근거로 가능한 문장:

> 미확인 문서 목록의 조인 전 후보 제한을 적용하고 14개 조회 조건의 결과 동등성을 검증했다. 로컬 1만 문서 데이터의 generic plan 첫 페이지 실행 시간 중앙값을 24.609ms에서 1.182ms로 줄였다.

API 부하 재검증 전에는 처리량 향상·타임아웃 해소·운영 지연 개선을 덧붙이지 않는다.

## 5. 우선순위 2 — LLM 동시 실행: 복구 경험을 재발 방지로 연결하기

### 확인된 문제

### 구조적으로 중요한 이유

문서와 검색에는 각각 독립된 작업 풀이 있다. [문서 작업 풀](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/global/config/DocumentGenerationWorkerConfig.java)과 [검색 작업 풀](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/global/config/SearchWorkerConfig.java)의 기본 생성 동시성은 각각 2다. 동일 모델 서버를 쓰면 두 기능의 동시 사용과 애플리케이션 인스턴스 증가가 공유 자원에 합쳐진다. 작업 수와 실제 순간 모델 요청 수가 항상 같다는 뜻은 아니다.

현재 영속 Job·lease·시도 검증·결과 원자성은 이미 있다. 외부 모델 호출 중 DB 트랜잭션을 계속 유지하지 않도록 분리한 코드도 있다. 필요한 일은 단순한 “비동기 전환”이나 “Job 테이블 도입”이 아니다. **모델이 감당할 수 있는 작업량과 입력 크기, 기능별 우선순위, 재시도 조건을 함께 제어하는 일**이다.

**이력서 가치:** 실제 운영 실패를 입력 문제로 오인한 지점부터 찾아, 외부 시스템의 자원 한계와 백엔드의 복구 정책을 연결할 수 있다. 구현량은 문서 쿼리보다 크지만 장애 분석 역량은 더 잘 드러난다.

## 6. 우선순위 3 — 검색: 빠른 응답과 정답 근거를 함께 보장하기

### 속도 개선의 근거는 있지만 품질 보장은 아직 없다

[검색 지연 실험](../qa/697-latency/README.md)은 실제 Qwen과 로컬 Spring SSE를 사용했다. 고정 질문 2개, 변형별 워밍업 3회·측정 3회에서 탐색 에이전트 대신 직접 검색한 경우 첫 delta 중앙값이 단일 문서 질문 8.171초 → 2.695초, 교차 문서 질문 19.604초 → 2.597초였다. 순차 모델 호출이 줄어드는 방향은 유효한 근거가 있다.

그러나 고정 fixture 2개와 소표본이다. 해당 실험의 직접 경로 후보 수는 3개였고, 현재 [FAST_PATH](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/infrastructure/llm/SearchFastPathDocumentRetriever.java:16)는 최대 20개를 조회한다. 실험 수치를 현재 구현 전체나 실제 사용자 질문 분포의 개선율로 바로 옮길 수 없다.

### 현재 코드의 구체적 빈틈

- 기본 검색 모드는 FAST_PATH다. 현재 질문을 정규화해 검색하며, 검색 단계에서 대화 이력으로 생략된 대상을 복원하지 않는다. 의도 분류와 최종 답변에 이력이 전달되는 것과, 검색 후보가 올바르게 선택되는 것은 별개다. “그 결정의 이유는?” 같은 후속 질문은 검증 대상이다.
- [검색 SQL 어댑터](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/infrastructure/persistence/SearchDocumentQueryAdapter.java)는 제목·주제·요약·본문에 `ILIKE` 조건과 가중 점수를 적용한다. 이 구조만으로 현재 DB가 항상 순차 스캔한다고 단정할 수 없다. 실제 데이터의 실행 계획과 검색 재현율을 확인해야 한다.
- FAST_PATH는 후보 본문 전체를 전달한다. [컨텍스트 검사](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/infrastructure/llm/SearchAgentContext.java:16)는 직렬화된 메시지가 기본 48,000자를 넘으면 실패시킨다. 후보를 총예산에 맞춰 축소하는 단계는 이 경로에 없다. 예를 들어 본문 2,400자씩 20개면 본문만 48,000자이며 이력·메타데이터가 추가된다. 이는 입력 구성의 위험을 설명하는 계산이지 실제 실패 빈도 측정값은 아니다.
- [도구 반복 실패 조사](../implement-plan/search-tool-repeat-failure-investigation.md)는 과거 실패 15개 재실행에서 13개 생성 실패와 2개 완료를 기록했고, 정답 기준을 통과한 사례는 없었다. 반복 호출을 즉시 예외로 처리한 지점과 연결됐다. 현재 로컬 코드에는 반복을 안내로 바꾸는 변경이 있으므로 “아직 수정이 없다”는 진단은 틀리다. 실모델 재검증은 별도로 필요하다.

### 끝내야 할 작업

1. 단일 문서, 여러 문서, 후속 질문, 날짜 범위, 상충 근거, 근거 없음, 긴 문서, 반복 도구 호출을 포함한 사람이 검토한 평가셋을 만든다. 개발 중 본 질문과 최종 평가 질문을 분리한다.
2. 검색 단계의 Recall@k와 최종 답변의 근거 일치·출처 정확성·무근거 답변 비율을 분리한다. 첫 delta와 완료 시간을 함께 측정한다.
3. 현재 키워드 검색을 기준선으로 삼고, 후속 질문 정규화·후보 수·본문 발췌·토큰 예산을 먼저 비교한다. 일반 질문은 빠르게, 추가 탐색이 필요한 질문은 제한된 탐색을 사용하는 정책도 대안이다. 현재 코드에 자동 fallback이 있다고 간주하면 안 된다.

**이력서 가치:** “RAG/MCP를 사용했다”보다, 느린 모델 호출을 줄이면서 품질 저하를 어떻게 탐지·통제했는지가 강한 소재다. 다만 평가셋과 품질 기준을 만드는 비용이 크므로 단순 성능 작업으로 잡으면 범위가 늘어난다.

[의도 분류 모델 비교](../experiments/search-intent-model-benchmark-results.md)의 Qwen 399/400, 99.75%는 합성 평가셋의 **의도 분류 정확도**다. 전체 검색 정확도가 아니다. 비교 모델은 실행 환경·양자화·서빙 경로 차이도 있어 지연 차이를 모델 능력 하나로 설명하면 안 된다.

## 7. 우선순위 4 — STT: 단일 실행 보장과 안전한 복구를 동시에 만족시키기

### 코드에서 도출한 실패 조건

[RecordingTranscriptionService.initialize](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/recording/application/RecordingTranscriptionService.java:33)는 애플리케이션 시작 시 `recoverProcessing()`을 호출한다. [복구 서비스](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/recording/application/RecordingTranscriptionStateService.java:185)는 공유 DB의 PROCESSING 작업을 `SERVER_RESTARTED`로 실패시킨다. 실행 소유 인스턴스나 lease 만료를 기준으로 고르지 않는다.

따라서 같은 DB를 사용하는 인스턴스 A가 STT를 수행하는 동안 B가 시작하면, B의 초기화가 A의 진행 상태를 실패로 바꿀 수 있다. 이후 A의 결과는 현재 시도·상태 검사에서 반영되지 않을 수 있다. **이는 코드로 설명한 시나리오이며 실제 운영 발생을 확인한 사건은 아니다.** 배포 운영에서 실행을 완전히 분리하고 있다면 발생 조건도 달라진다.

[개발 blue-green 스크립트](/Users/yongtae/Desktop/knot/backend/scripts/dev_bluegreen_deploy.sh:372)는 후보 앱을 먼저 시작한 뒤 기존 앱의 연결을 drain하고 중지하는 순서를 갖는다. HTTP 연결이 비었다고 백그라운드 STT 작업까지 인계됐다는 뜻은 아니다. [배포 검증 문서](../implement-plan/blue-green-deployment-automation.md)도 실제 앱 blue-green 검증 완료와 단순 배포·health 성공을 구분한다.

또 하나는 DB 장애 후 슬롯 복구다. [완료·실패 확정 코드](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/recording/application/RecordingTranscriptionService.java:163)는 성공 저장과 실패 저장이 모두 실패하면 로컬 `transcriptionThread`를 유지한다. 다음 작업으로 넘어가 AI 결과를 덮어쓰지 않으려는 보호 의도가 있고 기존 테스트도 이를 기대한다. 하지만 DB가 회복됐을 때 이 상태를 재조정하는 경로가 없으면 후속 dispatch가 계속 막힐 수 있다. 단순히 참조를 비우는 수정도 안전하지 않다.

[AI 서버 TranscriptionJobService](/Users/yongtae/Desktop/knot/ai-server/src/main/java/com/knot/ai/transcription/application/TranscriptionJobService.java:15)는 현재 JobSnapshot과 worker를 메모리에 보관하며 새 작업이 이전 결과를 대체한다. runner의 임시 파일이 존재하는 것과, API가 재시작 후 결과를 복구할 수 있는 것은 다르다.

### 끝내야 할 작업

1. 동일 DB에 앱 두 개를 띄워 A 처리 중 B 시작을 재현한다. AI 성공 직후 DB 장애, 결과 저장 전 프로세스 종료, 종료 신호 중 재시도를 함께 다룬다.
2. 실행 소유권·lease와 오래된 실행의 결과 확정을 막는 시도 식별자를 설계한다. 외부 AI 서버가 동시에 하나만 처리한다는 제약은 유지해야 한다.
3. AI 결과를 백엔드가 확정하기 전까지 보존하는 인계 규칙과, DB 회복 뒤 재확정하는 절차를 정한다. 결과 보존과 다음 작업 허용을 따로 생각한다.
4. 중복 실행·중복 결과가 없고, 작업이 영구 정체되지 않으며, 배포 중 살아 있는 작업을 오인 실패시키지 않는지 검증한다.

**이력서 가치:** 단일 서버에서 다중 인스턴스·배포 상황으로 넘어갈 때의 소유권과 복구 문제를 설명할 수 있다. 단일 AI 장비가 제약이라면 무조건 병렬 처리량을 높이는 것이 정답은 아니다.

수동 STT 재시도 정책에는 [API 문서의 미해결 충돌](../api/recording-transcription-retry.md)이 있다. 구현 단계에서는 최신 제품 결정을 확인해야 하며, 이 보고서는 새 재시도 정책을 확정하지 않는다.

### 끝내야 할 작업

1. URL 발급 실패, PUT 중 연결 단절, PUT 성공·완료 응답 유실을 따로 재현한다. 특히 마지막 경우에는 서버 상태를 확인해 불필요한 전체 재업로드를 줄일 수 있다.
2. 최소 변경은 실패한 Blob을 보존하고 재시도·파일 다운로드를 제공하는 것이다. 탭 종료까지 견뎌야 한다면 IndexedDB 등의 지속 보관을 검토한다.
3. 저장 용량, 브라우저 종료, 권한 상실·로그아웃 후 삭제, 중복 완료 요청을 다룬다. 오디오 보존 기간과 사용자에게 보이는 복구 상태도 계약에 포함한다.
4. 장애 주입 조건별 원본 복구율, 중복 업로드 바이트, 완료까지의 시간, 브라우저 메모리 사용을 측정한다. multipart 도입은 파일 크기·재전송 비용 근거가 생긴 뒤 판단한다.

**이력서 가치:** 사용자 손실과 해결 효과가 명확하다. 다만 UI에 재시도 버튼 하나를 추가한 정도라면 백엔드 역량을 크게 보여주기는 어렵다. 업로드 완료의 멱등성, 원본 보존·삭제, 실패 구간별 복구까지 묶어야 강해진다.

제품 문서에서 미뤄둔 “새로고침 뒤 녹음 재개”와 “종료된 녹음의 업로드 실패 복구”는 범위가 다르다. 전자를 해결하는 큰 프로젝트로 자동 확대할 필요는 없다.

## 9. 우선순위 6 — SSE: 연결 수 증가에 따른 DB 읽기 비용 검증

### 확인된 구조와 아직 모르는 것

[SearchAnswerSseConnection](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/presentation/stream/SearchAnswerSseConnection.java:91)은 반복해서 스냅샷을 읽고 변경된 내용만 전송한다. [기본 설정](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/global/config/SearchWorkerProperties.java:20)은 스트림 폴링 100ms, 동시성 8이다.

[SearchAnswerSnapshotService](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/application/SearchAnswerSnapshotService.java:63)는 각 스냅샷에 실행·대화·권한·메시지·근거·최신 receipt를 조회한다. 메서드 호출 수를 무조건 같은 SQL 왕복 수로 바꿀 수는 없지만, 응답 내용이 바뀌지 않아도 여러 DB 읽기가 반복되는 구조다.

조회 처리 시간을 제외한 단순 상한 계산으로 연결당 초당 약 10회, 8개면 약 80회 스냅샷 조회가 가능하다. 이는 **실측 QPS가 아니다.** 현재 제한은 무제한 연결이 아니며, 초기에 관측된 검색 지연은 주로 모델 호출이었다. SSE를 현재 가장 큰 병목이라고 쓰면 안 된다.

또한 [SearchAnswerContentBuffer](/Users/yongtae/Desktop/knot/backend/src/main/java/com/knot/backend/search/application/SearchAnswerContentBuffer.java:9)는 1,024자 또는 50ms 기준의 버퍼를 이미 둔다. “매 토큰마다 DB에 쓰던 것을 처음 배치 처리했다”는 설명도 현재 코드와 맞지 않는다.

### 끝내야 할 작업

연결 1·8개와 동시성 설정을 늘린 조건에서 SQL 수, DB CPU, 풀 대기, 첫 delta, 재연결 복구 시간을 측정한다. 결과에 따라 폴링 간격 조절, 불변 데이터 조회 축소, 같은 답변 구독자 간 조회 공유, 이벤트 통지+영속 스냅샷 복구를 비교한다. 프로세스 간 통지가 실제로 필요할 때 Redis 등 별도 구성요소를 고려한다.

**이력서 가치:** 비용을 먼저 정량화하면 좋은 성능 사례가 된다. 측정 없이 “Redis Pub/Sub로 확장성 확보”를 목표로 잡으면 기술 도입을 정당화하는 프로젝트가 되기 쉽다.

## 11. 추천하는 작업 선택과 이력서 구성

**하나만 추가로 한다면 문서 조회 개선을 API 부하 검증까지 완결하는 것을 추천한다.** 이미 문제 기록·계측·쿼리 대안·결과 동등성 근거가 있어, 새 프로젝트를 벌이는 것보다 불확실성이 작다. 이때 SQL 개선 후에도 연결 대기가 줄지 않으면 그 결과를 인정하고 다음 원인을 좁혀야 한다.

장애 대응과 분산 시스템 역량을 더 강조하고 싶다면 LLM 동시 실행 제어를 선택한다. 검색 경험을 중심으로 지원한다면 검색 품질·지연 평가를 선택하되, 독립 평가셋 없이 모델이나 검색 기술을 바꾸는 일부터 시작하지 않는다.

추천 이력서 구성은 성능 1건, 신뢰성 1건, 개발 생산성 1건이다.

1. 문서 조회: 관측한 병목 → 실행 계획 대안 → 결과 일관성 → API 부하 전후 검증.
2. 문서 생성 또는 STT: 실패 구간 → 소유권·재시도·결과 인계 → 장애 주입 → 재발 방지.
3. CodeBuild: 동일 검증 유지 → 캐시·작업 분리 → 반복 측정 → 실패 산출물 보존.

세 항목을 다 하기 위한 계획은 아니다. 현재 본인 기여가 확인되는 성과를 먼저 쓰고, 한 항목의 증거를 보강하는 편이 낫다. 숫자가 아직 없는 미래 성과를 이력서 완성 문장처럼 작성하지 않는다.

각 사례는 면접에서 다음 질문에 답할 수 있어야 한다.

- 실제 사용자 문제였는가, Dev 시험 문제였는가, 코드에서 예측한 위험이었는가?
- 기존 코드가 이미 해결하던 것은 무엇이고, 정확히 어떤 경계를 바꿨는가?
- 다른 대안과 비교했는가? 선택하지 않은 이유는 비용·정합성·제약 중 무엇인가?
- 동일 조건 비교였는가? 표본 수, 실패 표본, 환경 차이를 설명할 수 있는가?
- 개선 뒤 남은 문제는 무엇이며 본인이 직접 맡은 부분은 어디까지인가?

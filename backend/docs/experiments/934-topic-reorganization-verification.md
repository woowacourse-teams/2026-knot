## 테스트 증거

### PR #938 인수 테스트 CI 실패와 시각 정밀도 보정

Backend CI [39905831871](https://github.com/woowacourse-teams/2026-knot/actions/runs/39905831871)의 `remaining` 작업에서 인수 테스트 1건이 실패했다. `DocumentTopicReorganizationAcceptanceTest.start_success_endToEnd`는 `SUCCEEDED`를 기대했지만 `QUEUED`를 반환했다. 같은 실행의 통합 테스트는 성공했다.

원인은 테스트의 나노초 정밀도 고정 `Clock`과 PostgreSQL `timestamptz`의 마이크로초 정밀도 차이다. DB가 `next_attempt_at`을 위로 반올림하면 테스트 시계는 그 시각보다 앞선 상태로 고정되어, 작업을 여러 번 호출해도 실행 가능 조건을 만족하지 않는다. 로컬에서 소수초를 `123456789`로 고정해 같은 `QUEUED` 실패를 재현했고, 별도 진단 assertion으로 저장 전 `2026-10-23T05:36:11.123456789Z`와 DB 왕복 후 `2026-10-23T05:36:11.123457Z`의 차이를 확인했다. 진단용 assertion은 제거했다.

인수 테스트의 고정 시각만 `ChronoUnit.MICROS`로 절삭했다. 기존 DB 통합 테스트와 같은 정밀도를 사용하며, API·실행 가능 시각 비교·재시도 정책·스케줄러는 변경하지 않았다. 테스트 제외, sleep, 무조건 재실행으로 실패를 숨기지 않았다. 보정 후 해당 클래스 5개와 `spotlessCheck`가 통과했다. 이어서 `./gradlew acceptanceTest spotlessCheck bootJar`가 2분 14초에 성공했고 인수 테스트 전체 596개에서 실패·오류·건너뜀은 0개였다.

순수 도메인·파서 테스트를 먼저 실패시킨 뒤 구현했다. PostgreSQL 검증은 Docker의 실제 pgvector/pgvector:pg18과 Flyway V63을 사용했다. 모의 모델 응답은 실제 모델 품질 증거와 분리한다.

최종 `./gradlew spotlessApply check bootJar` 성공: unit 2,055개(실모델 opt-in 2개 건너뜀), integration 917개(기존 환경 조건 4개 건너뜀), acceptance 596개. 전체 3,568개 중 실패·오류 0개, 건너뜀 6개. 새 재정리 DB 통합 테스트 19개 및 보안 인수 테스트 5개도 포함한다. 실행 시간은 7분 35초이며 배포·모델 성능 지표가 아닌 전체 검증 명령 소요 시간이다.

이후 환경 변수 매핑·테스트 선언 위치 보정 후 관련 unit 56개(실모델 opt-in 2개 건너뜀), integration 34개, acceptance 5개와 bootJar를 다시 통과했다. git diff --check도 통과했다. Persona profile/source 읽기 근거 39개 및 두 보고서는 기록했으나 workflow finish implement는 evidence-path-unsafe로 실패했다. 이 도구의 경로 검증 차단과 Gradle 제품 검증 결과는 구분한다.

## 실제 모델 관측

주소는 사용자가 제공한 HTTPS LM Studio 서버다. 인증 후 /v1/models에서 qwen3.8-27b 존재를 확인했다. 서버 양자화·GPU 사용률·다른 사용자의 부하는 이번에 관측하지 않았다.

후속 실험의 실제 LM Studio 컨텍스트 초과 응답이 기존 클라이언트에서 REQUEST_REJECTED로 분류되는 문제를 발견했다. 관측한 stream 오류의 code·type·message 조합만 INPUT_LIMIT으로 인식하도록 고쳤다. 실제 형태 양성 1건과 OOM·잘못된 code/type·파싱 불가 음성 6건을 추가했다. 변경 전 33개 중 1개 실패, 변경 후 33개 통과 및 위 전체 검증으로 회귀를 확인했다.

## 팀 성능 목표와 검증 계획

사용자 확인: 팀 내 목표는 **문서 1,000개를 5분 안에 재정리 완료**다. 시작 요청부터 전체 적용 완료까지 큐·재시도·저장 시간을 포함해 측정한다. 30분 제한은 장애 시 안전 상한이며 목표 시간을 대신하지 않는다.

이전에 제시한 100개 1분·5,000개 20분은 근거가 부족한 제안이므로 확정 기준으로 채택하지 않는다. 1,000개 5분도 현재 달성한 성능으로 기록하지 않는다.

현재 직렬 25개 배치의 분류는 1,000개에 최소 40회 필요하다. 30,743ms가 매번 같다는 가정만 해도 분류 합계 약 20분 30초이며 최종 통합·큐·DB 시간은 빠진다. 실제 회의의 예측값이 아니라 현재 설정의 병목을 보여주는 계산이다.

실자료 검증 전에는 모의 모델 5,000개 DB 실험과 실제 모델 배치 관측을 합쳐 운영 처리량이라고 주장하지 않는다. 비교할 때 모델·양자화·프롬프트 버전·입출력 토큰·주제 후보 수·문서 길이·동시성·냉/온 상태·동시 신규 문서 생성 여부를 고정/기록한다.

다음 검증은 사람이 예상 배정을 표시한 여러 회의 자료로 진행한다. 기존 의미를 놓친 새 주제 생성, 다른 분야의 잘못된 통합, 반복 실행의 불필요한 변경, 장애 중 일관성을 함께 확인한다. 25개 배치의 입력 길이별 시간→100개 전체 실행→1,000개 전체 실행을 측정한다. 표본이 적을 때는 개별값·중앙값·최댓값을 제시하고, 충분한 반복 자료 없이 p95나 SLA를 주장하지 않는다.

후보 최적화는 요약만으로 충분한 문서/추가 본문이 필요한 문서의 구분, 배치 크기, 제한된 동시 요청이다. 현재 구현에 품질 검증 없이 본문 제거·병렬 실행 변경을 적용하지 않았다. 실제 1,000개·5분 달성 여부와 운영 활성화 적합성은 아직 미검증이다.

## 실행 방법

일반 검증: Java 25 환경에서 `./gradlew check`.

실모델 opt-in: 안전한 실행 환경에서 LLM_BASE_URL, LLM_API_TOKEN, LLM_MODEL과 RUN_TOPIC_LIVE_TEST=true를 제공하고 `./gradlew test --tests '*DocumentTopicLiveModelTest'`를 실행한다. 기본 CI에서는 해당 테스트를 건너뛴다. Gradle 실행 결과에는 키를 출력하지 않는다.

작업 지표는 knot.document.topic.steps의 result와 knot.document.topic.step.duration을 확인한다. 로그는 workspaceId·operationId·오류 코드만 남긴다. 전체 작업 지연과 품질 지표는 위 별도 실험 기록으로 보완해야 한다.

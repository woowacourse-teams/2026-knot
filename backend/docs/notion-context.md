# 구현 계획에 필요한 Notion 근거 찾기

백엔드 기획·구현·리뷰에서 관련 원문을 찾는 저장소 공통 문서 탐색 기준이다. 개인 스킬 설치를 요구하지 않으며 어떤 작업 도구에서도 아래 절차를 적용한다.
현재 원문 캐시는 `backend/docs/notion/`에 있고 Git에서 제외한다. 전체 캐시는 수집 자료이며,
백엔드에 필요한 규칙을 모두 검토·정제한 문서가 아니다. 파일 수나 수집 `complete`로 검토 완료를 판단하지 않는다.

## 읽는 순서

1. 사용자 요청·대상 Issue에서 기능, API 경로, 관련 엔티티, 성공·실패 조건을 식별한다.
2. 저장소 루트의 `backend/docs/product/current-v2-mvp.md`, 관련 ADR·기존 구현 계획과 실제 코드를 읽는다.
3. 아래 탐색 범위에서 관련 원문 파일의 **목록부터** 찾고 제목·상태·본문으로 관련성을 확인한다.
4. 선택한 API 계약과 이를 뒷받침하는 도메인·기획 문서를 읽는다. 의존하는 규칙이 있으면 그 문서까지 추가한다.
5. 본문과 필요한 DB 속성을 읽기 좋은 근거로 정리하고, 실제 코드와 비교해 계획서에 기록한다.

## 작업별 탐색 범위

| 작업 | 먼저 찾을 원문 | 함께 확인할 근거 |
|---|---|---|
| HTTP 계약·권한·오류 | `notion/api/`의 경로·메서드·요청·응답 | 관련 도메인 규칙, Controller·DTO·Security·ErrorCode |
| Entity·컬럼·상태 전이 | `notion/domain/`의 Entity·컬럼 관계도·ERDiagram | 관련 API, JPA Entity·Migration·ADR |
| 문서 생성·STT·LLM·재시도 | API와 도메인의 해당 기능 | 관련 기획 정책, Job/Document/Recording 구현과 실패 처리 |
| 워크스페이스·초대·탈퇴 | API와 도메인의 해당 기능 | 현재 MVP 기준, 권한·트랜잭션·삭제 규칙 |
| 요구사항·사용자 흐름 | `notion/planning/`의 현재 정책·기능 요구사항 | 해당 API·도메인, 확정 Issue·ADR |
| 인터뷰·프로토타입·QA | 해당 작업의 필요성이 있을 때만 | 조사·과거 실험·관측 결과로 구분; 확정 요구사항으로 승격하지 않음 |

제목만으로 찾지 못하면 같은 범위에서 API 경로·엔티티 이름·동의어로 본문을 검색한다.
관련 없는 인터뷰·QA·과거 문서는 계획 문맥에 넣지 않는다. 파일 개수를 강제로 제한해 필요한 의존 근거를 누락하지 않는다.

### 로컬 검색 예시

저장소 루트에서 실행한다. 아래 검색어는 예시이며 현재 작업의 단어와 실제 API 경로로 바꾼다.
`--no-ignore`는 Git에서 제외한 이 캐시를 읽기 위해 필요하다. 검색 경로를 이 디렉터리로 한정한다.

```sh
rg --no-ignore -l -i -e '재시도' -e 'retry' -e 'DocumentGenerationJob' backend/docs/notion/api backend/docs/notion/domain -g '*.md' -g '!README.md'
rg --no-ignore -l -e '재시도' -e '문서 생성' backend/docs/notion/planning -g '*.md' -g '!README.md'
```

목록을 확인한 뒤 선택한 파일만 읽는다. manifest에서는 선택한 page_id의 수정 시각·수집 상태를 확인한다.
`history/`·전체 JSON·전체 원문을 한 번에 문맥에 넣지 않는다. 원문 경로를 발견했다고 본문을 읽은 것으로 기록하지 않는다.

## 계획서에 주입하는 근거

선택한 각 자료에서 현재 작업에 필요한 다음 값만 추출한다.

- API: 메서드·경로·입력·출력·권한·오류·멱등성 조건.
- 도메인/ERD: 엔티티 관계·상태 전이·불변 조건·컬럼 제약.
- 기획: 현재 적용 범위·성공/실패 사용자 흐름·제외/미정 사항.
- DB 속성: 현재/과거 구분, 상태, 최신 문서 관계와 작업에 필요한 필드 값.
  Notion 내부 ID·색상·아바타 URL·서식 JSON은 계획에 복사하지 않는다.

계획서의 `범위와 브랜치` 절에 짧은 근거 표를 둔다.

| 자료 | 원문/저장소 출처와 확인 시점 | 이번 작업에 적용하는 사실 | 판정 |
|---|---|---|---|
| 실제로 읽은 자료 | 원문 URL, 필요하면 로컬 경로, 수정 시각 | 필요한 규칙만 요약 | 확정 요구사항 / 현재 구현 관측 / 미확정 / 과거 참고 |

ignored 캐시의 경로만으로 출처를 기록하지 않는다. 다른 개발자가 확인할 수 있도록 원문 URL 또는
추적되는 저장소 문서·Issue·ADR의 출처를 남긴다. 사용자 결정과 같은 항목을 명시적으로 다루는 최신 API의
우선순위는 저장소 공통 정합성 규칙을 따른다. DB의 `구현: YES`는 실제 구현 증거가 아니다.

## freshness와 실패 처리

- 선택한 page_id의 `body_revision`과 `properties_revision`, `captured_at`, `status`를 확인한다.
- 수집된 과거 시점과 현재 원문을 방금 확인한 시점을 구분한다. 캐시가 있다고 현재 최신이라고 단정하지 않는다.
- `revision_mismatch`, `body_missing`, `properties_truncated`가 있으면 해당 근거는 불완전하다.
  `attachment_or_unsupported_block`이면 작업에 필요한 내용이 그 블록에 있는지 확인한다.
- 캐시가 없으면 `docs/harness/notion-docs-sync.md`에 따라 운영 n8n 또는 사용자 export를 이용한다.
  레거시 Notion MCP로 대체하지 않는다. 갱신이 불가능하면 읽을 수 있는 저장소 근거로 진행하며,
  그 누락이 설계에 영향을 주는 항목만 미확정으로 남긴다.

이 절차는 에이전트가 관련 근거를 찾아 읽도록 하는 설정이다. 모든 문서를 자동으로 읽거나,
읽지 않은 문서를 정제하거나, 캐시가 없는 다른 개발자의 환경에 원문을 자동 배포하는 기능은 아니다.

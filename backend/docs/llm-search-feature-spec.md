# Knot AI 문서 검색 MVP 기능 기획서

## 1. 문서 상태

- 상태: MVP 구현 방향 확정
- 기준일: 2026-09-01
- 관련 Issue: #271, #275
- 관련 ADR: [`271-llm-search-architecture-benchmark.md`](adr/271-llm-search-architecture-benchmark.md)
- 선택 방향: 마지막 성공 동기화 스냅샷을 사용하는 PostgreSQL 기반 하이브리드 RAG

이 문서는 통제 스냅샷과 LM Studio/Notion MCP smoke test 결과를 반영한 MVP 기능 계약이다. ADR은 저장소 규칙에 따라 팀 리뷰 전까지 `Proposed`로 유지하고, 리뷰 승인 후 `Accepted`로 변경한다.

## 2. 해결할 문제

팀원은 과거 회의록과 결정사항을 찾을 때 문서 제목·날짜·위치를 기억해야 한다. 문서가 존재해도 여러 페이지를 직접 확인하거나 팀원에게 다시 물어봐야 하므로 정보 탐색 시간이 길고 성공률이 낮다.

사용자는 문서 위치나 날짜를 기억하지 않아도 자연어로 다음을 질문할 수 있어야 한다.

- `우리 코드 컨벤션 뭐로 정했지?`
- `PostgreSQL을 왜 사용하기로 했더라?`
- `로드맵 회의 언제 했지?`

## 3. 제품 목표와 성공 기준

### 목표

1. 자연어 질문만으로 Knot Workspace의 동기화된 팀 문서를 찾는다.
2. 답변과 근거 문서를 함께 제공해 사용자가 원문을 확인할 수 있게 한다.
3. 기존 수동 탐색보다 정보 탐색 시간을 줄이고 성공률을 높인다.
4. 사용자 화면에 첫 답변 내용을 5초 이내 표시하는 것을 목표로 한다.

### 성공 기준

한 질의는 다음 조건을 모두 만족할 때 성공으로 판정한다.

- 답변이 원문 의미를 왜곡하지 않는다.
- 동기화된 Workspace 문서에서 확인할 수 있는 정보만 답한다.
- 관련 문서는 질문과 직접 관련된 문서만 최대 3개 제공한다.
- 문서 날짜, 간단한 내용, 제목으로 사용자가 문서를 판단할 수 있다.
- 문서가 충돌하면 임의로 하나를 최종 정답으로 선택하지 않는다.
- 근거가 없으면 찾지 못했다고 말한다.
- 사용자가 답변과 문서를 확인하고 `찾았어요`라고 판단할 수 있다.

최종 정보 탐색 성공률 목표값은 30개 이상 독립 질문에 대한 사람 평가 후 결정한다.

## 4. 권한과 검색 범위

- Knot Workspace 소유자가 해당 Workspace의 Notion OAuth 연결을 설정한다.
- 소유자가 승인한 Notion 페이지와 하위 페이지를 Knot Workspace 공용 검색 코퍼스로 취급한다.
- 해당 Knot Workspace의 팀원은 같은 공용 코퍼스를 검색할 수 있다.
- 개인 Notion 계정의 권한을 매 검색마다 재판정하는 방식은 MVP에서 지원하지 않는다.
- 선택·승인되지 않은 Notion 페이지, 다른 Notion Workspace, 다른 Knot Workspace의 문서는 색인·답변 근거에서 제외한다.
- Notion OAuth access/refresh token은 Java 백엔드에 암호화해 보관하고, 채팅 모델이나 프롬프트에 전달하지 않는다.
- 연결된 사용자가 Notion 원문을 직접 볼 수 없는 경우를 고려해 MVP의 관련 문서 카드는 제목·날짜·요약·참조 상태를 우선 제공한다. 원문 링크와 Knot 내부 미러링은 별도 범위다.

> MVP 권한 모델은 “Workspace 소유자가 승인한 문서를 해당 Knot Workspace 구성원이 함께 검색”하는 방식이다. 개인별 Notion ACL을 적용해야 한다면 별도 권한 모델과 재검토가 필요하다.

## 5. 연결·동기화·활성화 흐름

### 상태별 동작

| 상태 | AI 검색 | 동작 |
| --- | --- | --- |
| 최초 전체 동기화 중 | 불가 | 전체 동기화가 성공할 때까지 검색 입력을 비활성화한다. |
| 최초 전체 동기화 완료 | 가능 | 완료된 스냅샷과 pgvector 인덱스를 활성화한다. |
| 활성 상태에서 재동기화 중 | 가능 | 기존 마지막 성공 스냅샷으로 검색하고 최신화 상태를 표시한다. |
| 재동기화 성공 | 가능 | 새 스냅샷을 검증한 뒤 원자적으로 활성 스냅샷을 교체한다. |
| 일반 재동기화 실패 | 가능 | 기존 성공 스냅샷을 유지하고 최신 문서가 아닐 수 있음을 표시한다. |
| 연결 해제 | 불가 | 연결과 인덱스를 논리적으로 비활성화하고 토큰을 폐기한다. |
| 재연결 후 전체 동기화 중 | 불가 | 새 전체 동기화가 끝나기 전에는 기존 스냅샷을 다시 활성화하지 않는다. |
| 재연결 동기화 완료 | 가능 | 새로 완료된 스냅샷만 활성화한다. |
| 재연결 동기화 실패 | 불가 | 비활성 연결을 되살리지 않고 재시도를 안내한다. |

### 동기화 원칙

- Notion 문서를 정규화할 때 page ID, 제목, 원본 URL, 계층, 작성일, 수정일, 본문을 보존한다.
- 문서와 청크에는 `workspace_id`, `connection_id`, `snapshot_id`를 포함해 범위를 강제한다.
- 부분 동기화 결과는 검색에 노출하지 않는다.
- 기존 문서는 물리 삭제 대신 논리 삭제/비활성화를 우선한다.
- 같은 Notion Workspace를 다시 연결하면 기존 연결을 무조건 폐기하지 않고 재인증·전체 동기화 후 다시 활성화할 수 있게 한다.

## 6. 사용자 흐름

### 최초 진입

1. 사용자가 AI 검색 페이지에 진입한다.
2. 최초 사용자면 새 대화 세션을 생성하고, 기존 사용자는 최근 세션을 선택하거나 새 세션을 만든다.
3. 입력창에 질문 예시를 표시한다.
4. 최초 동기화가 끝나지 않았다면 동기화 상태와 검색 잠금 사유를 표시한다.

### 질문과 답변

1. 사용자가 자연어 질문을 입력한다.
2. 현재 선택된 세션의 이전 대화만 문맥으로 사용한다.
3. 활성 스냅샷에서 관련 청크를 검색한다.
4. 검색된 근거만 채팅 모델에 전달해 답변을 스트리밍한다.
5. 답변 아래에 직접 관련된 문서를 최대 3개 표시한다.
6. 질문·답변·관련 문서·참조 상태·피드백을 현재 세션에 저장한다.
7. 사용자는 `👍 찾았어요` 또는 `👎 못 찾았어요`를 답변마다 한 번 남긴다.

### 처리 상태

5초 안에 답변 청크가 표시되지 않으면 검색을 중단하지 않고 다음과 같은 사용자 언어 상태를 표시한다.

- `팀 문서에서 관련 내용을 찾고 있어요`
- `관련 문서를 선별하고 있어요`
- `답변을 정리하고 있어요`

내부 용어인 임베딩·rerank·MCP 호출명을 사용자 상태 문구에 노출하지 않는다. 문서 개수와 후보 수는 실제 계측값과 불일치할 수 있으므로 초기 MVP에서는 고정된 진행 단계 중심으로 표시한다.

## 7. 지원 질문과 답변 정책

| 유형 | 처리 방식 |
| --- | --- |
| 사실 질문 | 문서에 기록된 사실과 관련 문서를 답한다. |
| 결정 근거 질문 | 결정 사실과 문서에 명시된 이유를 구분해 답한다. 이유가 확인되지 않으면 추정하지 않는다. |
| 문서 위치/회의 날짜 | 날짜, 간단한 내용, 관련 문서를 함께 제공한다. |
| 후속 질문 | 현재 세션의 직전 문맥을 유지하되, 이전 세션은 참조하지 않는다. |
| 충돌 | 문서별 주장과 날짜를 보여주고 어떤 내용이 최종인지 확정하지 않는다. |
| 정보 없음 | `현재 동기화된 팀 문서에서는 관련된 정보를 찾지 못했습니다.`라고 답한다. |
| 너무 넓은 질문 | 최근 결정사항·로드맵·백엔드 진행 상황 등 선택지를 제시해 범위를 좁힌다. |
| 애매한 질문 | 문맥으로 특정할 수 있으면 추론 사실을 밝히고, 특정할 수 없으면 구체화를 요청한다. |

## 8. 기술 결정

### 기본 검색 경로

```text
Notion OAuth (Workspace 소유자)
        ↓
Java 백엔드 동기화
        ↓
문서 정규화·청킹·메타데이터 저장
        ↓
PostgreSQL + pgvector 임베딩 인덱스
        ↓
질의 정규화 + PostgreSQL 키워드/메타데이터 pre-filter
        ↓
Qwen3-Embedding-0.6B 의미 검색
        ↓
필요한 청크만 Qwen 채팅 모델에 전달
        ↓
답변 + 관련 문서 최대 3개 + 피드백
```

### 각 방식의 역할

| 방식 | MVP 역할 | 결정 근거 |
| --- | --- | --- |
| Raw 전체 원문 | 제외 | 현재 스냅샷은 약 155만 자로 컨텍스트 보호선을 초과했다. |
| PostgreSQL 직접 검색 | pre-filter와 빠른 기준선 | 검색 p50 약 79.6ms로 가장 빠르지만 의미가 다른 표현에 약하다. |
| pgvector RAG | 기본 검색 경로 | 한국어 의미 검색과 Workspace·스냅샷·문서 근거 통제가 가능하다. |
| MCP live | 동기화/원문 확인·별도 비교 | 실제 호출은 가능했지만 질의마다 도구를 호출하면 지연이 크다. |

MCP는 접근 프로토콜이지 검색 품질 자체가 아니다. MCP가 pgvector를 조회하면 RAG 경로로 분류하며, MVP의 기본 질의 경로는 Java 백엔드가 관리하는 PostgreSQL 스냅샷으로 고정한다.

### 모델과 저장소

- 임베딩 기본 후보: `Qwen3-Embedding-0.6B-GGUF`, 현재 실험 응답 차원 1,024
- 벡터 저장소: PostgreSQL `pgvector`
- 채팅 모델: 모델 공급자 교체가 가능한 추상화로 두고, 현재 검증은 LM Studio의 `qwen/qwen3.6-27b`로 수행한다.
- Hosted NIM은 동일한 입력·프롬프트·생성 옵션으로 교체 검증할 수 있게 한다.
- 모델에는 Notion token을 전달하지 않고 검색된 문서 청크와 필요한 메타데이터만 전달한다.

## 9. 속도 기준과 실제 측정

### 목표

`request accepted`부터 사용자 화면의 첫 답변 청크까지를 end-to-end TTFT로 측정하고 5초 이내 표시를 목표로 한다. 검색 준비 시간, 임베딩 시간, pgvector 시간, 모델 TTFT, 최종 완료 시간을 분리 계측한다.

### 현재 측정값

통제 스냅샷의 동일 질문·동일 모델 비교 결과는 다음과 같다.

- RAG 검색 p50: **약 200.2ms**
- RAG 임베딩 p50: **약 132.4ms**
- pgvector 단계 p50: **약 73.4ms**
- DB 직접 검색 p50: 약 79.6ms
- MCP replay 검색 p50: 약 118.7ms
- 통제 생성 실험의 RAG·DB·MCP replay 첫 답변: 각각 10/10건 5초 이내

실제 LM Studio/Notion MCP smoke test에서는 end-to-end 완료가 약 38~77초, 후속 질문은 약 190초였다. 따라서 제품 기본 경로를 질의마다 실시간 Notion MCP를 호출하는 방식으로 두지 않는다.

RAG 검색 자체는 약 0.2초 수준이지만 답변 생성 모델의 reasoning·출력량이 전체 응답 시간을 좌우한다. 5초 목표는 검색 시간만으로 충족했다고 판단하지 않고, Java 연동 환경에서 end-to-end TTFT로 다시 검증한다.

## 10. 저장해야 하는 정보

구현 시 다음 개념적 데이터를 Workspace 범위로 분리한다.

- Notion 연결: provider, Workspace 식별자, 암호화 credential, 연결 상태
- 동기화 실행: 시작·완료·실패 시각, 동기화 상태, 오류, 대상 범위
- 문서/청크: page ID, 제목, URL, 날짜, 계층, 본문, 논리 삭제 상태, snapshot ID
- 임베딩: 모델 식별자, 차원, 청크 식별자, 벡터, 생성 시각
- 대화 세션: Workspace, 생성자, 제목, 생성·수정 시각
- 메시지: 사용자/AI role, 내용, 순서, 생성 상태
- 답변 근거: 메시지와 관련 문서·청크·참조 상태의 연결
- 피드백: 하나의 AI 답변에 하나의 `찾았어요/못 찾았어요`

## 11. 구현 순서

1. Workspace 소유자 Notion OAuth와 대상 페이지 설정을 기존 연결 경계에 연결한다.
2. 최초 전체 동기화·재동기화·재연결·논리적 삭제·원자적 snapshot 활성화를 구현한다.
3. PostgreSQL 문서/청크/pgvector 색인과 키워드 pre-filter를 구현한다.
4. 하이브리드 검색 결과를 기존 채팅 스트리밍에 연결하고 근거 문서 최대 3개를 반환한다.
5. 사실·결정 근거·문서 위치·후속·충돌·무응답·광범위 질문 정책을 적용한다.
6. 세션 복원, 답변 근거 저장, 피드백 저장을 연결한다.
7. 검색 단계와 모델 단계를 계측하고 5초 초과 상태를 표시한다.
8. 30개 이상 독립 질문과 사람 품질 평가로 운영 전환 여부를 판정한다.

## 12. 인수 조건

- [ ] 최초 전체 동기화 완료 전 AI 검색을 사용할 수 없다.
- [ ] 최초 동기화 완료 후 활성 snapshot으로 팀원이 검색할 수 있다.
- [ ] 재동기화 중에는 기존 성공 snapshot으로 검색할 수 있다.
- [ ] 재동기화 성공 시 새 snapshot이 원자적으로 활성화된다.
- [ ] 연결 해제는 논리적 삭제/비활성화이며 token은 폐기된다.
- [ ] 같은 Notion Workspace 재연결은 전체 동기화 완료 후에만 다시 활성화된다.
- [ ] 다른 Workspace의 문서·세션·근거가 섞이지 않는다.
- [ ] Notion token이 모델 요청·로그·응답·프롬프트에 노출되지 않는다.
- [ ] 답변마다 직접 관련 문서를 최대 3개 제공하고 무관한 문서로 수를 채우지 않는다.
- [ ] 충돌·정보 없음·너무 넓은 질문을 각각의 정책대로 처리한다.
- [ ] 세션을 새로고침·재로그인 후에도 복원하고 현재 세션의 후속 질문만 사용한다.
- [ ] 각 AI 답변에 피드백 하나를 저장하고 다시 열어 확인할 수 있다.
- [ ] end-to-end 첫 답변 청크 시간과 검색/모델 단계별 시간을 기록한다.
- [ ] 5초 초과 시 사용자 언어 상태를 표시하고 검색을 계속한다.

## 13. MVP에서 하지 않는 것

- 매 질문마다 Workspace 전체 원문을 모델에 전달하는 방식
- 매 질문마다 실시간 Notion MCP를 기본 검색 경로로 호출하는 방식
- 사용자가 직접 검색 범위를 지정하는 기능
- 개인별 Notion ACL을 매 검색마다 재판정하는 기능
- 프로젝트 전체 요약·기간별 요약·다문서 신규 분석
- 서로 다른 대화 세션의 자동 맥락 결합
- 다른 사용자의 개인 세션 조회
- 다른 Workspace의 문서·세션·근거 결합
- Notion과 Knot의 양방향 편집·Knot 내부 원문 미러링
- reranker의 최종 모델·점수식을 현재 문서만으로 확정하는 것

## 14. 출시 전 보류 조건

MVP 내부 검증은 하이브리드 RAG로 진행한다. 다만 다음 검증이 끝나기 전에는 전체 사용자 대상 운영 전환을 완료로 보지 않는다.

- Java가 Workspace별 credential을 올바르게 선택하고 서버 내부에서만 사용하는지
- 연결 해제·재인증·권한 범위·Workspace 격리가 동작하는지
- 30개 이상 독립 질문에서 답변 의미와 관련 문서 품질이 기준을 통과하는지
- 실제 동기화 데이터에서 end-to-end TTFT 5초 목표가 충족되는지
- 임베딩·pgvector 인덱스 비용과 문서 증가에 따른 성능이 감당 가능한지

위 조건이 실패하면 RAG를 즉시 폐기하는 것이 아니라 pre-filter, 청킹, rerank, 모델 reasoning 설정을 조정한 뒤 동일 평가셋으로 재검증한다.

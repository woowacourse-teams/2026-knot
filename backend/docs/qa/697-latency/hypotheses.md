# #722 탐색 지연 가설 및 검증

작성: 2026-10-16
상태: 고정 fixture 수동 A/B 완료. 넓은 질문 정답셋과 prompt 순서 실험은 후속 과제

## 기존 관측

초기 실측에서 단일 회의 질문의 첫 delta p50은 8.296초, 회의 간 비교는 18.547초였다. 이후 동일한 코드·모델·고정 fixture로 다시 실행한 agent 기준선은 각각 8.171초와 19.604초였다. 같은 실험의 `direct-search` 변형은 각각 2.695초와 2.597초였다. A/B 실행은 변형·시나리오별 워밍업 3회와 측정 3회이며, 첫 delta 및 최종 답변·근거의 fixture 검증을 통과했다.

세 표본은 분산과 꼬리 지연을 안정적으로 추정하기에 부족하다. 기존 측정은 고정 합성 문서와 좁은 문자열 기대값을 사용해 전체 검색 품질을 입증하지 않는다. 따라서 아래 항목은 원인 확정이 아니라 반증 가능한 가설로 취급한다.

## 가설

## A/B 결과

| 질문 유형 | 경로 | 첫 delta p50 / p95 | 전체 완료 p50 / p95 | 측정 답변 |
| --- | --- | ---: | ---: | ---: |
| 단일 회의 | 기존 agent | 8.171 / 8.412초 | 9.667 / 9.835초 | 3/3 답변·근거 통과 |
| 단일 회의 | 수동 direct search | 2.695 / 3.150초 | 4.097 / 4.289초 | 3/3 답변·근거 통과 |
| 회의 간 비교 | 기존 agent | 19.604 / 19.754초 | 22.085 / 22.562초 | 3/3 답변·근거 통과 |
| 회의 간 비교 | 수동 direct search | 2.597 / 2.659초 | 5.463 / 5.551초 | 3/3 답변·근거 통과 |

측정 표본 3개의 nearest-rank p95는 사실상 표본 최댓값이다. 기존 agent와 비교해 첫 delta p50은 단일 회의 fixture에서 67.0%, 회의 간 비교 fixture에서 86.8% 짧았다. 수동 변형도 분류와 최종 답변 생성을 그대로 사용하고 검색 계획 LLM·MCP 왕복만 건너뛴다. 따라서 결과는 검색 범위를 좁힐 수 있는 fixture에서의 가능성 증거이며, 일반 질문에 대한 대체 경로 채택 근거는 아니다.

기존 경로의 단일 회의 retrieval은 약 5.3–5.5초였고 순차 탐색 LLM 호출 3회가 대부분을 차지했다. 회의 간 비교 retrieval은 약 15.7–16.5초였고 탐색 LLM 호출 4회가 약 15.7–16.2초였다. MCP handshake와 검색·목록·읽기 도구 왕복은 이 시간에 비해 작았다. 반대로 direct-search의 DB 검색·문서 읽기는 수 밀리초에서 수십 밀리초였고 기대한 fixture 문서 ID가 모두 `SearchEvidence`에 기록됐다. 따라서 H1, H2, H4는 이 고정 fixture에서 지지된다.

회의 간 비교에서는 각 계획 호출의 입력 token 수가 899 → 1,018 → 1,466 → 1,942로 늘었지만 응답 시간은 호출별로 단조 증가하지 않았다. 예를 들어 1,466-token 호출은 앞선 두 호출보다 빨랐다. 출력 길이·모델 상태도 함께 변하므로 H3는 미판정이며, 반복 문맥이 원인이라고 단정하지 않는다.

직접 검색 변형에서 분류는 워밍업 후 대체로 0.8–1.2초였다. `SearchAnswerJsonStream`은 전체 JSON에서 `answer` 키를 찾은 뒤에야 본문을 내보낸다. 로그에서 첫 provider content부터 첫 SSE delta까지 대략 1.1초가 추가로 걸렸고, 서버가 첫 delta를 보낼 때의 `contentPersistedAtToSseSendMs`는 대체로 100ms 미만이었다. 이는 서버 SSE send가 아니라 응답 필드 생성 또는 파싱 경로를 추가 조사할 근거다. 다만 `answer` 키가 실제로 도착한 시각을 직접 기록하거나 필드 순서를 바꾸는 대조군은 없으므로 H6의 원인 여부는 아직 검증되지 않았다. `answer`를 JSON 응답의 첫 필드로 요청하고 동일한 답변·근거 검증을 유지하는 A/B가 다음 실험이다.

## 검증 방법

1. `agent` 기준 경로와 수동 `direct-search` 변형을 같은 모델·질문·fixture·로컬 PostgreSQL·SSE 경로로 실행한다. 두 경로는 시나리오마다 세 번 워밍업하고 각각 세 번 측정했다.
2. `direct-search`는 분류와 최종 답변 생성을 유지하고, 검색 계획 LLM과 MCP 왕복만 건너뛴다. 질문 원문을 기존 DB 검색에 전달하고 상위 세 문서를 직접 읽는다. 운영 기본값이나 production 코드 동작은 바꾸지 않는다.
3. 첫 delta·전체 완료·분류·검색·각 LLM 호출·MCP 호출을 기록한다. 검색된 근거가 fixture 문서 ID를 포함하고 답변에 fixture 핵심 문자열이 있는지도 검사한다.
4. H1/H2/H4는 직접 검색 A/B와 phase 로그로 판정했다. H3는 provider의 `promptTokens`와 응답 시간을 대조했지만 입력 토큰이 늘어도 응답 시간이 단조 증가하지 않아 미판정이다. H5/H6는 classifier·provider first content·SSE 전송 시각과 파서 구현을 함께 대조했다.
5. 작은 수동 표본으로 방향만 확인했다. 통계적 성능 주장이나 배포 결정 전에는 각 변형 30회 이상과 더 넓은 한국어 정답·근거 세트를 사용해야 한다.

## 판정 원칙

- 속도 개선은 첫 delta p50/p95 및 `document_retrieval` 시간으로 본다.
- 사실 문자열뿐 아니라 실제 `search_evidences` 문서 ID가 기대 문서와 일치해야 품질 관측을 통과한다.
- 직접 경로의 고정 fixture 통과는 일반 한국어 질문의 정확도 증거가 아니다.
- H3의 prompt token 수가 제공되지 않으면 문맥 크기가 원인이라고 단정하지 않는다.
- `progress` 이벤트는 체감 대기 안내이며, 첫 답변 delta 단축으로 계산하지 않는다.

# 탐색 첫 delta 지연 문제 해결 기록

작성일: 2026-10-16
대상: Issue [#722 탐색 첫 delta 지연 구간 계측](https://github.com/woowacourse-teams/2026-Knot/issues/722)
상태: 단계별 계측 및 고정 fixture A/B 완료. 일반 질문 품질을 포함한 빠른 검색 경로 채택은 미결정.

## 문제 상황

탐색 질문을 보낸 뒤 화면에 답변이 처음 나타나기까지 오래 걸린다. 사용자는 실제 화면에서 첫 delta가 약 36초 걸린 사례를 보고했다. 당시 요청 ID와 단계별 로그가 없어 그 요청의 정확한 원인은 재구성할 수 없었다. 이후 Qwen 기반 실제 모델 요청과 서버 계측 로그를 사용해 단일 회의 질문과 여러 회의 비교 질문을 분리 측정했다.

측정 대상은 질문 전송부터 클라이언트가 첫 완전한 SSE `delta` 이벤트를 수신할 때까지다. 전체 답변 종료 시간도 함께 기록한다. 접수 커밋 후 worker 대기, 의도 분류, 문서 탐색, 탐색 중 LLM·MCP 호출, 최종 답변 LLM, 답변 저장, SSE 전달을 `answerId`로 연결해 본다. 질문·답변 원문은 로그에 저장하지 않고 입력 문자 수와 provider가 제공하는 토큰 수만 기록한다.

처음에는 첫 delta와 전체 완료 시간만 보였기 때문에 느린 구간이 검색, 모델, 도구 통신, 저장, SSE 중 어디인지 알 수 없었다. 특히 단일 회의의 사실 조회와 회의 간 변경·이유 종합을 같은 질문 경로로 처리해도 되는지 확인할 기준이 없었다.

## 가설

| ID | 가설 | 관측되면 기대하는 결과 |
| --- | --- | --- |
| H1 | 탐색 계획을 위한 순차 LLM 호출이 첫 delta 지연의 주된 원인이다. | 각 계획 호출의 시간이 검색 구간 대부분을 차지하며, 이 호출을 건너뛴 경로에서 첫 delta가 크게 줄어든다. |
| H2 | 여러 회의 질문은 DB/MCP 왕복보다 더 많은 순차 계획 호출 때문에 느리다. | 비교 질문에서 LLM 탐색 호출 수와 시간이 늘고, 도구 왕복 시간은 작게 유지된다. |
| H3 | 매 탐색 호출에 앞선 문맥과 도구 결과를 반복 전달해 입력 처리 시간이 커진다. | 입력 토큰이 커질수록 응답 시간이 함께 증가한다. |
| H4 | 간단한 질문은 질문 원문으로 DB 검색하고 상위 문서를 읽어도 핵심 사실과 실제 근거를 보존할 수 있다. | 직접 검색 경로가 같은 fixture의 핵심 답과 근거 문서 ID를 유지하면서 지연을 줄인다. |
| H5 | 분류와 서버 SSE 전송은 기존 경로에서 가장 큰 병목이 아니다. | 분류·전송 시간이 순차 탐색보다 작고, 직접 검색 후에는 다음 병목 구간으로 분리된다. |
| H6 | JSON 답변의 `answer` 필드가 늦게 생성되어 provider 첫 content와 client 첫 delta 사이에 추가 대기가 생긴다. | 두 시각 사이에 반복 가능한 간격이 있으며, 현재 파서가 `answer`를 보기 전에는 본문을 내보내지 않는다. |

## 가설 검증

실제 `qwen3.8-27b`를 HTTPS OpenAI 호환 API로 호출하고, Testcontainers PostgreSQL 및 로컬 Spring SSE 흐름을 사용했다. Dev/RDS는 사용하지 않았다. 기존 `agent` 경로와 QA 전용 수동 `direct-search` 변형을 같은 모델·질문·고정 DRAFT 문서 fixture로 비교했다. `direct-search`도 분류와 최종 답변 생성을 유지하고, 탐색 계획 LLM 및 MCP 왕복만 건너뛰어 기존 DB 검색에 질문 원문을 전달한 뒤 상위 세 문서를 읽는다. 이 실험 경로는 운영 코드의 기본 동작을 바꾸지 않는다.

각 경로·시나리오마다 순차 3회 워밍업 후 3회 측정했다. 따라서 A/B 측정값은 총 12건이며, 각 측정 답변은 `COMPLETED`, 예상 핵심 사실, 예상 `SearchEvidence.documentId`를 모두 통과했다. 이 검증은 고정 fixture에 대한 자동 assertion이지 사람이 평가한 전체 답변 품질 점수는 아니다.

| 질문 유형 | 확인 내용 |
| --- | --- |
| 단일 회의 | 배포 회의에서 담당자로 정한 사람을 찾는다. |
| 회의 간 비교 | 6월 10일 카드 결제 논의에서 6월 12일 계좌 이체 결정으로 바뀐 점과 수수료 이유를 찾는다. |

운영 환경 설정 중 모델 요청을 막는 문제도 재현해 분리했다. 클라이언트는 base URL 뒤에 `/v1/chat/completions`를 붙이므로 `KNOT_LLM_BASE_URL`에 `/v1`을 넣으면 URL 검증에 실패한다. base에는 HTTPS 호스트만 지정해야 한다. 사용자가 제공한 평문 HTTP 주소는 인증 없이 401을 반환했고 HTTPS로 redirect하지 않았다. 키를 평문 HTTP로 보내지 않고 HTTPS 주소로 실험했다. API 키는 비공개 환경 설정에서만 사용했으며 문서·로그·명령 인수에 기록하지 않았다.

## 실행 계획

1. `answerId`를 기준으로 단계별 로그를 연결한다. worker 대기, 의도 분류, 문서 검색, 탐색 LLM 호출별 시간·입력 길이·token usage, MCP handshake·도구 호출, 최종 LLM 첫 content·완료, 저장과 첫 SSE send를 나눈다.
2. 기준 경로와 직접 검색 변형을 단일 회의 및 회의 간 비교 fixture에서 같은 조건으로 실행한다. 질문·문서·모델·DB·SSE 경로를 고정하고 경로별 워밍업 3회 후 측정 3회를 수행한다.
3. 응답이 끝까지 완료되는지, 답변의 핵심 사실이 기대 문구를 포함하는지, 저장된 근거 문서 ID가 기대 문서인지 확인한다. 지연만 줄고 근거가 사라지는 경로는 개선으로 판정하지 않는다.
4. 단계별 시간을 비교해 병목 가설을 지지·기각·미판정으로 나눈다. 세 표본 결과를 운영 p95나 전반적인 검색 정확도 주장으로 확대하지 않는다.
5. 다음 실험에서는 먼저 H6을 분리한다. `answer` 필드가 JSON 출력의 첫 필드가 되도록 요청한 변형과 현재 파서를 같은 질문·모델·정답·근거 조건으로 비교하고, 파서가 필드를 관측한 시각도 계측한다.
6. 빠른 경로 채택 여부는 더 넓은 한국어 정답셋으로 결정한다. 단일 회의, 회의 간 변경, 담당자·날짜, 후속 질문, 모호한 기간, 결과 없음, 근거 충돌을 포함하고 답변 사실과 실제 evidence 전체를 검토한다. 품질이 확정되기 전에는 agent 경로를 대체하지 않는다.

재현용 Gradle 명령, 환경 변수 주입 방법, 로그 필드와 측정 정의는 [수동 latency benchmark 안내](README.md)에 있다. 여기의 실제 A/B 측정은 문서의 기본 30회 재현 절차가 아니라, 개발 중 방향을 확인하기 위한 각 조건 3회 측정이다.

## 결과

측정은 모두 초 단위다. 세 표본의 nearest-rank p95는 사실상 표본 최댓값이다.

| 질문 유형 | 경로 | 첫 delta p50 / p95 | 전체 완료 p50 / p95 | 핵심 사실·근거 |
| --- | --- | ---: | ---: | --- |
| 단일 회의 | 기존 agent | 8.171 / 8.412 | 9.667 / 9.835 | 3/3 통과 |
| 단일 회의 | 수동 direct search | 2.695 / 3.150 | 4.097 / 4.289 | 3/3 통과 |
| 회의 간 비교 | 기존 agent | 19.604 / 19.754 | 22.085 / 22.562 | 3/3 통과 |
| 회의 간 비교 | 수동 direct search | 2.597 / 2.659 | 5.463 / 5.551 | 3/3 통과 |

측정 p50 기준으로 첫 delta까지 걸린 시간은 단일 회의 질문에서 5.476초(67.0%), 회의 간 비교 질문에서 17.007초(86.8%) 줄었다. 전체 답변 완료 시간은 단일 회의 질문에서 5.570초(57.6%), 회의 간 비교 질문에서 16.622초(75.3%) 줄었다. 이는 각 조건을 세 번 측정한 고정 fixture 결과이며, 운영 트래픽의 일반적인 개선량을 뜻하지 않는다.

같은 fixture에서 direct search는 첫 delta p50을 단일 회의 질문에서 67.0%, 회의 간 비교에서 86.8% 줄였다. 기존 agent 경로의 문서 탐색은 단일 회의에서 약 5.3–5.5초, 회의 간 비교에서 약 15.7–16.5초였다. 단일 회의는 탐색 계획 LLM 3회, 비교 질문은 4회를 순차 호출했다. 검색·목록·읽기 MCP 도구 호출은 주로 한 자릿수에서 수십 밀리초여서 두 fixture에서 주요 병목은 도구 왕복이 아니라 반복된 LLM 계획 호출이었다.

직접 검색에서도 분류는 약 0.8–1.2초 남았다. 최종 답변 모델이 첫 content를 보내기까지는 대략 0.9초였지만, provider 첫 content와 클라이언트 첫 delta 사이에 약 1.1초가 관측됐다. `SearchAnswerJsonStream`은 JSON의 `answer` 키를 읽기 전까지 본문을 내보내지 않는다. 서버의 첫 SSE send 측정은 대체로 100ms 미만이었다. 이 차이는 H6을 시험할 근거지만, `answer` 키가 실제 도착한 시각을 별도로 재지 않았고 필드 순서를 바꾼 대조군도 없으므로 원인이 확인된 것은 아니다.

회의 간 비교 호출에서 기록된 prompt token 수는 899 → 1,018 → 1,466 → 1,942로 증가했지만 각 호출 응답 시간은 단조 증가하지 않았다. 출력 길이와 모델 서버 상태 등 다른 요인이 함께 움직이므로 H3는 판정하지 않았다.

| 가설 | 판정 | 근거와 한계 |
| --- | --- | --- |
| H1 순차 탐색 LLM이 병목 | 고정 fixture에서 지지 | 직접 검색에서 첫 delta가 크게 줄고 agent의 검색 구간은 순차 LLM 호출 시간으로 설명된다. |
| H2 다중 회의의 계획 호출 증가 | 지지 | 비교 질문이 4회 계획 호출을 하고 탐색 시간이 더 길었다. 두 질문 유형만 비교했다. |
| H3 반복 입력 문맥이 주원인 | 미판정 | 입력 token은 증가했으나 응답 시간과 단조 관계가 없었다. |
| H4 직접 검색으로 사실·근거 보존 | 고정 fixture에서 지지 | 두 fixture의 측정 6/6이 기대 답변과 document ID를 통과했다. 일반 한국어 질문은 미검증이다. |
| H5 분류·SSE가 주요 병목이 아님 | 부분 지지 | agent의 탐색보다 작고 SSE send는 짧다. 직접 검색 후 classifier와 JSON 전달 대기가 남는다. |
| H6 JSON 필드 순서가 delta 지연 원인 | 미검증 후보 | provider 첫 content 이후 간격과 현재 파서 동작은 관측했지만 조작 실험은 안 했다. |

초기 화면에서 보고된 약 36초는 당시 개별 요청의 correlation 로그가 없어 위의 통제된 측정 표와 직접 대응시킬 수 없다. 위 실험은 해당 증상과 유사한 지연 경로를 좁혔으며 최초 요청의 원인을 소급 확정한 것이 아니다.

측정 구현에서는 answer ID로 구간 로그를 연결하고, 질문·문서 내용을 남기지 않으며, provider가 token usage를 주지 않으면 수치를 추정하지 않는다. `contentPersistedAtToSseSendMs`는 DB snapshot의 `updatedAt`부터 서버 `SseEmitter.send()` 반환까지의 근사치다. 이는 브라우저가 수신 확인한 시간이 아니며, 사용자 체감 첫 delta는 benchmark의 클라이언트 수신 시각으로 판단한다.

## 결론

첫 delta 지연의 현재 가장 강한 설명은 기존 agent 경로가 문서를 찾기 전 계획용 LLM을 여러 차례 순차 호출한다는 점이다. 고정된 두 fixture에서는 MCP·DB 왕복보다 이 호출이 훨씬 큰 시간을 차지했다. 단순 질문에서는 직접 검색이 크게 빨랐고 답변과 근거도 유지했지만, 실험 질문이 두 개뿐이므로 모든 질문에 agent를 제거하거나 direct search를 기본값으로 채택할 근거는 부족하다.

현재의 다음 병목 후보는 분류 지연과 JSON 파서가 첫 content를 client delta로 내보내기까지의 대기다. 우선 `answer` 필드 순서 A/B를 추가해 이 대기의 원인을 확인하고, 동시에 더 넓은 정답·근거 세트로 간단한 질문 빠른 경로의 재현율과 근거 충실도를 평가한다. 그 전까지 결과는 최적화 방향을 고르는 실험 근거로 사용하고 제품 동작 변경이나 운영 성능 보장으로 표현하지 않는다.

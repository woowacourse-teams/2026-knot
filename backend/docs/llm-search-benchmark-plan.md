# Knot LLM 문서 검색 벤치마크 계획

## 1. 문서 상태

- 상태: 통제 스냅샷 1차 실행 및 LM Studio/Notion MCP-live smoke test 완료, 하이브리드 RAG MVP 방향 결정, 운영 전환 검증 전
- 목적: Notion 팀 문서 검색에 사용할 아키텍처를 실측으로 결정
- 최종 도입 방식: MVP는 하이브리드 RAG로 진행하고, 전체 사용자 운영 전환은 추가 품질·권한·지연 검증 후 결정
- 현재 범위: Notion Markdown 내보내기 기반 통제 실험 → LM Studio/실제 Notion MCP smoke test → Java 연동 및 전체 비교 검증
- 구현 원칙: MVP 기본값은 하이브리드 RAG로 두되, 운영 전환 전 검증 게이트와 재검토 조건을 통과해야 한다.

## 2. 문제와 목표

팀원이 과거 회의록이나 결정사항을 찾을 때 문서의 날짜·위치·제목을 기억해야 하는 문제를 해결한다.

사용자는 다음과 같은 자연어 질문만으로 팀 문서에서 정보를 찾는다.

- `우리 코드 컨벤션 뭐로 정했지?`
- `PostgreSQL을 왜 사용하기로 했더라?`
- `로드맵 회의 언제 했지?`

### 제품 목표

1. 기존 수동 문서 탐색보다 정보 탐색 시간을 줄인다.
2. 사용자가 원하는 정보를 실제로 찾는 성공률을 높인다.
3. 답변과 관련 문서를 함께 제공하여 사용자가 원문을 검증할 수 있게 한다.
4. 첫 답변 내용이 표시되는 시간을 5초 이내로 목표한다.

5초를 넘을 경우 검색을 중단하지 않고 문서 검색·선별·답변 작성 상태를 표시한다.

### 성공 기준

다음 조건을 모두 만족해야 한 질의를 성공으로 판정한다.

- 답변이 원문 의미를 왜곡하지 않는다.
- 답변이 검색된 문서에서 확인 가능한 내용만 사용한다.
- 제공된 관련 문서가 질문과 직접 관련 있다.
- 사용자가 답변과 관련 문서를 확인하고 `내가 찾던 정보를 찾았다`고 판단할 수 있다.

정보 탐색 성공률의 목표 수치는 임의로 정하지 않고 사용자 테스트 결과로 결정한다.

## 3. 이번 실험에서 이미 합의한 제품 정책

### Notion 연결 주체와 검색 범위

- Knot Workspace 소유자가 검색에 사용할 Notion 연결을 설정한다.
- 소유자가 지정한 Notion 연결 대상 문서 집합을 Knot Workspace의 공용 검색 코퍼스로 취급한다.
- Knot Workspace의 팀원은 동일한 공용 코퍼스를 검색할 수 있다.
- 개인별 Notion 권한을 매 검색마다 다시 판정하는 방식은 이번 MVP의 기준으로 삼지 않는다.
- 단, 실제 Notion API가 읽을 수 있는 범위는 연결에 공유된 페이지와 하위 페이지로 제한된다. “전체 Workspace”를 사용하려면 연결에 필요한 최상위 페이지를 실제로 공유해야 한다.
- 다른 Knot Workspace의 문서와 대화는 검색 근거로 사용하지 않는다.

### 동기화와 활성화

검색 대상은 항상 마지막으로 완전히 완료된 동기화 스냅샷이다.

| 상태 | 검색 가능 여부 | 동작 |
| --- | --- | --- |
| 최초 동기화 중 | 불가 | 전체 동기화가 끝날 때까지 AI 검색을 비활성화한다. |
| 최초 동기화 완료 | 가능 | 완료된 스냅샷을 활성화한다. |
| 재동기화 중 | 가능 | 기존의 마지막 성공 스냅샷으로 검색하고, 최신화 진행 중임을 표시한다. |
| 재동기화 성공 | 가능 | 새 스냅샷을 원자적으로 활성화한다. |
| 일반 재동기화 실패 | 가능 | 기존 성공 스냅샷을 유지하고 최신 문서가 아닐 수 있음을 표시한다. |
| 연결 해제 | 불가 | 연결·검색 인덱스를 논리적으로 비활성화하고 토큰을 폐기한다. |
| 재연결 후 전체 동기화 중 | 불가 | 새 동기화가 완료되기 전에는 기존 스냅샷도 다시 활성화하지 않는다. |
| 재연결 동기화 완료 | 가능 | 새로 완료된 스냅샷만 검색 대상으로 활성화한다. |
| 재연결 동기화 실패 | 불가 | 기존 비활성 연결을 되살리지 않고 재시도를 안내한다. |

연결 해제 시 데이터는 우선 논리적 삭제 또는 비활성화만 한다. 과거 대화는 유지할 수 있지만, 연결이 끊긴 문서의 참조는 `현재 접근 불가` 상태로 표시한다.

부분적으로 동기화된 데이터는 검색에 노출하지 않는다. 동기화 버전과 활성 스냅샷을 분리하여, 새 스냅샷 검증이 끝난 뒤 한 번에 전환한다.

### 대화 세션과 답변

- 대화 세션은 Knot Workspace와 사용자 범위에 속한다.
- 현재 선택된 세션의 질문·답변만 후속 질문의 문맥으로 사용한다.
- 관련 문서는 최대 3개까지만 제공한다.
- 관련성이 충분한 문서만 제공하며, 3개를 채우기 위해 무관한 문서를 추가하지 않는다.
- 정렬은 관련도 우선이며, 관련도가 같을 때 최신성을 고려한다.
- 문서 간 충돌은 임의로 하나를 정답으로 정하지 않고 문서별 주장과 날짜를 함께 보여준다.
- 답변을 뒷받침할 근거가 없으면 찾지 못했다고 명시한다.
- 모든 AI 답변에 `찾았어요 / 못 찾았어요` 피드백을 하나씩 연결한다.

## 4. 비교할 검색 아키텍처

이번 실험의 주 비교군은 다음 네 가지다. 네 방식 모두 동일한 채팅 모델, 시스템 프롬프트, 생성 옵션, 질문 세트를 사용한다.

### A. 원본 컨텍스트 직접 전달

내보낸 문서 전체 또는 가능한 전체 원문을 하나의 요청 컨텍스트로 구성하여 NIM에 전달한다.

장점:

- 구현이 가장 단순하다.
- 별도의 검색 품질이나 인덱스 품질에 영향을 받지 않는다.
- 작은 문서 집합에서 기준선으로 사용하기 좋다.

단점:

- 문서가 많아지면 컨텍스트 한도에 걸릴 수 있다.
- 입력 토큰과 지연 시간이 커진다.
- 개인정보·권한 범위·문서 누락을 관리하기 어렵다.
- 실서비스 기본 방식으로는 확장성이 낮을 가능성이 높다.

컨텍스트 한도를 넘는 경우 임의로 잘라서 성공한 것으로 처리하지 않는다. `원본 방식은 현재 코퍼스 규모에서 실행 불가`로 기록한다.

### B. 로컬 RAG

동기화 시 Notion 문서를 Knot 저장소로 가져오고, 문서를 정규화·분할·인덱싱한다. 질의 시 관련 청크를 검색한 뒤 검색 결과만 NIM에 전달한다.

기본 검색 방식은 벡터 검색을 포함한 하이브리드 검색을 우선 검토한다. 벡터화 방식과 저장소는 현재 확정하지 않고, 벤치마크 구현 시 실제 운영 비용과 품질을 함께 비교한다.

장점:

- 질의 시 NIM으로 보내는 컨텍스트를 줄일 수 있다.
- 응답 시작 시간이 짧고 문서 규모가 커져도 확장하기 쉽다.
- 마지막 성공 스냅샷을 기준으로 안정적으로 검색할 수 있다.
- 문서·청크·메타데이터·참조 링크를 통제할 수 있다.

단점:

- 동기화·청킹·임베딩·인덱스 갱신이 필요하다.
- 검색에서 관련 문서를 놓치면 답변 품질도 함께 떨어진다.
- 문서 삭제·충돌·페이지 계층·권한 범위를 데이터 모델로 관리해야 한다.

### C. MCP 기반 검색

NIM이 호출할 수 있는 읽기 전용 검색 도구를 Knot 백엔드가 제공한다. 도구 호출 결과를 바탕으로 NIM이 답변을 작성한다.

MCP는 접근 프로토콜이므로, MCP 도구가 로컬 벡터 DB를 조회하면 별도의 검색 방식이 아니라 `MCP 인터페이스를 사용한 RAG`로 분류한다. 이번 비교에서 C는 실시간 Notion 조회를 기준으로 한다.

장점:

- 최신 Notion 문서를 직접 조회할 수 있다.
- NIM이 필요한 문서만 단계적으로 요청할 수 있다.
- 검색 도구와 답변 생성의 책임을 분리하기 쉽다.

단점:

- 검색 도구 호출 횟수에 따라 첫 응답이 늦어질 수 있다.
- Notion API의 페이지네이션·검색 지연·실패·속도 제한 영향을 받는다.
- 모델의 도구 선택 품질과 도구 스키마 설계에 결과가 좌우된다.
- 실시간 권한과 장애 처리 경로가 복잡해진다.

보안상 Notion 토큰을 NIM에 전달하지 않는다. 모든 Notion 호출은 Knot 백엔드가 수행하고, NIM에는 필요한 문서 내용과 메타데이터만 전달한다.

### D. PostgreSQL 직접 검색

동기화된 문서 청크를 PostgreSQL에 저장하고, 벡터 유사도 계산 없이 텍스트 인덱스와 키워드 조건으로 관련 문서를 조회한다. 별도 임베딩 생성 비용이 없어 검색 지연 기준선으로 사용한다.

장점:

- 구현·운영이 단순하고 검색 요청이 빠르다.
- PostgreSQL 권한·트랜잭션·백업 경계 안에서 관리할 수 있다.
- 정확한 기술명·식별자·날짜가 문서에 그대로 있는 경우 강하다.

단점:

- 표현이 다른 자연어 질문과 동의어·맥락 검색에 약하다.
- 검색어에 없는 개념이나 문서 간 의미 연결을 놓칠 수 있다.
- 키워드 pre-filter만으로 답변 품질을 보장하지 않는다.

## 5. 벤치마크 실행 구조

```text
Notion Markdown & CSV export
          ↓
snapshot normalize + manifest
          ↓
same question set / gold labels
          ↓
┌──────────────┬──────────────┬──────────────┬──────────────────┐
│ Raw context  │ Local RAG    │ DB direct    │ MCP replay/live   │
└──────────────┴──────────────┴──────────────┴──────────────────┘
          ↓
same NIM model + same prompt/options
          ↓
TTFT / completion / source / quality report
```

### 공통 실행 조건

- 모든 비교군은 동일한 NIM 모델을 사용한다.
- 선택하는 NIM 모델은 일반 채팅과 도구 호출을 모두 지원해야 한다.
- 모델, 프롬프트, temperature, 최대 출력 토큰, timeout, retry 정책을 실행 전에 고정한다.
- 비교군별로 다른 것은 문서 검색·전달 방식뿐이어야 한다.
- 질문 순서와 반복 횟수는 실행 전에 고정하고, cold start와 warm 상태를 분리 기록한다.
- 동일한 스냅샷과 동일한 질문으로 반복 실행한다.
- NIM Trial/Hosted API는 이번 검증과 프로토타이핑 용도로만 사용한다. 운영 배포 전에 라이선스와 비용 조건을 별도로 확인한다.

## 6. 테스트 데이터 준비

### Notion 내보내기

1. Notion에서 `Markdown & CSV` 형식으로 내보낸다.
2. 하위 페이지 포함 옵션을 사용한다.
3. 페이지 본문은 Markdown으로, 데이터베이스는 CSV로 보존한다.
4. 원본 Markdown·CSV는 Git에 커밋하지 않고 로컬의 무시된 테스트 데이터 경로에 둔다.
5. 파일명만으로 페이지를 식별하지 않도록 원본 URL, 페이지 ID, 제목, 계층 경로, 생성일, 수정일을 별도 manifest로 보존한다.
6. 내보내기 파일의 내부 링크와 데이터베이스 관계가 정규화 과정에서 유지되는지 확인한다.

Markdown 내보내기는 통제된 동일 스냅샷을 만들기 위한 방법이다. 실제 Notion API의 실시간 지연·권한·페이지네이션을 재현하지 않으므로, 실시간 MCP 결과와 같은 것으로 해석하지 않는다.

### 질문 세트와 정답표

20명 이상 사용자 인터뷰에서 나온 실제 질문을 우선 사용한다. 확보된 질문 전체를 분류하고, 각 질문에 사람이 확인한 정답표를 만든다.

정답표 항목:

- 질문 원문과 질문 유형: 사실 / 결정 근거 / 문서 위치
- 핵심 답변 사실
- 정답 또는 근거가 되는 페이지
- 문서 날짜와 위치 정보
- 함께 보여도 되는 관련 문서
- 충돌하는 문서와 충돌 내용
- 답이 없어야 하는 질문 여부
- 애매하거나 범위가 넓어 명확화가 필요한 질문 여부

필수 테스트 유형:

- 직접적인 사실 질문
- `왜 그렇게 정했는지`를 묻는 결정 근거 질문
- 날짜·회의록·문서 위치를 찾는 질문
- 후속 질문: `왜 그렇게 정했는데?`, `관련된 거 더 알려줘`
- 문서 간 충돌 질문
- 문서에 없는 정보 질문
- 너무 넓은 질문
- 표현이 다른 동의어·약어·한국어/영어 혼합 질문

## 7. 단계별 실행 계획

### 0단계 — 스냅샷과 기준선 준비

- Notion Markdown & CSV 내보내기 파일을 수집한다.
- 정규화 결과와 manifest를 생성한다.
- 질문 정답표를 확정한다.
- 동일 NIM 모델의 채팅·스트리밍·도구 호출 가능 여부를 확인한다.
- 한두 개 질문으로 NIM 연결과 스트리밍 기준선을 확인한다.

산출물:

- 재현 가능한 로컬 스냅샷
- 질문·정답표 파일
- NIM 모델 및 실행 옵션 기록

### 1단계 — 통제된 동일 스냅샷 비교

내보낸 동일 스냅샷을 네 비교군에 각각 제공한다.

- A: 원본 컨텍스트 직접 전달
- B: 로컬 RAG
- C: PostgreSQL 직접 검색
- D: 동일 스냅샷을 반환하는 MCP replay 서버

MCP replay 서버를 두는 이유는 실제 Notion 네트워크 지연을 제외하고, MCP 도구 호출·모델 도구 선택·답변 생성 비용을 원본/RAG와 비교하기 위해서다.

이 단계에서 확인할 것:

- 컨텍스트 크기와 NIM 입력 한도
- 첫 답변 청크까지의 지연
- 검색 결과 누락 여부
- 관련 문서 최대 3개 선별 품질
- 충돌·무응답·명확화 처리

### 2단계 — 실제 Notion 연동 비교

Notion 연결과 백엔드 읽기 도구를 구성한 뒤 다음을 비교한다.

- B: 마지막 성공 스냅샷을 사용하는 로컬 RAG
- C: 실제 Notion을 조회하는 MCP

실제 연동 단계에서는 Notion API의 검색 지연, 페이지네이션, 하위 블록 순회, 권한 범위, 속도 제한, 네트워크 오류를 별도로 측정한다.

2026-09-01에 LM Studio `mcp/notion` plugin을 통해 `notion-search`와 `notion-fetch`를 실제 호출하는 smoke test를 완료했다. PostgreSQL 결정 근거, 후속 질문, 로드맵 회의 날짜, Redis 예시·충돌, 코드 컨벤션을 확인했으며, 넓은 질문은 잘못된 문서를 선택하는 실패도 재현했다. 이 결과는 LM Studio가 관리하는 OAuth 연결의 기능 검증이며, Java가 Workspace별 credential을 전달하는 경로의 검증이나 최종 5초 성능 판정은 아니다.

원본 직접 전달 방식은 1단계의 통제 기준선으로 유지한다. 실제 Workspace 전체를 매 요청 원본으로 전송하는 것은 운영 방식으로 바로 채택하지 않는다.

### 3단계 — 아키텍처 판정

속도만으로 결정하지 않는다. 먼저 보안·범위·근거·정확성 기준을 통과한 비교군만 후보로 남긴다. 후보 중에서 다음 우선순위로 최종 방식을 선택한다.

1. Workspace 범위 누출이 없는가
2. 답변과 관련 문서가 정답표를 만족하는가
3. 첫 답변 청크의 p50/p95와 5초 이내 비율이 우수한가
4. 동기화·장애·비용·운영 복잡도가 감당 가능한가
5. 문서 수가 늘어날 때 성능이 유지되는가

결과는 비교표와 실패 사례를 함께 남긴다. MVP 기술 선택은 하이브리드 RAG로 결정하고, 전체 사용자 대상 운영 전환 여부는 추가 검증 결과로 판정한다.

### 4단계 — 제품 MVP에 반영

판정된 방식을 제품 검색 경로에 연결한다.

- Workspace 소유자용 Notion 연결과 대상 문서 설정
- 최초 전체 동기화 진행 화면과 완료 전 검색 잠금
- 활성 스냅샷 기반 검색
- 재동기화 중 기존 스냅샷 제공
- 동기화 성공 후 새 스냅샷 원자적 활성화
- 연결 해제의 논리적 삭제와 토큰 폐기
- 재연결 후 새 전체 동기화 완료 전 재활성화 금지
- 답변 스트리밍과 문서 단위 상태 표시
- 답변·관련 문서·피드백·문서 참조 상태 저장

## 8. 측정 지표

- 평균보다 p50과 p95를 우선 기록한다.
- 5초 이내 첫 답변이 표시된 비율을 기록한다.

- 입력·출력 토큰 수와 컨텍스트 크기
- MCP 도구 호출 횟수와 각 호출 시간
- Notion API 요청 수, 페이지네이션 횟수, 재시도 횟수
- 동기화 전체 시간과 인덱싱 시간
- timeout, 429, 인증 오류, 네트워크 오류, 모델 오류 비율
- cold start와 warm 상태의 차이

## 10. 구현 시 제안하는 경계

현재 백엔드의 채팅 스트리밍 구조를 확장하되, 벤치마크 전략과 제품 기본 검색 경로를 먼저 분리한다.

개념적 구성:

- `SnapshotLoader`: 내보내기 스냅샷과 manifest 로드
- `DocumentNormalizer`: Markdown·CSV·페이지 계층·메타데이터 정규화
- `RawContextStrategy`: 원본 컨텍스트 실험군
- `RagStrategy`: 로컬 청크·벡터/하이브리드 검색 실험군
- `McpReplayStrategy`: 동일 스냅샷 replay 실험군
- `McpNotionStrategy`: 실제 Notion 읽기 실험군
- `NimAnswerGenerator`: 공통 NIM 채팅·스트리밍 생성기
- `BenchmarkRunner`: 동일 질문·옵션·반복 조건 실행
- `BenchmarkReport`: 지연·토큰·오류·품질 평가 결과 출력

제품 데이터는 다음 개념을 기준으로 설계한다.

- Notion 연결과 연결 상태
- 동기화 실행 및 동기화 상태
- 완료된 스냅샷과 현재 활성 스냅샷
- 페이지 원문·메타데이터·계층 정보
- 청크·임베딩·검색 메타데이터
- 답변과 관련 문서 참조

검색 쿼리에는 항상 `Knot Workspace ID`와 `active snapshot ID`를 포함한다. 임베딩 검색 결과를 받았더라도 이 범위를 통과하지 못한 문서는 답변 컨텍스트에 넣지 않는다.

현재 채팅의 LLM 추상화와 SSE 스트리밍은 NIM 어댑터의 연결 지점으로 활용한다. 제품 검색 상태는 내부 기술 용어 대신 다음과 같은 문서 단위 표현으로 노출한다.

- 관련 문서를 찾고 있어요
- 관련 문서 후보를 선별하고 있어요
- 답변을 정리하고 있어요

## 11. 보안·운영 주의사항

- Notion access token은 Knot 백엔드에만 보관하고 NIM 요청에 넣지 않는다.
- 외부 NIM으로 보내는 데이터는 연결된 대상 문서 범위 안에서만 구성한다.
- 내보낸 원문과 벤치마크 결과에 토큰·비밀번호·불필요한 개인정보를 넣지 않는다.
- 내보내기 데이터는 Git에 추가하지 않는다.
- 연결 해제 시 검색 경로에서는 즉시 제외하고, 논리 삭제 데이터는 복구·감사 목적에 한해 보관 여부를 별도로 결정한다.
- NIM Hosted Trial은 테스트·프로토타이핑 용도이며, 운영 배포 전에 약관·크레딧·라이선스·비용을 확인한다.
- Notion 검색 API는 전체 페이지 열거를 보장하지 않을 수 있으므로, 전체 동기화는 연결된 루트 페이지와 하위 블록을 페이지네이션하여 수집하는 방식으로 검증한다.

## 16. 2026-09-01 LM Studio/Notion MCP-live smoke test

- LM Studio `0.4.16`의 native `/api/v1/chat`에서 `qwen/qwen3.6-27b`와 `mcp/notion` plugin을 사용했다.
- LM Studio가 실제 `notion-search`와 `notion-fetch`를 호출하고, PostgreSQL 결정 근거를 `01. 기술 스택과 라이브러리 도입` 문서에서 생성하는 것을 확인했다.
- 후속 질문은 이전 응답 ID를 사용해 PostgreSQL 문맥을 유지했지만, 추가 MCP 검색과 reasoning으로 약 190초가 걸렸다.
- 로드맵 날짜·Redis의 예시/공식 결정 부재·구체화한 코드 컨벤션 질의는 동작했지만, 넓은 코드 컨벤션 질의는 관련도가 낮은 백엔드 문서를 선택했다.
- 관측된 live 요청의 end-to-end 완료 시간은 약 38~77초였고, 후속 질문은 약 190초였다. 따라서 현재 5초 목표를 충족한다고 판정하지 않는다.
- 이 smoke test는 LM Studio-managed OAuth 연결이며, 실제 Workspace별 Java credential forwarding·권한 격리·전체 A/B 비교는 후속 검증으로 남긴다.

## 17. 2026-09-02 #274 MCP live adapter 구현 상태

- Streamable HTTP MCP initialize·initialized·tools/call handshake와 JSON/SSE 응답 파싱을 benchmark 경계에 추가했다.

- NIM tool call은 notion-search와 notion-fetch의 읽기 전용 인자만 검증하며, Notion credential은 MCP endpoint에만 보내고 모델 컨텍스트에는 보내지 않는다.
- live benchmark는 MCP HTTP 요청 수, fetch page 수, retry 수, 429 rate-limit 수, access 지연, 모델 TTFT·완료 시간, E2E 지연을 분리 기록한다.
- 인증 거부·JSON-RPC 오류·페이지 범위 이탈·페이지네이션·rate limit 경계 테스트를 추가했다.
- 현재 live benchmark 실행기는 실제 OAuth token과 연결 Workspace allowlist를 환경변수로 받아야 한다. 저장소에는 token이나 live 결과를 기록하지 않으며, Java credential forwarding과 30개 이상 사람 품질 검수는 #275의 후속 게이트다.

## 18. 2026-09-02 #275 품질 게이트 구현 상태

- 독립 질문 workload를 기존 13개 대화형 골드셋과 분리해 31개 case·33개 turn으로 추가했다.
- benchmark runner가 JSON workload를 기존 BenchmarkCase 입력으로 읽을 수 있게 했다.
- 자동 gate는 검색 결과의 source·중복·오류·무응답·광범위 질문을 검사하고, 등록되지 않은 답변 형식은 자동 성공/실패로 단정하지 않는다.
- 사람 검수는 answer_correct, sources_relevant, policy_compliant 세 축을 모두 채운 terminal label만 허용하며, 누락·중복·pending이 있으면 통과하지 않는다.
- 현재 사람 검수 파일은 템플릿만 제공하고 실제 생성 결과에 대한 라벨은 비어 있다. 따라서 #275의 품질 통과와 최종 아키텍처 판정은 아직 완료로 표시하지 않는다.
- 실제 NIM e2e 결과, 실제 Notion MCP-live 결과, Java Workspace credential forwarding, cold/warm 반복 조건을 모두 동일 실행 ID로 채운 뒤 사람 검수를 수행한다.

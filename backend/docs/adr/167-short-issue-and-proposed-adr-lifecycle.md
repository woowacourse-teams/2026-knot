# 짧은 Issue와 코드 리뷰 기반 ADR 생명주기

## 상태

Proposed

## 관련 Issue

- #167 [BE] 팀 공통 Issue / ADR 기획 하네스 도입
- #218 [BE] Issue 기획 하네스 원격 게시 지원

## 한 줄 요약

GitHub Issue는 기존 세 섹션으로 짧게 유지하고, 중요한 결정만 구현 브랜치에서
`Proposed` ADR로 생성해 코드와 함께 리뷰한다.

## 왜 이 결정이 필요했나

기존 하네스는 구현 범위, 실패·복구 흐름과 ADR 전문을 Issue에 모두 출력했다. 내부
검증에는 유용했지만 팀의 기존 Issue보다 훨씬 길어 작업 내용을 빠르게 파악하기 어려웠다.

팀은 `구현 기능 설명`, `TODO`, `메모`로 이루어진 기존 템플릿을 유지하면서도, 실제
상황과 선택 근거가 대화에서 사라지지 않기를 원한다. Codex와 Claude Code가 같은 규칙과
검증기를 사용해야 한다는 제약도 있다.

초기 하네스는 안전을 위해 모든 생성 요청을 dry-run으로 제한했다. 그러나 사용자가 실제
Issue 생성을 명시적으로 요청해도 별도 수작업이 필요했고, 게시 재시도 시 같은 계약을
중복 생성하지 않는 복구 기준도 없었다.

동시에 #165가 `frontend/`의 구현·리뷰 하네스를 추가하고 있어, 저장소 공통 Issue 기획
계약과 프론트엔드 구현 규칙의 책임 범위를 분리해야 한다.

## 결정 동인

- Issue에서 문제와 해야 할 일을 빠르게 파악할 수 있어야 한다.
- 중요한 결정의 실제 대안, 선택 이유와 재논의 조건은 장기간 남아야 한다.
- AI가 팀이 논의하지 않은 대안을 만들어 결정 근거를 보강해서는 안 된다.
- 이미 명시된 결정 근거를 확인하기 위한 형식적인 인터뷰를 반복해서는 안 된다.
- 결정과 구현은 같은 PR에서 함께 검토할 수 있어야 한다.
- Codex와 Claude Code의 결과가 도구별 프롬프트 차이로 갈라지지 않아야 한다.
- 프론트엔드 전용 구현 지침과 저장소 공통 Issue 계약이 서로 덮어쓰지 않아야 한다.
- 기본 실행은 원격을 변경하지 않아야 하며, 현재 요청의 명시적 승인만 게시 권한이 돼야 한다.
- 게시 재시도와 부분 실패가 같은 Issue에서 안전하게 복구돼야 한다.

## 무엇을 결정했나

- Issue 본문은 `구현 기능 설명`, `TODO`, `메모` 세 섹션만 사용한다.
- 중요한 결정이 있으면 `구현 기능 설명`에 구체적인 문제 상황과 목표를 1~2문장으로
  적고, `메모`에는 결정 한 줄과 예정 ADR 경로만 적는다.
- ADR은 현실적인 대안이 둘 이상이고, 결정이 장기간 영향을 주며, 후속 작업에서 반복
  참조할 때만 작성한다.
- AI는 현재 맥락, 구체적인 상황, 결정 필요성, 실제 대안, 최종 선택과 선택 이유의
  출처를 먼저 확인한다. 자료가 누락·충돌했거나 현재 유효성이 불명확할 때만 해당 판단을
  묻는다. 대안이 없으면 한 번 확인한 뒤 ADR을 만들지 않는다.
- 구현을 시작하면 AI가 현재 작업 브랜치에 `backend/docs/adr/<Issue 번호>-<slug>.md`를
  `Proposed`로 생성한다. 새 Issue 기획 중에는 slug와 번호 placeholder만 표시하고, 실제
  Issue 번호가 정해진 뒤 경로를 확정한다. 이 파일은 코드와 같은 PR에 포함한다.
- 팀이 PR에서 승인한 뒤에만 ADR을 `Accepted`로 바꾼다. AI는 자동 merge하지 않는다.
- Codex와 Claude Code는 같은 Python 검증기와 정책 문서를 사용하고, 각 도구의 프로젝트
  지침은 이 정본을 가리키는 어댑터로 유지한다.
- 기본 실행은 항상 dry-run으로 유지한다. 현재 사용자가 실제 생성을 명시했고 계약이
  통과했으며 `--publish --repo OWNER/REPO`가 함께 주어진 경우에만 GitHub에 쓴다.
- 게시 전 `contract_id` 표식으로 모든 상태의 Issue를 검색한다. 하나면 재사용하고, 둘
  이상이면 추가 생성 없이 중복 해소를 요구한다.
- ADR이 필요한 새 Issue는 생성 직후 실제 번호로 예정 경로를 확정한다. 이때
  `gh issue edit`는 방금 생성하거나 재사용한 동일 Issue의 본문 갱신에만 사용한다.
- 검색·생성·본문 갱신 실패는 승인 여부와 성공 여부를 구분해 보고한다. 생성 뒤 실패하면
  실제 Issue 번호와 URL을 보존해 재개할 수 있게 한다.
- Issue 게시 권한에는 GitHub Project 변경, branch, commit, push, PR 또는 merge가 포함되지
  않는다.
- #167은 루트의 공통 Issue·ADR 계약을, #165는 `frontend/`의 구현·리뷰 규칙을 담당한다.

## 결과

- 내부 snapshot은 범위, 실패·복구, 완료 조건과 검증 근거를 계속 보존한다.
- 고위험 인터뷰를 생략하면 여섯 결정 정보의 내용과 출처를 snapshot에 남기고 사용자에게
  생략 사실을 알린다.
- GitHub Issue는 팀이 익숙한 길이와 형태를 유지한다.
- ADR이 필요 없는 Issue에는 상황 설명이나 ADR 판단 문구를 억지로 추가하지 않는다.
- 구현 세션이 기획 세션의 결정 snapshot을 복구하지 못하면 AI는 대안을 추측할 수 없고,
  빠진 결정 정보만 다시 확인해야 한다.
- 새 Issue 번호가 정해지기 전에는 ADR 파일을 만들 수 없으며, 구현 단계에서 실제 번호를
  전달해야 한다.
- 명시적으로 승인된 생성 요청은 검증 결과와 같은 계약 표식을 가진 GitHub Issue로
  이어지고, 같은 snapshot을 재실행해도 기존 Issue를 재사용한다.
- GitHub 검색 색인이 늦으면 중복 가능성이 남는다. 둘 이상의 정확한 계약 표식이 발견되면
  하네스는 정본을 임의로 선택하지 않고 `hold`한다.
- 같은 정책을 바꾸려면 공통 문서와 검증기를 먼저 수정하고 Codex·Claude 어댑터의
  정합성을 함께 검증해야 한다.
- 프론트엔드 Issue 기획에는 공통 계약을 먼저 적용하고 구현에는 `frontend/` 지침을
  추가로 적용한다.

## 다시 논의해야 할 조건

- 구현 시작 시 결정 snapshot을 이어 받지 못해 같은 질문을 반복하는 일이 잦다.
- 한 줄 ADR 메모만으로 관련 결정을 찾기 어렵다.
- Issue가 다시 길어지거나 구현자가 필요한 계약을 반복해서 놓친다.
- 팀이 ADR 전용 PR이나 Issue 생성 시점의 `Proposed` 파일을 선호한다.
- Codex와 Claude Code가 같은 입력에서 반복적으로 다른 판정을 낸다.
- 근거가 누락·충돌했거나 오래됐는데도 인터뷰를 생략하는 사례가 반복된다.
- 계약 표식 검색이 GitHub 색인 지연이나 API 변경 때문에 안정적인 멱등성을 제공하지 못한다.
- 팀이 Issue 생성과 GitHub Project 연결을 하나의 승인 단위로 자동화하기로 결정한다.

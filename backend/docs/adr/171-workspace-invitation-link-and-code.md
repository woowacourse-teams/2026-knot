# 워크스페이스 초대에 링크와 코드를 함께 제공한다

## 상태

Proposed

## 관련 Issue

- #171 [BE] 워크스페이스 초대 도메인 및 저장 구조 구현

## 한 줄 요약

워크스페이스 초대는 하나의 초대에서 24시간 동안 유효한 링크와 코드를 함께 제공하고, 재발급하면 기존 초대를 무효화한다.

## 왜 이 결정이 필요했나

공유 링크를 바로 열어 참여하는 사용자와 Slack 같은 외부 앱에서 코드만 복사해 Knot 안에서 입력하는 사용자를 모두 지원해야 한다. 두 진입 방식이 서로 다른 초대 생명주기를 가지면 만료와 재발급 상태가 어긋날 수 있으므로 하나의 초대로 관리할 필요가 있다.

## 트레이드 오프

| 선택지 | 장점 | 단점 | 채택 여부 |
| --- | --- | --- | --- |
| 링크만 제공 | 클릭만으로 참여할 수 있어 흐름이 단순하다. | 링크를 열기 어려운 환경에서 앱 안의 참여 경로를 제공하지 못한다. | 미채택 |
| 코드만 제공 | 외부 앱에서 짧은 값을 복사해 입력할 수 있다. | 링크를 통한 즉시 참여 흐름을 제공하지 못한다. | 미채택 |
| 링크와 코드를 하나의 초대로 함께 제공 | 두 사용자 흐름을 지원하고 만료·무효화 생명주기를 공유한다. | 두 식별자를 생성하고 안전하게 검증해야 한다. | 채택 |

## 무엇을 결정했나

- 하나의 Workspace Invitation이 링크 토큰과 초대 코드를 함께 가진다.
- 두 값은 발급 후 24시간 동안 함께 유효하다.
- 재발급할 때 기존 Invitation을 먼저 무효화하고 새 Invitation을 만든다.
- 원문 링크 토큰과 코드는 저장하지 않고 각각의 해시만 저장한다.
- Sprint 3에서는 초대 사용 횟수를 제한하지 않는다.
- 현재 채택된 PostgreSQL 저장 기준과 Issue #171 범위에는 발급자 식별자가 없으므로
  `createdByMemberId`는 이번 테이블에 추가하지 않는다. 후속 발급 API는 발급 시점에
  Workspace 구성원 여부를 검증하고, 발급자 이력 저장이 필요해지면 ERD 합의 후 새
  migration으로 추가한다.

## 결과

- 링크와 코드 참여가 같은 만료·무효화 판단을 사용한다.
- 원문이 데이터베이스에 남지 않지만, 발급 시점에는 사용자에게 원문을 한 번 전달해야 한다.
- 만료됐더라도 무효화되지 않은 초대는 새 초대를 만들기 전에 명시적으로 무효화해야 한다.
- 초대 발급·재발급과 참여 유스케이스는 후속 Issue에서 이 저장 계약을 사용한다.
- 도메인 명세에 있는 발급자 식별자와 현재 PostgreSQL 저장 기준의 차이는 남아 있으며,
  발급자 감사 이력이 필요해지면 팀 합의가 필요하다.

## 다시 논의해야 할 조건

- 링크와 코드의 만료 시간을 서로 다르게 운영해야 한다.
- 초대 사용 횟수 제한이나 일회용 초대가 필요하다.
- 초대 발급 이력에 발급자 식별자를 영속해야 한다.
- 원문 전달 또는 해시 검증 방식이 보안 요구를 충족하지 못한다.

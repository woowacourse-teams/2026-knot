# 요구사항 문장이 바뀌는 작업은 기능 요구사항 검토 DB에 제안하고 기획 컨펌 담당의 확정 기록이 생긴 뒤에만 정본과 이슈를 만든다

## 상태

Proposed

## 관련 Issue

- #1002 [FE] 기획 변경은 기능 요구사항 검토와 1차 컨펌을 거치게 하고 담당자, 승인 규칙을 knot-feature에 반영한다

## 한 줄 요약

요구사항 문장이 바뀌는 작업은 기능 요구사항 검토 DB에 제안하고 기획 컨펌 담당의 확정 기록이 생긴 뒤에만 정본과 이슈를 만든다

## 왜 이 결정이 필요했나

10/22 ADR #909, #958로 도메인 팀이 기획을 정하고 유월은 PR에서만 컨펌했다. 하네스는 기능 요구사항 업데이트부터 시작해 컨펌 지점이 없었다

10/25 주말 한 팀원이 하네스로 새 기능을 끝까지 돌려 기능 요구사항 7개, QA 행 11개, 이슈(#982)를 만든 뒤에 컨펌을 요청했다. 같은 주말 #979는 담당자가 실제 작업자와 달랐고 FE PR이 BE 승인만으로 머지됐다

결정 동인:

- 확정 전 내용을 다른 팀원 에이전트가 구현 근거로 읽지 않을 것
- 반려 시 되돌릴 것이 없을 것
- 기획 컨펌 담당의 병목을 키우지 않을 것
- 컨펌 근거가 사람의 말이 아니라 확인 가능한 기록일 것

## 트레이드 오프

- 정본에 바로 쓰고 컨펌받기(#982 방식): 빠르지만 확정 전 내용이 정본과 BE 동기화 캐시로 들어가고 반려 시 되돌릴 곳이 많다
- 검토 DB에 제안하고 1차 컨펌 뒤 정본 반영: 한 단계 늘지만 정본에는 확정된 것만 남는다
- 개발 중 작은 조정은 1차 컨펌 없이 PR로만 확인: 병목은 줄지만 작은 조정과 기획 변경의 경계가 모호하다

## 무엇을 결정했나

요구사항 문장이 바뀌는 작업은 기능 요구사항 검토 DB에 제안하고 기획 컨펌 담당의 확정 기록이 생긴 뒤에만 정본과 이슈를 만든다

회의에서 경계가 모호한 갈래를 두는 것보다 모든 문장 변경을 초안으로 먼저 확인받는 편이 빠르다는 의견이 많았다. 검토 DB는 정본과 분리돼 확정 전 내용을 에이전트가 읽지 않고, 확정 기록으로 하네스가 컨펌을 검사할 수 있다

## 결과

- 정본에는 확정된 것만 남는다
- 값 하나 바꾸는 일도 제안을 거쳐 기획 컨펌 담당의 확인이 늘어난다
- ADR #958의 기획서 수정 권한은 기능 추가, 수정, 삭제에 딸린 경우 1차 컨펌 뒤로 좁혀진다

## 다시 논의해야 할 조건

- 1차 컨펌 대기가 개발을 자주 막을 때
- 기획 컨펌 담당이 늘거나 바뀔 때
- 노션 자동화로 확정 즉시 하네스를 실행할 수 있게 될 때

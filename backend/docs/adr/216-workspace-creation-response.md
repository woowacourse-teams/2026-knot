# Workspace 생성은 생성된 ID만 반환하고 초대 코드 발급과 조회는 별도 API와 Issue로 분리한다.

## 상태

Proposed

## 관련 Issue

- #216 [BE] 워크스페이스 생성 API 구현

## 한 줄 요약

Workspace 생성은 생성된 ID만 반환하고 초대 코드 발급과 조회는 별도 API와 Issue로 분리한다.

## 왜 이 결정이 필요했나

Workspace 생성 직후 프론트엔드는 후속 초대 화면으로 이동해야 하며 회의 문서에는 생성 응답에 초대 코드까지 포함하는 안과 ID만 반환하는 안이 함께 남아 있었다.

팀은 초대 코드를 생성 응답에 함께 반환해 호출 수를 줄이는 방법과 생성 ID로 URL을 구성한 뒤 초대 정보를 별도로 조회하는 방법을 논의했다.

결정 동인:

- 프론트엔드가 새로고침 후에도 URL의 Workspace ID로 상태를 복원할 수 있어야 한다.
- Workspace 생성의 원자적 범위를 Workspace와 OWNER 멤버십에 한정한다.
- 24시간 만료와 재발급을 가진 초대 수명주기를 생성 계약과 독립적으로 변경할 수 있어야 한다.

## 트레이드 오프

- 생성 응답에 초대 코드를 포함한다: 추가 호출은 줄지만 Workspace 생성과 초대 발급의 실패 및 변경 범위가 결합된다.
- 생성 응답에는 ID만 포함하고 초대 정보를 별도 API로 다룬다: 후속 호출은 필요하지만 생성과 초대의 책임 및 수명주기를 분리할 수 있다.

## 무엇을 결정했나

Workspace 생성은 생성된 ID만 반환하고 초대 코드 발급과 조회는 별도 API와 Issue로 분리한다.

생성된 ID만으로 후속 URL 상태를 안정적으로 구성할 수 있으므로 초대 책임까지 생성 응답에 결합할 필요가 없다.

## 결과

- POST /workspaces는 201 Created와 ID만 반환한다.
- 초대 화면은 Workspace ID를 사용해 별도 초대 API를 호출해야 한다.
- 초대 발급 조회 참여의 실패와 만료 정책은 Workspace 생성 transaction에 포함되지 않는다.

## 다시 논의해야 할 조건

- 제품 흐름이 Workspace 생성과 초대 발급을 반드시 하나의 원자적 작업으로 요구할 때
- 초대 정보의 별도 조회가 사용자 경험이나 성능 목표를 충족하지 못한다는 측정 근거가 생길 때

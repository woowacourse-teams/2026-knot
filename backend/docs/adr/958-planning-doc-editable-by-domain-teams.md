# 기획서(V2)도 도메인 팀이 knot-feature 흐름 안에서 고치고, 기존 요구사항과 충돌하는 변경은 멈춰 영향받는 도메인 팀이 결정한다

## 상태

Proposed

## 관련 Issue

- #958 [FE] knot-feature 하네스에서 팀원이 기획서를 고칠 수 있게 바꾸기

## 한 줄 요약

기획서(V2)도 도메인 팀이 knot-feature 흐름 안에서 고치고, 기존 요구사항과 충돌하는 변경은 멈춰 영향받는 도메인 팀이 결정한다

## 왜 이 결정이 필요했나

2026-10-22 knot-feature 도입 때 기획서는 읽기 전용 참조 문서로 두고 변경은 유월 승인으로 묶었다. 같은 날 도메인 팀이 자기 도메인의 기획과 디자인 권한을 갖기로 했다

2026-10-25 팀원이 기능을 기획하다 기획서까지 바꿔야 하면 하네스가 거부하고 노션 페이지도 편집이 막혀 있어, 유월을 기다리지 않고는 진행할 수 없다는 문제가 제기됐다

결정 동인:

- 도메인 팀이 기획부터 개발까지 독립적으로 끝낼 수 있는가
- 다른 도메인에 닿는 기획서 변경이 드러나는가
- 잘못된 변경을 되돌릴 수 있는가

## 트레이드 오프

- 현행 유지: 기획서는 읽기 전용, 유월 승인 뒤 유월이 고친다. 기준 문서가 안정적이지만 기획서 변경마다 흐름이 유월에게서 멈춘다
- 도메인 팀이 흐름 안에서 고친다: 팀이 독립적으로 진행하지만 다른 도메인에 닿는 변경을 충돌 브리핑과 PR 컨펌으로 잡아야 한다

## 무엇을 결정했나

기획서(V2)도 도메인 팀이 knot-feature 흐름 안에서 고치고, 기존 요구사항과 충돌하는 변경은 멈춰 영향받는 도메인 팀이 결정한다

기능 요구사항, 도메인 규칙, API 명세에는 이미 충돌 브리핑과 노션 변경 사항으로 도메인 팀 권한을 줬고 기획서만 예외로 남아 흐름이 멈췄다. 같은 장치를 기획서에도 적용하면 사전 승인 없이도 변경이 PR 컨펌에서 드러난다

## 결과

- 기획서 변경이 필요한 기능도 유월 승인 없이 끝까지 간다
- 유월은 기획서 변경을 사전 승인이 아니라 최종 PR 컨펌에서 본다
- 다른 도메인에 닿는 변경은 충돌 브리핑에 의존하므로 브리핑 품질이 중요해진다

## 다시 논의해야 할 조건

- 한 팀의 기획서 변경이 다른 팀 구현과 어긋난 사례가 나올 때
- 기획서가 자주 바뀌어 기준 문서로서 신뢰가 떨어질 때

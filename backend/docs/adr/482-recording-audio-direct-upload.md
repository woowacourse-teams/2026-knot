# 녹음 최종 오디오는 FE가 Presigned URL로 객체 저장소에 직접 업로드하고 백엔드는 URL 발급과 완료 확인만 한다

## 상태

Proposed

## 관련 Issue

- #482 [BE] 최종 오디오 업로드 URL 발급 API 구현

## 한 줄 요약

녹음 최종 오디오는 FE가 Presigned URL로 객체 저장소에 직접 업로드하고 백엔드는 URL 발급과 완료 확인만 한다

## 왜 이 결정이 필요했나

녹음은 최대 2시간이며 스프린트 목표는 종료 후 최종 오디오 업로드까지다. 개발 서버는 NCP 단일 서버이고 운영 저장소 위치는 미확정이다.

업로드 API 구현 직전 사용자가 프론트 직접 업로드로 진행해도 되는지, 백엔드가 받아서 올리는 편이 나은지 확인했다.

결정 동인:

- 큰 파일이 백엔드 서버를 거치지 않을 것
- 저장소 접근 키를 클라이언트에 노출하지 않을 것
- 저장소 공급자를 설정으로 바꿀 수 있을 것

## 트레이드 오프

- FE 직접 업로드(채택): 서버 부하·크기 제한·재전송 부담이 없지만 URL 발급·완료 확인·CORS·미완료 파일 정리가 필요하다
- 백엔드 중계 업로드: FE가 단순하지만 2시간 파일이 Nginx·Spring을 통과해 요청 크기·타임아웃·임시 디스크 조정이 필요하고 재시도 시 큰 파일을 다시 보낸다

## 무엇을 결정했나

녹음 최종 오디오는 FE가 Presigned URL로 객체 저장소에 직접 업로드하고 백엔드는 URL 발급과 완료 확인만 한다

녹음 파일 크기와 단일 개발 서버를 고려하면 서버를 거치지 않는 직접 업로드가 안정적이고, 접근 키는 서버가 서명한 일회성 URL로만 위임한다.

## 결과

- 백엔드는 업로드 예약·URL 발급·완료 확인 API를 제공한다
- FE는 서명 조건과 같은 Content-Type·Content-Length로 PUT해야 한다
- 버킷 CORS와 미완료 객체 수명주기 규칙이 필요하다
- AWS SDK v2 S3 모듈을 도입한다

## 다시 논의해야 할 조건

- 업로드 실패율이 높아 서버 중계 fallback이 필요할 때
- 조각 업로드나 실시간 업로드가 필요할 때

# 초대 참여는 하나의 인증 경로에서 멱등하게 처리한다

## 상태

Proposed

## 관련 Issue

- #244 [BE] 초대 코드·링크로 워크스페이스 참여 API 구현

## 한 줄 요약

인증된 사용자는 `POST /api/v1/invitations/accept`에 코드 또는 링크 credential을 전달해 참여하며,
신규 멤버십은 `201`, 기존 멤버십은 변경 없이 `200`으로 응답한다.

## 왜 이 결정이 필요했나

프론트엔드는 같은 초대 화면에서 6자리 코드와 링크를 제공한다. 참여 API를 코드와 링크로
나누면 사용자가 입력한 credential 종류에 따라 클라이언트가 경로를 선택해야 하고, 두
경로의 보안·멱등·오류 계약이 어긋날 수 있다.

또한 참여 요청은 로그인과 재시도, 초대 재발급, 동일 사용자의 동시 요청과 겹칠 수 있다.
응답 유실 뒤 재시도한 사용자를 오류로 처리하거나, 재발급으로 무효화된 credential이
경쟁 상태에서 수락되면 사용자 경험과 초대 생명주기가 일관되지 않는다.

결정 동인:

- 코드와 링크 참여를 같은 FE-BE 계약으로 처리해야 한다.
- 참여는 인증된 사용자에게만 허용하고 기존 CSRF 방어를 그대로 적용해야 한다.
- 응답 유실과 중복 요청이 멤버십 중복이나 오류로 이어지지 않아야 한다.
- 재발급과 참여가 겹쳐도 무효화된 credential로 멤버십이 커밋되면 안 된다.
- 6자리 코드의 탐색 위험은 미리보기와 참여를 합산해 제한해야 한다.

## 트레이드 오프

| 선택지 | 장점 | 단점 | 채택 여부 |
| --- | --- | --- | --- |
| 코드와 링크 참여 경로를 분리 | 입력 종류별 동작이 URL에 드러난다. | FE 분기가 늘고 보안·오류·멱등 계약이 중복된다. | 미채택 |
| 코드와 링크를 하나의 참여 경로에서 처리 | 참여 진입점과 응답 계약이 하나로 유지된다. | 서버가 credential 종류를 분류해야 한다. | 채택 |
| 워크스페이스 하위 URL 사용 | 참여 뒤 대상 리소스를 URL에서 알 수 있다. | 참여 전에는 사용자가 workspace ID를 알지 못한다. | 미채택 |
| 초대 리소스 URL 사용 | 사용자가 가진 credential만으로 참여할 수 있다. | 참여 결과의 workspace ID는 응답으로 알려야 한다. | 채택 |
| 중복 참여를 충돌로 처리 | 새 멤버십 생성 여부가 엄격히 드러난다. | 응답 유실 뒤 재시도가 실패하고 FE 복구가 복잡해진다. | 미채택 |
| 중복 참여를 멱등 성공으로 처리 | 재시도와 동시 요청이 같은 멤버십으로 수렴한다. | `200`과 `201` 두 성공 상태를 문서화해야 한다. | 채택 |
| 로그인 전 참여 상태를 서버에 보관 | 로그인 뒤 자동으로 참여를 이어갈 수 있다. | 임시 상태와 callback 흐름이 추가된다. | 미채택 |
| 인증·CSRF를 갖춘 요청에서 바로 참여 | 기존 보안 경계를 재사용하고 서버 상태가 늘지 않는다. | 로그인 전 credential은 클라이언트가 다시 제출해야 한다. | 채택 |

## 무엇을 결정했나

- 참여 API는 인증과 CSRF 검증이 필요한 `POST /api/v1/invitations/accept`로 제공한다.
- 요청 본문은 `credential` 하나만 받고 코드와 링크 토큰을 같은 분류 규칙으로 처리한다.
- 6자리 코드는 대문자로 정규화하고, 다른 nonblank 입력은 대소문자를 구분하는 링크
  토큰 원문으로 검증한다.
- 코드 참여는 미리보기와 같은 remote address별 1분 30회 제한을 공유하며 링크 참여는
  이 제한을 소비하지 않는다.
- 초대의 hash, 만료, 무효화 여부를 멤버십 처리 전에 검증하고 실패 원인은 같은 `404`로
  응답한다.
- 신규 멤버십을 만들면 `201`, 이미 OWNER 또는 MEMBER이면 역할을 바꾸지 않고 `200`을
  반환한다. 두 응답 본문은 workspace ID와 이름만 포함한다.
- 초대 참여와 재발급은 같은 Workspace row lock 순서를 사용한다. 잠금 뒤 초대를 다시
  조회하고 검증해, 경쟁 결과를 유효한 참여 성공 또는 통합 `404` 중 하나로 선형화한다.
- 동일 Workspace의 참여 요청은 직렬화하고 기존 멤버십 유일 제약을 최종 방어로 둔다.
- 참여 응답은 상태 코드와 관계없이 캐시하지 않고 원문 credential을 로그에 남기지 않는다.

## 결과

- FE는 credential 종류를 구분하지 않고 하나의 참여 요청만 보낸다.
- 같은 사용자의 재시도와 동시 요청은 하나의 멤버십으로 수렴한다.
- 서로 다른 사용자는 같은 유효한 초대를 반복해서 사용할 수 있다.
- 초대 재발급과 참여가 겹쳐도 무효화된 credential을 기준으로 멤버십이 커밋되지 않는다.
- Workspace row lock 때문에 같은 Workspace의 동시 참여는 직렬화된다. MVP에서는 일관성을
  우선하며, 참여량이 커지면 잠금 경합을 다시 측정해야 한다.
- 코드 제한은 JVM 메모리 기반이므로 서버 재시작과 다중 인스턴스 전체의 전역 제한을
  보장하지 않는다.

## 다시 논의해야 할 조건

- 로그인 전 credential을 서버에 보관해 로그인 뒤 자동 참여를 이어가야 할 때
- 워크스페이스별 동시 참여량 때문에 row lock 경합이 운영 병목이 될 때
- 다중 인스턴스에서 코드 미리보기와 참여의 전역 호출 제한이 필요할 때
- 일회용 초대, 사용 횟수 제한 또는 참여 감사 이력이 필요할 때
- 멤버십 상태나 역할 정책이 추가되어 기존 멤버의 참여 결과가 달라질 때

# 피드백은 프론트 Worker가 Notion 「사용자 피드백 접수함」에 바로 넣고, PostHog 이벤트는 저장 성공 뒤에만 보낸다

## 상태

Proposed

## 관련 Issue

- #930 [FE] 피드백 보내기 기능 구현

## 한 줄 요약

피드백은 프론트 Worker가 Notion 「사용자 피드백 접수함」에 바로 넣고, PostHog 이벤트는 저장 성공 뒤에만 보낸다

## 왜 이 결정이 필요했나

Notion 10/21 기준은 BE 없이 PostHog 설문 API 방식으로만 피드백을 받는다. 프론트는 Cloudflare Worker로 PostHog와 Sentry 요청을 중계하고 있다(ADR 838)

Notion 기준은 PostHog 이벤트로만 피드백을 받는데, PostHog는 전송 결과를 알려 주지 않아 피드백이 빠져도 사용자와 팀 모두 모른다.

결정 동인:

- 피드백이 팀에 도착했는지 확실히 알 수 있는가
- R8 실패 표시가 실제 결과를 따르는가
- BE 없이 지금 팀이 할 수 있는가
- 토큰과 공개 경로 관리 부담

## 트레이드 오프

- A. PostHog로만 받기: 코드가 가장 적고 Notion 기준 그대로지만, 탭을 닫거나 차단되면 피드백이 빠지고 실패를 알 수 없다
- B. 프론트 Worker로 Notion 접수함에 넣기: 저장 결과로 성공과 실패를 알고 팀 접수함에 바로 들어오지만, 토큰 관리와 공개 경로 악용 방지가 필요하고 Notion 기준을 바꾼다
- C. PostHog 웹훅에서 n8n을 거쳐 Notion에 넣기: 앱 코드는 PostHog만 쓰지만, 빠지는 문제가 그대로 남고 n8n 설정과 관리가 늘어난다

## 무엇을 결정했나

피드백은 프론트 Worker가 Notion 「사용자 피드백 접수함」에 바로 넣고, PostHog 이벤트는 저장 성공 뒤에만 보낸다

저장 응답으로 성공과 실패를 확실히 알 수 있고, 팀이 이미 쓰는 접수함으로 바로 들어오며, 기존 Worker 중계 구조에 경로 하나만 더하면 된다

## 결과

- 긍정: 피드백이 접수함에 들어갔는지 사용자와 팀이 안다
- 긍정: BE 변경 없이 기존 Worker 구조를 쓴다
- 부정: Notion 토큰을 Worker 비밀값으로 관리해야 한다
- 부정: /relay/f는 누구나 부를 수 있어 스크립트 스팸을 막지 못한다
- 부정: 접수함 열 이름이 바뀌면 저장이 실패한다

## 다시 논의해야 할 조건

- 접수함에 스팸 줄이 들어오기 시작할 때
- Notion API 거절로 보내기 실패가 자주 보고될 때
- BE에 피드백 저장을 만들 여유가 생길 때

# 기존 SQL 불변성과 정확한 환경/JAR 쌍의 한시 검토 승인을 배포 조건으로 삼고 Dev Worker 형식 변경은 점검 중 순차 교체한다.

## 상태

Proposed

## 관련 Issue

- #989 [BE] Blue-Green 마이그레이션 검토 승인과 Dev 순차 Worker 교체

## 한 줄 요약

기존 SQL 불변성과 정확한 환경/JAR 쌍의 한시 검토 승인을 배포 조건으로 삼고 Dev Worker 형식 변경은 점검 중 순차 교체한다.

## 왜 이 결정이 필요했나

Dev와 Prod는 Blue-Green을 쓰지만 SQL 파일 추가를 일괄 차단하던 검사로 정상 빌드가 반복 롤백됐다.

2026-10-25 Dev V62~69 및 Prod V62~66 후보를 실제 활성 V61 JAR와 비교했다. Dev V69 전사 작업 형식 변경 때문에 동시 Worker 호환성을 따로 처리해야 했다.

결정 동인:

- 기존 SQL 불변
- 구버전 롤백 호환성
- Worker 작업 형식 충돌 방지
- 운영 승인 범위 제한
- Prod 관측 검사 유지

## 트레이드 오프

- SQL 추가 일괄 차단: 검토 누락을 막지만 호환되는 확장도 반복 롤백된다.
- 검토한 확장만 정확한 JAR 쌍으로 허용: 운영 검토 비용이 있지만 승인 범위를 제한하며 배포 가능하다.
- Dev 구·신 Worker 동시 실행: 점검은 줄지만 새 2분 전사 형식을 구 Worker가 처리할 위험이 있다.
- Dev 점검 후 순차 교체: 잠시 503이 발생하지만 구·신 Worker 중복을 방지한다.

## 무엇을 결정했나

기존 SQL 불변성과 정확한 환경/JAR 쌍의 한시 검토 승인을 배포 조건으로 삼고 Dev Worker 형식 변경은 점검 중 순차 교체한다.

사용자는 안전 검사 유지와 Dev만 점검 중 순차 교체를 선택했다. Prod는 형식 충돌 조건이 없어 기존 rolling을 유지한다.

## 결과

- 추가 SQL마다 운영 검토와 만료 승인 파일이 필요하다.
- 기존 SQL 수정·삭제는 승인으로 우회할 수 없다.
- Dev 순차 교체 시 짧은 점검이 발생한다.
- 배포 실패가 적용된 DB 확장을 되돌리지는 않는다.

## 다시 논의해야 할 조건

- 비호환 컬럼 삭제/형식 변경 필요 시 expand-contract 분리 검토
- 구·신 Worker 작업 형식이 공존 가능해지면 점검 방식 재검토
- 자동화된 신뢰 가능한 호환 검증을 도입할 때

# 문서 탭 주제별 목록은 폴더 틀을 유지한 채 폴더 안의 행만 라이브러리 없이 가상화합니다.

## 상태

Proposed

## 관련 Issue

- #1117 [FE] 문서 탭 주제별 목록 가상화

## 한 줄 요약

문서 탭 주제별 목록은 폴더 틀을 유지한 채 폴더 안의 행만 라이브러리 없이 가상화합니다.

## 왜 이 결정이 필요했나

문서를 모두 받아 폴더별로 묶어 보여주는 화면이고, 카드 모양과 section, ul, li 구조를 유지해야 합니다. 세션 녹화 비용이 DOM을 붙이는 작업에 비례해서 그리는 행 수를 줄여야 합니다.

문서가 1,939개인 워크스페이스에서 문서 탭 「주제별」을 누르면 행을 모두 그려서, CPU 4배 느림 기준 화면이 보일 때까지 로컬 898\~966ms, 운영 1,530\~1,631ms가 걸립니다. 다시 받기가 끝나면 내용이 같아도 컴포넌트 37,168개가 다시 렌더링됩니다.

결정 동인:

- DOM, React 렌더링, 세션 녹화 비용을 함께 줄이는가
- 폴더 카드 구조와 의미 있는 목록 구조를 유지하는가
- 뒤로 가기, 창 크기 변화, 빠른 스크롤을 풀 수 있는가

## 트레이드 오프

- content-visibility: CSS만 고치면 되지만 DOM과 React 렌더링, 세션 녹화 기록이 줄지 않고 CPU 4배 느림에서 716\~892ms입니다.
- 직접 구현: 원리를 확인하고 의존성이 늘지 않지만 뒤로 가기와 포커스를 직접 풀어야 합니다.
- TanStack Virtual: 측정과 구간 계산을 맡길 수 있지만 폴더 틀을 유지하면 폴더마다 훅과 scrollMargin이 필요합니다.
- react-window: 바깥 틀을 List가 그려서 폴더 카드 구조와 맞지 않습니다.
- 한 줄로 펴기: 폴더 수가 크게 늘어도 빠르지만 카드 모양과 section, ul 구조를 다시 만들어야 합니다.

## 무엇을 결정했나

문서 탭 주제별 목록은 폴더 틀을 유지한 채 폴더 안의 행만 라이브러리 없이 가상화합니다.

행 30개 상한선이 44\~51ms로 그리는 행 수가 비용을 정한다는 분석과 맞습니다. 폴더 틀은 요소 140개(전체의 0.8%)만 늘어서 구조를 지키는 쪽을 골랐고, 라이브러리 없이 구현해 원리를 확인한 뒤 부족할 때만 의존성을 더합니다.

## 결과

- 탭 진입과 다시 받기의 렌더링 비용이 줄어듭니다.
- 화면 밖 문서는 Cmd+F로 찾지 못합니다.
- 폴더마다 보이는 구간을 구하므로 폴더 수만큼 계산과 측정이 늘어납니다.
- 행 높이가 바뀌는 디자인 변경은 높이 계산도 함께 고쳐야 합니다.

## 다시 논의해야 할 조건

- 뒤로 가기, 창 크기 변화, 빠른 스크롤 빈 칸 가운데 2026-11-16까지 풀지 못한 문제가 있으면 TanStack Virtual을 적용합니다.
- 사용자 경험 피드백의 원인이 폴더 틀이거나 폴더 수가 크게 늘어 폴더 틀이 느려지면 한 줄로 펴기를 검토합니다.
- 캘린더 탭이 같은 목록을 쓰면 공용 코드로 내릴지 정합니다.

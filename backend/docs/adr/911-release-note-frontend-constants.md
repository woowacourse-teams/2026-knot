# 새 소식 노트는 서버나 노션이 아니라 프론트 상수 파일 한 곳에 두고 릴리즈 직전 기획자가 써서 배포와 함께 낸다

## 상태

Proposed

## 관련 Issue

- #911 [FE] 새 소식 패널에 릴리즈 노트 내용 보여 주기

## 한 줄 요약

새 소식 노트는 서버나 노션이 아니라 프론트 상수 파일 한 곳에 두고 릴리즈 직전 기획자가 써서 배포와 함께 낸다

## 왜 이 결정이 필요했나

매일 23시에 배포하지만 사용자는 무엇이 바뀌었는지 알 수 없다. 새 소식에서는 서버 저장, BE API, 노션 연동, 관리자 화면을 만들지 않기로 했다(새 소식 (공통) 하지 않는 것).

2026-10-19 첫 배포 후 회의에서 무엇이 개선됐는지 볼 수 있는 릴리즈 노트를 요청받았다. 새 소식 패널에 보여 줄 노트를 어디에 두고 누가 언제 쓸지 정해야 한다.

결정 동인:

- BE API 없이 프론트 배포만으로 낼 수 있는가
- 브라우저에 노션 토큰을 두지 않는가
- 같은 파일 충돌과 문구 품질
- 릴리즈 PR CI(NEWS-R9)가 빠뜨림을 확인할 수 있는가
- 제보한 문제가 고쳐졌다는 소식이 늦지 않은가

## 트레이드 오프

- 프론트 상수 파일에 릴리즈 직전 기획자가 쓰기(채택): 배포와 함께 나가고 CI로 확인할 수 있지만 문구를 고치려면 배포가 필요하다
- PR마다 작성자가 쓰기: 기억이 생생할 때 쓰지만 BE 팀원까지 사용자 문구를 써야 하고 같은 파일 맨 위에서 충돌이 잦으며 문구 품질이 들쭉날쭉하다
- 서버나 노션에서 받아 오기: 배포 없이 문구를 고칠 수 있지만 브라우저에 노션 토큰을 둘 수 없어 BE API가 필요하다
- 매 배포마다 또는 주 1회 묶어 내기: 매번 내면 점이 소음이 되고 주 1회면 제보한 문제가 고쳐졌다는 소식이 늦다

## 무엇을 결정했나

새 소식 노트는 서버나 노션이 아니라 프론트 상수 파일 한 곳에 두고 릴리즈 직전 기획자가 써서 배포와 함께 낸다

BE API와 노션 토큰 없이 노트가 배포와 함께 나가고, 릴리즈 PR CI가 맨 위 노트 id로 빠뜨림을 막을 수 있다. 나중에 서버로 옮겨도 지금 데이터 모양을 API 응답으로 그대로 쓸 수 있다.

## 결과

- 좋은 점: BE 작업 없이 노트가 배포와 함께 나간다
- 좋은 점: 노트 id와 순서를 단위 테스트와 릴리즈 PR CI가 확인할 수 있다
- 나쁜 점: 문구를 고치려면 프론트 배포가 필요하다
- 나쁜 점: 기획자가 릴리즈마다 develop으로 가는 새 소식 PR을 먼저 머지해야 한다

## 다시 논의해야 할 조건

- 배포 없이 문구를 고쳐야 할 때
- 사용자마다 다른 소식을 보여 줘야 할 때
- 릴리즈 주기나 노트를 쓰는 사람이 바뀔 때

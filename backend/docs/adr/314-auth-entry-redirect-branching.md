# 로그인 이후 진입 목적지 분기는 프론트엔드 홈 경로가 담당하고 백엔드는 고정 리다이렉트 주소만 설정한다

## 상태

Proposed

## 관련 Issue

- #314 [FE] 로그인 상태 기반 진입 분기와 라우트 가드

## 한 줄 요약

로그인 이후 진입 목적지 분기는 프론트엔드 홈 경로가 담당하고 백엔드는 고정 리다이렉트 주소만 설정한다

## 왜 이 결정이 필요했나

GitHub OAuth 로그인은 백엔드가 sendRedirect로 브라우저를 이동시키므로, 목적지를 백엔드 설정 문자열로 정한다. 그런데 로그인 이후 도착해야 할 화면은 닉네임 설정 여부와 워크스페이스 보유 여부에 따라 갈린다.

닉네임까지 마친 기존 회원이 dev 환경에서 다시 GitHub 로그인하면 백엔드 기본값인 상대 경로 /api/v1/auth/me로 이동해 API 도메인의 JSON 응답이 그대로 화면에 보인다. 프론트 자바스크립트는 API 도메인에서 실행되지 않으므로 이 이동에 개입할 수 없다.

결정 동인:

- 리다이렉트 설정은 고정 문자열 하나라 회원 상태별 분기를 표현할 수 없다
- 백엔드 환경변수는 운영과 개발 서버가 공유하는 설정이라 개수가 늘수록 서버별 관리 비용이 커진다
- 분기 판단에 필요한 상태 조회 API는 이미 배포되어 프론트가 호출할 수 있다
- 진입 규칙은 제품 정책이라 화면 요구사항이 바뀔 때 함께 바뀐다
- 인증 쿠키가 httpOnly라 프론트는 서버에 묻지 않고는 회원 상태를 알 수 없다

## 트레이드 오프

- 백엔드가 회원 상태를 판단해 목적지별로 다른 주소로 리다이렉트한다: 프론트가 추가 조회 없이 곧바로 도착하지만, 백엔드가 워크스페이스 보유 여부까지 알아야 하고 목적지가 늘 때마다 환경변수와 백엔드 코드를 함께 고쳐야 한다
- 백엔드는 고정 주소로만 보내고 프론트가 새 콜백 경로에서 분기한다: 분기 책임이 한곳에 모이지만 다른 목적이 없는 경로가 라우터에 하나 늘어난다
- 백엔드는 성공과 닉네임을 모두 온보딩 화면으로 보내고 프론트가 그 화면에서 분기한다: 경로가 늘지 않지만 쿠키가 httpOnly라 신규 가입자도 상태 조회를 기다린 뒤에 닉네임 카드를 보게 되고 온보딩 화면의 역할이 흐려진다
- 백엔드는 고정 주소로만 보내고 프론트가 기존 홈 경로에서 분기한다: 경로가 늘지 않고 신규 가입자 경로도 그대로이며, 로그인 사용자가 도메인 주소만 입력했을 때 필요한 판단과 같은 로직을 공유한다

## 무엇을 결정했나

로그인 이후 진입 목적지 분기는 프론트엔드 홈 경로가 담당하고 백엔드는 고정 리다이렉트 주소만 설정한다

진입 규칙은 화면 구성이 바뀔 때마다 함께 바뀌는 제품 정책이고, 그때마다 백엔드 배포와 서버별 환경변수를 고치는 비용이 프론트에서 조회 한 번을 더 하는 비용보다 크다. 분기 자리를 홈 경로로 두면 로그인한 사용자가 도메인 주소만 입력했을 때 필요한 판단과 같은 로직을 쓰게 되어 경로도 늘지 않고 신규 가입자의 온보딩 도착 속도도 그대로 유지된다.

## 결과

- 진입 규칙이 바뀌어도 프론트 코드만 고치면 되고 백엔드 배포가 필요 없다
- 백엔드가 설정할 값이 성공, 닉네임, 실패 세 개로 고정된다
- 홈 경로가 화면이 아니라 판정과 이동을 맡게 되어 짧은 로딩 화면이 필요하다
- 홈 경로가 프론트 라우터의 공개 계약이 되어 백엔드 설정과 함께 관리해야 한다
- 신규 가입자는 백엔드가 온보딩으로 바로 보내므로 추가 조회 없이 닉네임 카드를 본다

## 다시 논의해야 할 조건

- 진입 직후 로딩 지연이 사용자 경험 문제로 보고될 때
- 백엔드가 로그인 응답에 워크스페이스 보유 여부를 함께 내려주게 될 때
- 초대 링크처럼 로그인 이후 목적지가 외부에서 지정되는 흐름이 추가될 때
- 홈 경로에 실제로 보여줄 화면이 생겨 판정 역할과 충돌할 때

# 기능 결과처럼 오류가 아닌 신뢰성 숫자는 Sentry 지표로 세고, Sentry Issue는 고칠 수 있는 결함만 남긴다

## 상태

Proposed

## 관련 Issue

- #915 [FE] Sentry로 녹음 결과를 지표로 세고 업로드 실패 보고 기준 맞추기

## 한 줄 요약

기능 결과처럼 오류가 아닌 신뢰성 숫자는 Sentry 지표로 세고, Sentry Issue는 고칠 수 있는 결함만 남긴다

## 왜 이 결정이 필요했나

FE는 Sentry로 오류를 보고하고 PostHog로 사용 기록을 남긴다. PostHog는 다른 팀원이 관리한다

2026-10-22 녹음 중 연결이 끊겨 서버가 녹음을 끝냈지만 정상 응답이라 Sentry에 남지 않았고, 녹음 완주율을 FE 담당자가 볼 곳이 없었다

결정 동인:

- FE 담당자가 직접 보고 운영할 수 있는 곳
- 고칠 수 없는 Issue로 알림이 쌓이지 않을 것
- 개인정보를 남기지 않을 것

## 트레이드 오프

- PostHog 이벤트: 이미 recording_ended가 있고 사용자 단위 퍼널이 되지만 FE 담당자가 관리하지 않는다
- Sentry Issue(captureMessage): 리플레이가 붙지만 사용자 네트워크 탓의 끊김이 고칠 수 없는 Issue로 쌓인다
- Sentry 지표: Issue와 분리돼 비율과 사유 분포를 보지만 사용자 단위 퍼널은 어렵다

## 무엇을 결정했나

기능 결과처럼 오류가 아닌 신뢰성 숫자는 Sentry 지표로 세고, Sentry Issue는 고칠 수 있는 결함만 남긴다

FE 담당자가 직접 운영하는 Sentry 안에서 결함(Issue)과 결과(지표)를 나눠, 알림은 고칠 수 있는 것만 받고 비율은 지표로 본다

함께 정한 것:

- 끊긴 동안의 오류를 IndexedDB에 보관했다가 다시 연결되면 보내는 전송(오프라인 보관 전송)은 쓰지 않는다. 끊긴 동안의 network 오류는 보고 기준이 일부러 거르고, 알고 싶은 것은 끊긴 순간의 오류가 아니라 회복한 뒤 서버가 알려 주는 결과이기 때문이다
- 사용자가 적은 동안 성능 측정은 표본을 덜어 내지 않고 모든 환경에서 모두 측정한다. 운영 20%로는 화면별 p75를 낼 표본이 모이지 않는다. ADR 838의 「운영은 20%」를 바꾸며, Sentry Stats에서 운영 span이 할당량에 가까워지면 운영만 다시 낮춘다

## 결과

- 녹음 완주율과 실패 사유를 Sentry에서 본다
- 사용자 단위 퍼널은 PostHog에 남는다
- 지표 이름과 속성은 한 번 정하면 바꾸지 않는다
- 성능 측정 이벤트와 Cloudflare Worker 중계 요청이 늘어난다

## 다시 논의해야 할 조건

- PostHog 관리 주체가 FE로 바뀔 때
- Sentry 요금제나 지표 기능 조건이 바뀔 때

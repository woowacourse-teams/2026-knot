운영 정책이나 API·스키마를 바꾸는 계획이 아니다. 제품 원문이나 열린 PR을 새 근거로 도입하지 않았으며 현재 소스·기존 산출물·해당 호스트의 과거 전원 기록을 사용했다.

다른 5회 실행 구간에서는 같은 조회의 Sleep·DarkWake·Wake 항목이 발견되지 않았다. 다른 실행의 최대 힙 표본 간격은 약 2.096초 이하였고, 자원 표본 간격은 약 13.426초 이하였다.

따라서 **호스트 절전의 개입은 확인된 사실**이다. 유지보수 절전의 복귀 시각과 JVM 관측 재개 시각도 맞는다. DarkWake 구간을 정상적인 전경 실행과 동등한 상태로 취급하지 않는다.

다만 OS 기록의 5초·35초, 힙 공백 34.515초, 외부 수집 간격 45.444초는 겹치는 구간이다. 서로 더하거나 243.766초에서 빼서 보정 성능을 만들지 않는다. 약 83초 증가분 전체를 이 기록만으로 배분할 수도 없다.

### 2.3 지연 위치를 더 분해한 결과

| 관측 항목 | 변경 후 1회 | 변경 후 2회 | 변경 후 3회 |
| --- | ---: | ---: | ---: |
| Snapshot 클래스 Duration | 2.303초 | 2.270초 | **24.959초** |
| 같은 컨텍스트 MISS→STORE | 2.194초 | 2.134초 | **24.358초** |
| 해당 PostgreSQL 시작 로그의 시간 | 0.897초 | 1.087초 | **14.126초** |
| 해당 Flyway SQL 실행 보고값 | 0.132초 | 0.088초 | 0.948초 |

| 해당 컨텍스트 MISS→STORE | 1.730초 | 1.744초 | 4.877초 |

Snapshot 클래스는 주로 준비 구간이 길어졌다. DB 컨테이너 준비도 크게 느려졌으며, Flyway가 보고한 migration SQL 실행 시간만으로 24초 대부분을 설명하지는 못한다. 위 시간들은 포함 관계가 있어 단순 합산하지 않는다. Flyway 연결·검증 등 준비 비용 전체가 SQL 실행 보고값에 포함된다고 가정하지 않는다.

Transaction 클래스에서는 HTML 경로를 통해 `departure_failure_rollsBackMembership(true)`의 Duration이 **33.038초**였음을 확인했다. 같은 사례는 앞선 변경 후 두 실행에서 각각 0.028초·0.040초였다.

이 메서드는 일반 탈퇴·OWNER 승계 중 보관 처리 실패를 주입하고 같은 트랜잭션의 롤백을 검증한다. 해당 메서드 본문에는 명시적인 sleep·latch·future 대기가 없다. 같은 클래스의 별도 동시성 테스트와 혼동하지 않는다.

해당 사례의 보존된 표준 출력은 12:49:28.249~12:49:28.780, 약 **0.531초 범위**다. 이것은 메서드 시작·종료를 직접 측정한 시간이 아니므로 리포트 오류를 확정하는 근거도 아니다. 그러나 Duration 33.038초를 그 메서드의 SQL 대기 33초라고 해석해서는 안 된다. 다음 실험에서는 리포트 시각과 실제 단계 경계를 함께 기록해야 한다.

## 3. 다음 실험의 흐름과 관측 코드 제안

**첫 실험 대상은 코드 변경 전후가 아니라, 동일한 변경 후 후보의 전체 통합 테스트 3회다.** 호스트가 계속 깨어 있는 조건에서 지연이 다시 발생하는지 먼저 확인한다.

```text
동일 후보 소스·runtime 고정
→ 전원·덮개·백그라운드 작업 조건 기록
→ 명령 범위의 idle sleep 방지
→ 전체 통합 649개를 독립 JVM으로 3회 순차 실행
→ OS 전원 기록·두 관측 채널·클래스/단계 시간 대조
→ 환경 개입 여부와 잔여 지연을 분리해 판정
```

| 기존 위치·책임 | 다음 실험에서 제안하는 보완 |
| --- | --- |
| `document-persistence-context-20261016/experiment.py`의 `run()` | 기존 고정 runtime·리포트 분리·실제 classpath·649개 목록 검증을 재사용. 새 실험 경로에 3회의 실행 정보를 보존 |
| 재측정 runner의 명령 시간 측정 | 시작·종료의 wall clock과 monotonic 시각을 함께 기록. 임의로 절전 시간을 차감하지 않음 |
| `CacheProbe.sampleMemory()`·`line()` | 기존 힙·컨텍스트 이벤트를 유지하고 시각 대조에 필요한 값을 추가할지 검토. 관측 잠금 대기를 실제 애플리케이션 정지로 단정하지 않음 |
| `measure.sample_resources()` | 가벼운 외부 heartbeat를 느린 Docker 조회와 분리. ps·Docker 호출 각각의 시작·종료·timeout을 기록해 수집기 대기를 구분 |
| Gradle/JUnit 관측 설정 | 테스트 시작·종료와 준비 단계의 경계를 읽기 전용 listener로 기록. 제품·테스트 본문에 sleep·재시도를 추가하지 않음 |
| OS 상태 기록 | 실행 구간의 Sleep·DarkWake·Wake와 전원 상태를 별도 보존 |

위 항목은 제안이며 이번 요청에서는 관측 코드도 구현하지 않았다. 생산 코드·기존 assertion·테스트 격리 방식을 바꾸지 않는다. 소스의 각 private 구간을 세밀하게 바꾸기 전에 기존 이벤트와 listener 경계로 충분한지 확인한다.

## 4. 환경·저장 기반과 유지 조건

- 덮개를 연 상태와 안정된 전원 연결을 유지한다. 로컬 `caffeinate -i`로 실험 명령 실행 동안 idle sleep을 방지하는 방식을 우선한다. `-i`가 덮개 닫힘 절전까지 막는다고 가정하지 않으며, 실제 전원 기록으로 유효성을 확인한다.
- 다른 QA 실행·대규모 빌드와 겹치지 않는 시간대를 사용한다. 공유 컨테이너를 임의로 중지하지 않고 실행 중인 작업을 기록한다.
- 스케줄러 수정, 개선안 5 import 구성, PostgreSQL 이미지·Flyway, 캐시 크기8·힙1GiB를 유지한다.
- 컴파일은 사전에 끝내고 측정 중에는 기존 4개 준비 작업의 `UP-TO-DATE`를 확인한다. Gradle daemon·의존성·Docker 이미지 캐시 조건도 그대로 기록한다.
- JPA 대상 74개의 기존 rollback과 7테이블 경계 관측을 유지한다. 스케줄러를 끄거나 완료 한도·동시성 검증을 완화하지 않는다.
- DB 모델·migration 변경은 필요 없다. 테스트용 컨테이너·관측 파일만 새 경로로 분리하며 기존 6회 자료를 덮어쓰지 않는다.

## 5. 실험과 검증 순서

이번 과제는 원인 분리이므로 제품의 실패 테스트를 새로 만드는 TDD부터 시작하지 않는다. 관측 보완을 실제 구현할 때는 다음 검증을 먼저 수행한다.

### 1단계: 관측 자료의 구분 능력 확인

작은 수집기 검증으로 heartbeat와 Docker 조회가 분리됐는지, 명령 timeout과 자료 누락을 성공으로 처리하지 않는지 확인한다. 실제 호스트 절전을 일부러 유발해 제품 테스트를 깨뜨리지는 않는다. 리포터 Duration과 본문 시간을 혼동하지 않도록 단계 경계·시계 종류를 기록한다.

### 2단계: 절전 없는 동일 후보 전체 3회

측정 전 3회라는 횟수와 환경 유효성 기준을 고정한다. 별도 전체 테스트 워밍업을 추가한다면 준비 실행으로 미리 표시하고 모든 준비 결과도 보존한다. 느린 결과가 나온 뒤 워밍업으로 재분류하지 않는다.

| 검증 | 관측과 판정 |
| --- | --- |
| 실제 전체 실행 | 새 XML, 기존649개 목록·순서, 실패·오류·스킵, 스케줄러 결과 |
| 환경 유효성 | 실행 구간의 Sleep·DarkWake·Wake 개입 유무. 개입 시 환경 오염 표본으로 표시하되 원본과 시간은 보존 |
| 초기화 | 같은 후보의 컨텍스트39·PostgreSQL47·Flyway117회 여부와 변동 이유 |
| 격리 | 대상74개 활성 트랜잭션·rollback, 전·후 7테이블 행 수0 |
| 긴 표본 공백 | JVM·외부 heartbeat 공백과 수집 명령 자체의 지연을 구분 |
| 클래스 시간 | Snapshot의 준비 구간, Transaction의 준비·테스트 경계, 리포터 Duration을 대조 |

추가 진단을 시작할 기준은 미리 **정상 주기 대비 5초를 넘는 heartbeat 간격 또는 한 클래스 10초 초과**로 정한다. 이는 관측을 더 할 기준이며 표본을 제외하는 기준이 아니다. 환경이 정상인 느린 실행·GC·DB 대기는 성능 결과에 그대로 포함한다.

예정한 3회 중 환경 오염이나 실패가 발생하면 개수와 원인을 그대로 보고한다. 성공할 때까지 대체하지 않는다. 3회 안에 환경 정상 표본을 확보하지 못하면 코드 성능 결론을 확정하지 않는다.

### 3단계: 남은 현상에 따라 한 가지 진단만 추가

| 절전 통제 후 남은 현상 | 다음에 확보할 근거 |
| --- | --- |
| JVM heartbeat만 긴 공백, 외부 heartbeat는 정상 | GC·safepoint 로그, 필요 시 JFR·스레드 상태. 수집 도구의 synchronized 대기도 확인 |
| JVM·외부 heartbeat가 함께 지연, OS 절전 없음 | 호스트 CPU·메모리 압박·swap·다른 작업 및 Docker 상태의 같은 시각 기록 |
| heartbeat는 정상, DB 준비만 지연 | 컨테이너 생성→ready, DB 연결, Flyway validation·SQL 실행의 단계별 시간 |
| heartbeat는 정상, 테스트 본문이 지연 | 해당 DB의 `pg_stat_activity`·`pg_locks`·`pg_blocking_pids()`와 query 시작·종료, 해당 JVM 스레드 상태 |
| 본문 경계는 짧은데 리포터만 크게 측정 | wall/monotonic·Gradle/JUnit 시각 대조. 리포터 오류를 먼저 가정하지 않음 |

추가 관측은 별도 진단 실행으로 보존하고 첫 3회와 성능 표본을 섞지 않는다. 원인이 좁혀지지 않았는데 힙·캐시·풀 크기·timeout을 동시에 바꾸지 않는다. 재현되지 않으면 절전 없는 조건에서 미재현이라고 기록하며 영구 해결이라고 주장하지 않는다.

## 6. 완료 기준과 후속 판단

1. 절전 없는 조건의 예정3회 결과와 모든 실패·환경 오염 표본을 보존한다.
2. 긴 시간의 위치가 초기화·테스트 구간·전체 JVM·외부 수집·호스트 중 어디인지 구분하거나, 현재 관측으로 구분할 수 없는 이유를 명시한다.
3. 기존649개 검증과 대상74개 격리·스케줄러 동작을 유지한다.
4. 준비 시간·테스트 Duration·Gradle 명령 시간을 혼합하거나 포함 관계의 시간을 합산하지 않는다.
5. 실험 결과는 이 계획과 별도 문서로 작성한다.

**개선안 5의 채택 보류는 유지한다.** 다만 기존243초 표본은 호스트 절전이 확인됐으므로 import 정렬이 성능을 악화시켰다는 근거로 단정하지 않는다. 원래 전후3회 표와 평균·중앙값을 삭제하거나 243초에서 절전 시간을 빼서 수정하지 않는다.

첫 진단3회는 동일 후보의 환경 영향 확인이며 개선안 5의 전후 성능 비교가 아니다. 이후 환경·관측 조건이 안정되면 같은 스케줄러 수정과 같은 관측 설정을 양쪽에 적용해 전후 각3회의 새 비교를 계획한다. 실행 순서는 전→후 / 후→전 / 전→후의 3쌍처럼 사전에 고정하고, 진단 실행과 섞지 않는다. 이 후속 비교를 이번 요청에서 실행하지 않았다.

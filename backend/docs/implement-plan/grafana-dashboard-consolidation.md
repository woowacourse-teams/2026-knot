# Grafana 환경별 서비스 현황·요청 로그 통합

## 1. 범위와 브랜치

2026-10-15 사용자 승인. 현재 `be/feature/#672`에서 관측 설정만 변경한다. 새 Issue·커밋·원격 게시·Notion 작성은 요청 범위가 아니다. 활성 화면은 Knot-dev·Knot-prod 각각 서비스 현황과 로그·요청 추적, 총 4개다.

근거: 기존 `build-environment-dashboards.mjs`는 12개 환경별 화면을 생성한다. 카탈로그 추가 화면은 외부 원본을 요구한다. 알림 15개는 공통 대시보드 UID·패널 ID를 참조하며 Discord 템플릿은 환경별 overview/logs UID를 사용한다. 사용자 Grafana 캡처에서 Dev 요청 ID 한 건의 Nginx·Spring 두 로그를 확인했다. 이 세션의 실제 Grafana 접근은 정책으로 거부되어 운영 현재 목록·수정·화면 검증은 미확인이다.

## 2. 구현할 흐름

환경 폴더 → 서비스 현황의 health·수집·자원·요청/오류/p95 → 필요한 상세 행 펼치기 → 같은 시간의 로그 화면 → 요청 ID 붙여넣기 → Nginx·앱 로그 시간순 대조.

검색하지 않은 빈 요청 ID는 전체 로그로 확대하지 않는다. 최근 로그는 별도 패널에서 제공한다. Prod는 기존 prototype 로그를 사용하며 Spring과 요청 ID가 연결된다고 가정하지 않는다.

## 3. 나올 코드와 메서드 초안

기존 생성기는 원본 지표·쿼리·설명을 재사용한다. 새 `build-consolidated-dashboards.mjs`의 `buildConsolidatedDashboards`는 4개 활성 화면을 반환하고 `buildConsolidationBundle`은 겹치지 않는 보관용 UID와 대체 provisioning 설정을 반환한다. 기존 기본 provisioning은 운영 사전 대조 전에는 바꾸지 않는다.

상태 화면은 핵심만 펼치고 API 상세·서버·RDS·Dev JVM/연결 풀을 접힌 행으로 둔다. 로그 화면은 textbox 요청 ID 검색과 최근 앱·요청·5xx 패널을 제공한다. 요청 ID는 Loki 인덱스 라벨이 아니라 조회 시 추출 필드다.

## 4. 저장 기반과 주의할 점

DB·앱·수집기·알림 조건·정책·Webhook 변경은 없다. 기존 overview/logs UID와 해당 패널 ID는 유지한다. 나머지 기존 UID·패널은 보관용 폴더로 이동할 번들에 남겨 과거 알림 링크를 보존한다. 운영에서 추가된 카탈로그 등은 export를 받아 합쳐야 하며 알려지지 않은 자산을 삭제하지 않는다. 기존 배포 스크립트는 이 새 번들에 사용하지 않는다.

## 5. TDD와 검증 순서

1. 4개 화면·환경 고정·요청 ID 검색·중복 UID/ID·기존 알림/패널 연결 보존을 실패 테스트로 작성한다.
2. 생성기와 대체 provisioning 번들을 최소 구현한다. 로컬 생성 JSON은 테스트 결과와 일치해야 한다.
3. 기존 observability 계약 테스트와 새 테스트를 수행한다. 가능하면 운영과 분리된 로컬 Grafana·Loki에서 JSON 로드·쿼리·빈 ID/잘못된 ID를 확인한다. 모의 로그 검증은 운영 관측과 구분한다.

## 6. 완료 기준과 다음 작업

로컬 완료: 4개 활성 화면 생성, 요청 ID 안전한 문자열 보간, 같은 환경 로그만 조회, 기존 알림 대상 UID·패널 존재, 기존 알림 리소스 불변. 운영 완료: 실제 목록 export·백업 후 적용, 두 환경 폴더 각 2개·과거 링크·요청 ID 로그를 실제 화면에서 확인한다. 접근 차단 중에는 운영 완료라고 보고하지 않는다.

# #522 주제별 Markdown 작성 실제 관찰 · 2026-10-08

최종 요청의 합성 7개 응답은 당시 제품 `DocumentGenerator`(현재 `LlmDocumentGenerator`)와 `DocumentMarkdownValidator`를 재사용한 로컬 검사에서 모두 형식 검증을 통과했다. 의미 대조는 짧은 사례 6개 통과, 장문 1개 부분 충족으로 판정했다. 모델의 모든 입력에 대한 의미 정확성이나 최적 설정을 보장하지 않는다.

## 관찰 방법과 증거 구분

- 실제 호출: HTTPS `/v1/chat/completions`, 모델 alias `qwen3.8-27b`, 순차 요청. 비공개 회의 원문·운영 키는 기록하지 않았다.
- 실행 중 Java HTTP Client를 서버에 직접 연결한 E2E가 아니라, 제품 리소스·schema를 읽고 동일 payload로 호출한 수동 공급자 관찰이다. 생성 응답은 Java 25에서 실제 제품 Generator에 재입력해 JSON/Markdown을 검증했다. 일회성 실행 코드는 저장소에 포함하지 않았다.
- 자동 검증: Mockito 단위 테스트, 실제 로컬 HTTP 서버 통합 테스트, Spring Bean 활성/비활성·리소스 누락 테스트다. 실제 모델 품질 증거와 구분한다.
- 현재 GPU 사용·메모리·로드 컨텍스트는 이번 관찰에서 새로 측정하지 않았다. 과거 32768 설정을 서버 관측값으로 재확정하지 않는다. 동시 처리량·2시간 실제 회의·출력 4096 한계까지의 장문 생성도 미검증이다.

## 최종 요청 · 2026-10-08 당시 관측

| 항목 | 값 |
|---|---|
| temperature / top_p / top_k / repeat_penalty | 0.2 / 0.9 / 20 / 1.0 |
| reasoning / enable_thinking | off / false |
| reasoning_budget | 전송하지 않음 |
| max_tokens / stream | 4096 / false |
| 출력 | title·summary·content만 required, summary string 또는 null, 추가 필드 금지 |
| system | 작성 규칙 + Markdown 템플릿 직접 포함 |
| user | transcriptText 전체 + topic 하나의 JSON |

system 요청 문자열 SHA-256: `cbe136c1374dd4fd2316d01489d547ed0eb81d85108408c2b8a1777271989e54`.
예비 비교에서 켬/512 요청도 reasoning_tokens=0, reasoning_content 길이 0이었다. 서버가 512 예산을 적용했다고 확인할 수 없어서 기본 요청은 off로 정리했다. 켬/끔 한 쌍만으로 성능 우열을 판정하지 않았다. [공식 Chat Completions 문서](https://lmstudio.ai/docs/developer/openai-compat/chat-completions)의 지원 항목에도 이 경로의 reasoning_budget 보장은 명시돼 있지 않다.

2026-10-09 공통 client의 선택 예산 필드를 실제 HTTP 예산 실험의 `thinking_budget_tokens`로 정정했다. 위 당시 관측값은 바꾸지 않는다. 수정된 요청을 실제 모델에 재실행하지 않았으며, 기본 off 요청은 예산 필드를 전송하지 않는다.

## 예비 실패와 프롬프트 개선

- 구체적 출력 예시 전 조건부 개발 사례: 켬 요청 9.806초는 보류를 결정으로 분류했고, 끔 요청 13.433초는 결정과 보류에 중복했다. 둘 다 추론 토큰 0이었다.
- 조건부 보류·미결정·수락한 작업의 JSON 예시를 추가한 후, 조건부 검색 개발은 보류로 분리됐다.
- 수정안에 넣을 표현을 정한 것을 실제 적용 결정으로 승격하는 실패가 남았다. 적용 여부가 미결정이면 초안의 표현은 핵심 요약·할 일에 남기고 확정된 작성 기준만 결정에 넣으라는 규칙을 추가했다.
- 최종 관찰은 요청 해시를 함께 기록해 이전 리소스의 예비 출력과 구분했다. 프롬프트의 예시 수치가 실제 원문의 1,000명·금요일·7일에 섞이지 않는지도 대조했다.

### long-multiple

기대: 장문 끝 최종 7일·삭제 예외·담당자·기한 보존; 구체적 주간 점검 이유는 일반화.

장문 구성: 1일 보존 초안으로 시작하고 알림 화면·녹음 설정·원인 조사 자료 필요성을 돌아가며 반복한 120개 발언을 배치했다. 마지막에는 주간 점검 전 삭제 문제, 초안 철회와 마지막 실패부터 7일 보존, 성공 문서/실행 중 참조 보호, 만료 실패 작업만 정리, 서연의 다음 주 월요일 표 작성 약속을 넣었다. 대상 주제는 실패 자료 보존 기간이며 알림·녹음 안건은 제외한다.

## 적용 범위

이번 구현은 외부 호출과 결과 검증까지다. DB 저장·확인 대상·Job 성공·실패·자동 재시도는 #523~#525에서 연결한다. 상위 호출자는 외부 호출 전에 DB 트랜잭션을 끝내야 한다. 잘린 응답과 호출 오류를 부분 성공이나 NO_CONTENT로 바꾸지 않는다.

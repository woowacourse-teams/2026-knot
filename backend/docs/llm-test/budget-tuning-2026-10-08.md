# 추론 토큰 예산과 작성 품질 비교 · 2026-10-08

## 결론

추론 토큰 예산을 제한하면 지연을 줄일 수 있지만, 이 실험에서는 복합 발언의 분류와 필수 섹션이 잘못될 수 있었다. 정상 종료와 JSON 성공만으로 문서 품질을 판단하지 않는다. 운영 공통 기본값은 확정하지 않았다.

## 검증 범위와 근거

- 실제 대상: `${LLM_BASE_URL}`에서 실행 중인 `qwen3.8-27b`, Q8_0, 로드 컨텍스트 32,768.
- 모델 정보 API에서 추론 옵션은 `off/on`, 로드 설정의 `parallel`은 1로 관찰했다. low/medium/high의 별도 강도나 동시 처리량을 측정한 결과는 아니다.
- 입력은 합성 원문이다. 개인 회의 원문을 전송하지 않았다. 긴 입력은 반복 관찰을 포함한 합성 자료이며 실제 2시간 회의의 발화 밀도를 대표하지 않는다.
- 각 조건은 1회 실행했다. 고정 seed와 반복 측정이 없으므로 일반화된 정확도, P95 지연, 최적값을 뜻하지 않는다.
- v4 전체 시스템 프롬프트는 [작성용 프롬프트](topic-writer-v4.md), 입력과 이전 결과는 [작성 품질 기록](writing-quality-2026-10-08.md)에 있다.
- 직접 예산 제어 시험은 `@lmstudio/sdk@2.0.0`의 인증된 WSS 연결과 `model.respond()`로 수행했다. 공통 HTTP 연동 구현이나 브라우저 프리셋 적용을 완료했다는 의미가 아니다.

## 설정

```json
{
  "temperature": 0.2,
  "topPSampling": 0.9,
  "topKSampling": 20,
  "repeatPenalty": 1,
  "enableThinking": true,
  "maxTokens": 8192,
  "reasoningBudget": "각 시험의 512 / 1024 / 1536",
  "structured": "title, summary, content 세 문자열을 요구하는 JSON Schema"
}
```

`reasoningBudget`는 추론 구간의 토큰 제한이고, `maxTokens`는 추론과 최종 답을 합친 전체 생성 제한이다. 최종 답에 추가 8,192토큰을 보장하는 설정은 아니다. 입력·전체 출력도 로드 컨텍스트 안에 들어가야 한다. 이 구분과 런타임·추론 구분자 요구는 [LM Studio 공식 SDK 계약](https://github.com/lmstudio-ai/lmstudio-js/blob/main/packages/lms-shared-types/src/llm/LLMPredictionConfig.ts)에 따른다.

SDK fragment의 `tokensCount` 합으로 센 추론 토큰은 근사값이다. 표의 전체 생성 토큰은 서버 stats의 `predictedTokensCount`다. 제한 수치 근처의 추론 후 최종 JSON이 생성되는 현상을 관찰했으며, 추론 토큰의 정확한 내부 집계나 제한에 도달한 시점은 별도 계측하지 않았다.

## 판정 기준

첫 섹션의 핵심 요약, 필요한 고정 섹션의 순서와 생략, 조건·경계값·번복 보존, 다른 안건 배제, 수락하지 않은 요청과 채택을 논의하지 않은 제안의 구분을 확인했다. 자동 형식 검사 이후 실제 출력 내용을 읽어 판정했다. 통과는 해당 합성 사례에서 발견한 위반이 없다는 뜻이다.

8회 모두 `eosFound`로 종료했고 최종 JSON을 해석했다. 이 중 규칙 판정 통과는 4회다. 512와 1,024의 동일 짧은 사례 3개는 각각 2개 통과했다. 1,536은 복합 사례 하나만 측정했으므로 세 예산의 전체 통과율을 동등하게 비교하지 않는다.

### 속도와 품질의 변화

- 단순 조건부 실행과 수치 경계 사례는 512 예산에서 각각 26.23초, 27.05초였고 규칙 판정도 통과했다. 1,024에서는 43.38초, 46초로 늘었다.
- 복합 사례의 예산 512/1,024/1,536은 각각 29.6/52.08/66.47초였지만 모두 실패했다. 512에서는 핵심 요약 누락과 미수락 요청의 미결정 분류, 1,024에서는 미수락 요청의 미결정 분류, 1,536에서는 핵심 요약 누락이 있었다.
- 같은 v4 복합 사례의 예산을 지정하지 않은 HTTP 추론 시험은 170.62초에 통과했다. 설정 경로가 HTTP와 SDK로 다르고 각 1회이므로, 이 시간 차이를 예산 하나의 인과 효과로 확정하지 않는다.
- 긴 사례는 1,024 예산에서 81.97초였고, 입력 24,216·전체 생성 2,024·총 26,240토큰으로 종료했다. 예산 미지정 HTTP 시험의 157.87초보다 빨랐지만, 다른 안건 혼입과 논의하지 않은 미결정 추가로 실패했다. 미지정 시험도 다른 안건 혼입으로 실패했다.

### 현재 선택

32,768 입력 컨텍스트를 줄이지 않고 추론 예산과 전체 생성 한도를 별도로 제어할 수 있다는 근거는 확보했다. 단순 사례의 512는 빠른 후보이지만, 회의 전체를 처리하는 공통 운영값으로 채택하지 않는다. 1,024와 1,536도 복합 사례에서 실패했으므로 최적값이나 안정적인 기본값으로 부르지 않는다.

추론 예산에 닿는 것, 전체 생성 한도에 닿는 것, 요청 timeout은 구분한다. 이번 정상 종료 사례에서도 내용 오류가 있었다. 전체 출력 제한으로 끊긴 JSON이나 필수 섹션이 없는 문서는 완성 문서로 저장하지 않는 검증이 필요하다. 의미 오류를 단순 heading 검사만으로 모두 검출할 수 있다고 가정하지 않는다.

## SDK 연동 중 확인한 사항

- SDK 2.0.0에는 이전 예제의 `client.llm.get()`이 없어 기존 모델에 `createDynamicHandle()`로 연결했다. 이 시험에서 모델을 새로 로드하지 않았다.
- `result.content`에는 추론 내용이 포함될 수 있다. 최종 JSON은 `result.nonReasoningContent`에서 해석했다.
- 최초 SDK 연결 확인의 추론 호출 1회는 약 28.2초 후 파서가 `content`를 JSON으로 읽어 실패했다. 시험 코드의 파서 오류이며 위 8회의 문서 품질 판정에 포함하지 않는다. 추론 내용은 문서에 보존하지 않았다.
- 설치한 SDK 의존성과 실행기는 저장소 밖의 임시 환경 또는 메모리에서 사용했다. 이 폴더에는 설정·최종 출력·판정만 Markdown으로 유지한다.

## HTTP 호환 API의 예산 전달 시험

SDK 시험 이후, 서버의 `/v1/chat/completions`에 `thinking_budget_tokens: 512`를 전달해 동일한 조건부 실행 사례를 1회 추가 실행했다.

- HTTP 200, `finish_reason=stop`, JSON·내용 판정 통과.
- 응답 29.01초, 입력 1079토큰, 전체 생성 752토큰.
- 응답 usage의 `reasoning_tokens=510`. 추론 구간 제한 이후 최종 문서가 생성되는 현상이 이 서버·이 모델·이 요청에서 확인됐다.
- 요청의 `reasoning_effort=low`는 기존 HTTP 비교와 동일하게 유지했다. 모델 메타데이터가 off/on만 제공하므로 low를 독립된 추론 강도로 해석하지 않는다.
- 이 필드는 모든 LM Studio 버전이나 다른 제공자의 호환 API가 보장하는 공통 계약으로 확정하지 않는다. SDK의 `reasoningBudget`와 HTTP의 `thinking_budget_tokens`는 이름과 경로가 다르다. 호환성 변경 시 재검증이 필요하다.
- 위 8회 SDK 품질 판정에는 이 HTTP 1회를 포함하지 않았다.

## 후속 판단에 필요한 범위

복합 분류 실패와 장문 다른 안건 혼입은 남아 있다. 프롬프트나 처리 구조를 바꾼 후 같은 사례로 비교하고, 통과 후보를 반복 측정해야 한다. 지금 자료로 온도를 바꾸면 해결된다거나 예산을 더 키우면 항상 정확해진다고 결론 내리지 않는다. 주제 분류와 주제별 문서 작성이 합쳐진 전체 사용자 대기 시간, 여러 사용자 동시 요청, 실제 회의 원문 품질은 이번 측정 범위가 아니다.

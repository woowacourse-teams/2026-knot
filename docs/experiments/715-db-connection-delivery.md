# DB 연결 요청의 PostgreSQL 도달 구간 관측 — 실험 결과

## 1. 결론

**실제 호스트 수집을 포함한 사전 검증 17/17개를 통과한 뒤, 예정한 전체 통합 테스트 C1·C2·C3를 모두 실행했다. 매회 649개 테스트와 대상 74개의 격리 검증은 통과했다. DB 연결 timeout은 재현되지 않았다.**

양쪽 TCP 관측 완전성은 **C1·C2의 4개 구간 통과, C3의 2개 구간 불완전**이다. C3에서는 JVM 이벤트의 wall/monotonic 대응 편차가 고정 허용치 10ms를 초과했다. 따라서 전체 실행기는 마지막 관측 검사에서 exit 1로 종료했다. 테스트 실패와 관측 판정 실패를 구분하며, C3를 성공 실행으로 교체하거나 기준을 완화하지 않았다.

이번 결과는 **기존 검증·격리 유지와 진단 자료 보존을 확인한 결과**다. 과거 A3 장애의 전달 구간·근본 원인이나 개선안 5의 전체 성능 이점을 확정한 결과는 아니다.

## 2. 실험 목적과 조건

A3에서는 첫 JDBC 연결의 SSL 응답 읽기가 약 5초 후 timeout, fallback 인증 읽기가 약 5초 후 EOF로 실패했다. 당시 서버의 running·ready 상태만으로는 요청이 PostgreSQL까지 도착했는지 판단할 수 없었다.

이번에는 기존 비동기 연결 관측에 다음 자료를 추가했다.

| 구간 | 추가 관측 | 해석 범위 |
| --- | --- | --- |
| PostgreSQL | 연결 수신·SSLRequest 해석·인증/인가·세션/PID/remote endpoint | 서버가 실제 처리한 단계 |
| macOS loopback | 대상 mapped port의 TCP 송수신 요약 | 호스트 소켓의 송수신 |
| 대상 컨테이너 네트워크 | 5432 포트의 TCP 송수신 요약 | 컨테이너 네트워크 도달·응답 |
| JVM | 기존 Driver·SSL·인증 span, 물리 소켓, 원래 예외 | 클라이언트 호출의 결과 |

패킷 본문과 원시 pcap은 저장하지 않고 시각·주소·포트·TCP flags·sequence/ack·길이만 남겼다. 서버 로깅은 모든 실험 PG에 적용했고 양쪽 TCP는 snapshot 5클래스 그룹의 첫 연결로 제한했다. 정상 전체 실행에서 해당 그룹 DB는 매회 2개 생성됐다.

| 유지 조건 | 내용 |
| --- | --- |
| 제품·테스트·자원·frozen runtime | 기존 snapshot과 hash 일치 |
| 테스트 목록·실행 순서 | 매회 기존 649개 및 같은 클래스 순서 |
| JVM·캐시·힙 | 매회 새 테스트 JVM 1개, 캐시 8, 최대 힙 1GiB |
| DB·검증 | 실제 PostgreSQL/Flyway, 기존 `fsync=off`, 스케줄러 수정과 기존 assertion 유지 |
| 연결 조건 | SSL·제품 timeout·retry·준비 검사 변경 없음 |
| 실행 | `integrationTest --rerun --no-build-cache`, 실행별 XML/HTML 분리 |
| 준비 작업 | 컴파일·자원 처리 4작업 매회 UP-TO-DATE |
| 전원 | AC 전원, `caffeinate -dimsu`, 실행 구간 Sleep/DarkWake/Wake 0건 |
| 횟수 | C1 → C2 → C3, 총 3회, 대체·추가 전체 실행 0회 |

보조 이미지와 관측 소스/JAR/Python hash는 사전에 고정했다. 테스트 중 이미지 pull·도구 설치·컴파일을 수행하지 않았다. 로깅과 패킷 수집의 부하가 포함된 진단 조건이므로 전후 성능 비교로 사용하지 않는다.

첫 helper의 사용자 전환 실패, 빈 줄 파싱 오류, 즉시 종료 시 시작 상태 취소에 관한 중간 실패 원본도 보존했다. helper는 `NET_RAW`만 유지하고 `-Z root`로 기본 UID 전환을 피했다. 비어 있지 않은 미인식 입력은 여전히 파서 오류다. 사전 검증의 의도된 인증·무응답 실패는 본 실험의 장애 빈도에 포함하지 않는다.

## 6. 전달 구간 관측과 C3 제한

| 지표 | C1 | C2 | C3 |
| --- | ---: | ---: | ---: |
| 호스트 TCP 메타데이터 행 | 8,091 | 8,118 | 7,602 |
| 컨테이너 TCP 메타데이터 행 | 6,153 | 6,209 | 5,781 |
| 대상 DB 수 | 2 | 2 | 2 |
| drop·파서 오류 | 0 / 0 | 0 / 0 | 0 / 0 |
| 양쪽 준비→첫 Driver 간격 | 648.803~818.005ms | 687.758~946.713ms | 976.039~2,050.590ms |
| 전체 JVM wall/mono offset 범위 | 1.495ms | 1.516ms | **57.381ms** |
| 엄격한 완전 수집 판정 | 2개 | 2개 | **0개** |

각 대상 DB의 최종 서버 로그에는 receipt 14세션·SSLRequest trace 12세션·인가 14세션이 있었다. 이는 컨테이너 전체의 세션 수이며, 첫 애플리케이션 물리 소켓에 모두 대응했다는 뜻은 아니다.

C1·C2의 첫 Driver 소켓에는 호스트 송수신이 있었고 호출이 정상 종료됐다. 프록시 양쪽 바이트 패턴의 일치 결과는 `candidate_only`로 유지했다. 서로 다른 포트·sequence 번호를 같은 연결이라고 단정하지 않았다.

C3는 양쪽 준비·패킷·정상 종료 자료가 있고 Driver도 성공했지만, 실행 전체의 wall/mono 대응 편차가 허용치 10ms를 넘었다. 첫/마지막 offset 차이는 약 -55.927ms였다. **시계 보정, 이벤트 스케줄링 등 그 편차를 만든 원인은 이번 자료로 확정하지 않았다.** 고정 판정에 따라 두 구간 모두 `unknown_incomplete_capture`로 남겼다.

C3 첫 DB의 프록시 흐름은 바이트 합계 기준 `unmatched`, 두 번째 DB는 `candidate_only`다. 첫 경우 역시 전송 유실의 증거로 쓰지 않는다. 시작 시점·수집 범위·중계 대응이 충분히 확정되지 않았기 때문이다.

따라서 이번에 입증한 것은 **정상 연결에서 수집이 작동하고 그 한계를 검출했다는 것**이다. A3에서 SSLRequest가 DB에 도달했는지, 응답 복귀가 막혔는지는 장애 미재현으로 여전히 미확정이다. 서버 SSLRequest 로그는 해석 증거이며 응답 write 완료의 증거가 아니다.

**141개 서버 최종 로그와 282건 상태를 보존했다.** 기존 SQLException·연결 span·소켓·경계·XML·HTML·console·heartbeat·자원·전원 기록도 실행별로 남겼다. 이번 전체 실행에는 새 제품 실패 로그가 없으며, 과거 A3와 사전 검증 실패 원본을 보존했다.

follow/최종 로그 34쌍은 byte 단위로 같지 않았다. 기존 redactor가 연결 과정에서 등록된 값들을 치환하므로, 서로 다른 시점에 저장한 문자열의 마스킹 범위가 달라질 수 있다. 같은 행 수·순서에서 마스킹 토큰으로 설명 가능한 차이인지 대조했고 설명되지 않는 행 차이는 없었다. **이 대조는 원문 복원이나 byte 일치보다 약한 검증**이며 최초 audit의 불일치 목록도 그대로 남겼다.

종료 interrupt 원본 141건을 삭제하지 않았다. 최종 로그 저장 뒤의 예상 stream-close 알림과 예상 외 오류 0건을 구분했다. 대상 패킷 수집기 12개 스트림은 정상 종료·reader join·drop 0·한도 초과 없음이었다. helper 잔존 0, capture broker와 사용자 전용 socket도 종료했다. 공유 QA 컨테이너 3개는 같은 ID로 유지했다.

호스트 swap 사용량은 약 25,178~28,421MiB 범위였다. 높은 swap과 정상 연결이 함께 관측됐다는 사실만 기록하며, swap을 연결 장애나 실행 시간 차이의 단독 원인으로 확정하지 않는다.

| 전체 CI 성능 개선율 | 이번 실험에서 산출하지 않음 |

다음 진단을 계속한다면 **시계 편차 판정과 프록시 물리 연결 대응의 한계**를 먼저 계획해야 한다. C3를 사후 성공으로 바꾸기 위해 기준을 느슨하게 하거나 장애가 나올 때까지 반복하지 않는다.

이번 요청에서는 제품·테스트 코드를 바꾸거나 추가 전체 실행·commit·push·원격 설정 변경을 하지 않았다. 원인 미확정 상태에서 개선안 5를 제외하고 검증된 변경으로 마무리할 선택도 유지한다.

## 9. 도구 검증 한계

실제 Java 컴파일·PG/JDBC·JUnit·호스트/컨테이너 관측과 편집기·Persona 인증을 구분한다. Java LSP는 기존 timeout, Python/JSON LSP는 기존 미설치 상태다.

이번 Persona implementation/review의 report-filled는 모두 통과했다. `workflow finish implement`는 기존 `source-read-runtime-unavailable`로 exit 1이었다. 따라서 공식 종료 인증은 미완료이며 보고서는 diagnostic-only다. 실제 테스트·격리 통과, C3 관측 gate 실패, Persona 도구 미인증을 각각 구분한다. 환경·이력을 재생성하거나 무관한 검증을 추가하지 않았다. 문서의 로컬 링크와 대상 공백·git diff 공백 검사도 통과했다.

## 1. 실험 배경

개선안 2에서 문서 조회 테스트 4개의 import를 정렬한 뒤에도 문서 명령·생성 작업 재시도·원문 조회·세그먼트 저장 테스트는 다른 컨텍스트를 사용하고 있었다. 개선안 4 이후의 기존 성공 리포트와 코드를 대조해, 기본 JPA 설정이 같고 import가 다른 8클래스·74개 테스트를 다음 대상으로 선정했다.

| --- | --- | ---: |
| A | DocumentCommandRepositoryIntegrationTest | 6 |
| B | DocumentConfirmationQueryIntegrationTest | 10 |
| B | DocumentDetailQueryIntegrationTest | 9 |

| B | DocumentListQueryIntegrationTest | 7 |

기존 리포트에서 이 5개 설정의 최초 로딩 구간 합계 중앙값은 9.838초였다. 이 값은 대상 선정에만 사용했다. 이번 성능 비교에는 변경 전후를 새로 실행한 결과를 사용한다.

## 2. 가설과 적용한 변경

> 기본 JPA 설정이 같고 import만 다른 테스트들의 어댑터 구성을 정렬하면, 기존 SQL·제약·flush·rollback 검증을 유지하면서 5개 컨텍스트 설정을 하나로 줄일 수 있다.

대상 8개 클래스에 기존 어댑터 10개와 TestcontainersConfiguration을 동일하게 import했다. 문서·확인·생성 작업 저장소, 문서 조회 4종, 생성 입력·원문 조회, 세그먼트 저장소 어댑터를 등록했다. 원문 조회 어댑터가 의존하는 세그먼트 어댑터도 함께 포함했다.

Java 변경은 import 문과 `@Import` 구성뿐이다. 두 버전의 소스를 비교해 테스트 본문·fixture·assertion이 같음을 확인했고, 고정한 실행 산출물에서도 대상 테스트 클래스 8개만 달랐다.

다음 조건을 유지했다.

- 기본 `@DataJpaTest`와 테스트 트랜잭션·rollback
- 실제 PostgreSQL과 Flyway, 이미지 `pgvector/pgvector:pg18`
- 기존 flush·clear, 직접 SQL 조회, UNIQUE·FK·CHECK 검증
- 컨텍스트 캐시 최대 크기 8, 테스트 JVM 최대 힙 1GB
- production 코드·스키마·migration·Gradle 설정

공통 부모 클래스나 합성 애노테이션을 새로 만들지 않았다. 워커·SSE·마이그레이션 테스트 및 SQL 개수 검증용 statistics 설정은 이번 변경에 포함하지 않았다.

## 5. 단독·순서·DB 격리 검증

| 검증 | 결과 |

JUnit의 명시적 ClassOrderer로 순서를 지정하고 실제 클래스 시작 로그와 대조했다. Gradle 필터 인자 순서를 실행 순서로 간주하지 않았다.

트랜잭션 전·후 관측은 테스트 트랜잭션 밖에서 수행했다. 각 테스트 실행 직전에는 실제 트랜잭션이 활성화되어 있는지도 확인했다. 관측 테이블은 members, workspaces, documents, document_confirmations, document_generation_jobs, transcripts, transcript_segments의 7개다.

전후 측정 6회와 단독·순서 검증 11회에서 관측한 모든 경계에서 이 7개 테이블의 행 수는 0이었다. 제약 위반을 의도적으로 발생시키는 테스트 뒤에도 rollback과 다음 테스트의 정상 실행을 확인했다.

ID sequence가 1로 돌아오는 것을 격리 기준으로 사용하지 않았으며, 새 TRUNCATE·RESTART IDENTITY를 추가하지 않았다. 이 결과는 이번 대상·관측 테이블·확인한 순서에서의 격리 근거이며 모든 가능한 실행 순서를 검증한 것은 아니다.

## 7. 준비 과정과 제외 기준

첫 변경 후 준비 과정에서는 import 줄바꿈으로 Spotless가 실패했다. 측정 전에 포맷을 수정하고 Spotless와 재컴파일을 통과했다. 포맷 실패 로그와 수정 전 스냅샷을 보존했다. 이 준비 실패를 테스트 실패나 성능 표본으로 계산하지 않는다.

변경 전후 pilot 실행 각1회는 관측·고정 runtime·리포트 경로를 확인하기 위한 준비 실행으로 보존하고 본 측정표에서 제외했다. 이후 verified-focus 전후 각3회만 대상 시간표에 사용했다.

변경 후 전체 3회차에서는 `DocumentGenerationSchedulerIntegrationTest`의 최초 `TRUNCATE TABLE members, workspaces RESTART IDENTITY CASCADE`에서 PostgreSQL deadlock이 발생했다. 이 테스트는 100ms 주기의 실제 생성·복구 스케줄러를 켠 Boot 테스트이고, 이번 JPA 테스트 그룹과 다른 설정·컨텍스트 ID·PostgreSQL 컨테이너 ID를 사용했다.

이 근거로 새 공유 DB 안에서 스케줄러와 충돌한 상황은 배제할 수 있지만, 전체 실행 타이밍 변화 등 간접 영향까지 배제하지는 못한다. 스케줄러 동작과 초기 데이터 정리의 경합은 조사할 가설이다. 변경과 무관한 기존 문제라고 확정하지 않았다.

코드·시간 제한·스케줄러 설정을 바꾸지 않고 해당 클래스만 변경 전·후 각각1회 실행해 모두 통과했다. 이 두 실행은 원인 분리를 위한 진단이며 성능 표본에 섞지 않았다. 단독 통과가 deadlock 해결을 의미하지 않는다.

초기화가 줄었다는 사실만으로 전체 CI 개선을 선언하지 않는다. 이번에는 좁은 대상의 성능·격리 효과를 확인했지만, 전체 성공 반복과 비용 악화 여부를 충분히 확인하지 못해 원래 계획의 채택 기준을 충족했다고 판단하지 않는다.

다음에는 스케줄러의 초기 데이터 정리와 실제 스케줄링의 경합을 별도 범위에서 분석하고, 전체 실행 지연의 관측 근거를 확보한 뒤 동일 조건의 전후 성공 반복을 확보한다. GitHub Actions의 효과는 같은 workflow·runner 조건으로 별도 검증한다. 이 문서의 로컬 수치를 Actions 전체 개선율로 환산하지 않는다.

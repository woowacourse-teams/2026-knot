## 1. 재측정 목적

최초 실험에서는 대상 JPA 테스트의 컨텍스트와 DB 초기화를 5회에서 1회로 줄였지만, 전체 통합 실행 중 스케줄러 테스트의 최초 TRUNCATE에서 deadlock이 발생했다. 이후 해당 테스트의 불필요한 TRUNCATE를 빈 DB 확인 assertion으로 바꾸고 안정성 검증을 마쳤다.

이번에는 **스케줄러 수정을 양쪽에 동일하게 적용하고, 대상 8클래스의 JPA import 정렬 여부만 달리해 전체 통합 테스트를 전후 3회씩 새로 측정**했다. 스케줄러 수정 전의 실패 표본이나 수정 후 단독 회귀 시간을 새 성능 표본에 섞지 않았다.

**6회 모두 649개가 성공했고 실패·오류·스킵은 0개였다.** 스케줄러 테스트도 6회 모두 성공했으며 해당 테스트 로그에서 deadlock은 관측되지 않았다. 성공할 때까지 재시도해 교체한 표본은 없다.

중앙값은 사실상 비슷했고, 변경 후에는 긴 지연 표본이 포함됐다. 따라서 전체 통합 테스트가 빨라졌다고 결론 내리지 않는다. 반대로 작은 표본과 공유 호스트의 변동만으로 import 정렬이 전체 성능 악화의 원인이라고 확정하지도 않는다.

관측 테이블은 members, workspaces, documents, document_confirmations, document_generation_jobs, transcripts, transcript_segments다. 초기·종료 행 수는 테스트 트랜잭션 밖에서 확인했다. 기존 SQL·제약·flush·clear·assertion을 바꾸지 않았다.

이 결과는 대상·관측 테이블·이번 실행 순서의 격리 근거다. 앞선 단독 8클래스와 정방향·역방향·제약 우선 실행 결과도 최초 결과 문서에 보존했다. 이번에는 그 실행들을 성능 표본에 섞지 않았다.

스케줄러 수정 이후, 이번 재측정에 앞서 관측 도구 없는 일반 회귀도 동일 후보 소스로 통과했다. Spotless·단위 1,425개·통합 649개·인수 561개·JAR 빌드가 성공한 결과다. 이번 요청에서는 구현을 추가하지 않았으며, 그 일반 회귀와 새 관측 성능 실행 6회를 구분한다.

사용 힙 표본은 작아졌지만 동시 컨테이너 수와 DB 메모리는 일관되게 줄지 않았다. 따라서 메모리·자원 사용이 전반적으로 개선됐다고 주장하지 않는다. 공유 호스트와 유지된 캐시의 영향을 완전히 통제한 실험도 아니다.

기존 계획은 초기화 수뿐 아니라 전체 비용과 격리 악화 여부를 확인한 뒤 채택하도록 정했다. 이번 결과는 반복 초기화를 줄일 수 있다는 가설을 지지하지만, 전체 CI 피드백 시간을 줄였다는 근거는 충족하지 못했다. 느린 실행을 제외하거나 중앙값만 유리하게 해석해 채택하지 않는다.

실험 후보 코드는 비교·리뷰 근거로 `be/refactor/#715`의 별도 커밋에 보존한다. 이는 성능 검증을 마친 변경으로 최종 채택하거나 운영에 반영했다는 뜻이 아니다. 스케줄러 수정은 독립 커밋이므로 개선안 5와 분리해 검토할 수 있다.

블로그·이력서에는 **“테스트 설정 정렬로 전체 통합 실행의 컨텍스트·DB·Flyway 초기화를 각각 4회 줄이고, 전후 각 3회에서 기존 649개 검증과 대상 데이터 격리를 확인했다. 전체 실행 시간 개선은 확인하지 못해 채택을 보류했다.”**로 기록할 수 있다. 앞선 대상 74개 단독 실행의 56.8% 감소율을 전체 CI 개선율로 사용하지 않는다.

추가 성능 판단에는 이번 지연 구간의 자원·GC·호스트 상태와 GitHub Actions의 동일 runner 조건 측정이 별도로 필요하다. 이 문서는 이번 6회 실험의 최종 판정이며, Actions 성능이나 Issue #715 전체 완료를 선언하지 않는다.

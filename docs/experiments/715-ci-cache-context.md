- 판정: 용량 퇴출에 따른 동일 설정 재생성 확인. 캐시 16의 저장소 반영은 보류하고 기본값 8을 유지한다.
- 기준: `7fd075436df67921edc2fd0666eb2534fb302507`, `be/refactor/#715`.

## 1. 실험 목적과 방법

기존 캐시 크기 8에서 컨텍스트가 용량 때문에 퇴출된 뒤 같은 설정으로 다시 만들어지는지 확인하고, 입증되면 크기 16과 비교한다. 서로 다른 최초 설정, 명시적 초기화, 용량 퇴출을 구분한다.

제품 및 테스트 소스, assertion, 트랜잭션과 데이터 정리, PostgreSQL/Flyway, 힙 1GB를 유지했다. `build.gradle`의 캐시 기본값도 변경하지 않았다. 실험용 init script에서 테스트 JVM의 캐시 크기만 8 또는 16으로 지정했다.

설치된 Spring Test 7.0.8 소스를 읽고 `DefaultContextCache`의 조회·저장·제거를 실험용 Java agent로 관측했다. 키는 문자열이나 해시 값만 비교하지 않고 실제 `equals/hashCode`로 분류했다. 제거 호출 경로에서 `evictLruContextIfNecessary`와 `closeContext`를 구분했다. 캐시 연산과 반환값은 변경하지 않았다. 같은 실행 안에서 컨텍스트 식별자를 비교하며, 다른 JVM 사이의 숫자를 공유 증거로 사용하지 않는다.

양쪽에 캐시 TRACE 및 동일한 관측기를 적용했다. 관측기는 키 메타데이터를 유지하고 로그·메모리 샘플을 기록하므로 절대 시간과 메모리에 영향을 줄 수 있다. 이 결과를 관측기 없는 CI 실행 시간으로 해석하지 않는다.

| 순서·목록 | 성공 전체 실행의 실제 클래스 진입 순서 및 649개 inventory 동일 |

기존에 실행 중이던 QA 앱과 DB 컨테이너는 유지했다. 전용 벤치마크 호스트의 측정이 아니며, 캐시와 호스트 상태의 영향이 남아 있다.

## 3. 시간 비교와 성공 여부

초기 관측 중 같은 작업 폴더를 사용하는 다른 Gradle 빌드가 겹쳤고, 실험 실행이 `java.io.EOFException`으로 종료됐다. 이 실행은 새 XML이 생성되지 않았으며 이전 실행의 XML이 남아 있었다. 해당 XML을 현재 테스트 성공으로 사용하지 않도록 집계값을 무효화했다.

이후 binary·XML·HTML을 실행별 경로로 분리하고 XML 생성 시각 검사를 추가했다. 저장 경로 변경 전후 시간을 섞지 않기 위해 **경로 분리 이후의 교차 실행 6회**를 시간 비교 대상으로 정했다. 앞선 성공 3회는 구조 확인 자료로만 보존한다. 이 선택은 시간값의 크기를 기준으로 하지 않았다.

실제 순서는 16 → 8 → 16 → 8 → 16 → 8이다.

| 조건별 시도 | 캐시 8 | 캐시 16 |
| --- | --- | --- |
| 1회 | 138.533초·649개 성공 | 184.189초·649개 성공 |
| 2회 | 135.490초·649개 성공 | 135.069초·649개 성공 |
| 3회 | 138.397초·649개 성공 | **128.729초·7개 실패** |
| 성공 실행 | 3회 | 2회 |
| 중앙값 | **138.397초** | 동일한 성공 3회 비교 미충족으로 판정 보류 |
| 성공 실행 시간 범위 | 135.490–138.533초 | 135.069–184.189초·2회 참고값 |

실패 실행의 빠른 시간을 개선 성과에 포함하지 않았다. 성공한 캐시 16 실행 중 빠른 값만 고르지 않았으며 184.189초도 그대로 기록했다. 성공 3회씩의 비교와 안정성 조건을 만족하지 못했으므로 전체 시간 개선율을 계산하지 않는다.

분리 전 탐색 실행은 캐시 8의 247.934·233.840초, 캐시 16의 208.474초였다. 전체 시간 변동이 크므로 이 값과 뒤의 빠른 실행을 연결해 큰 개선율을 주장하지 않는다.

## 4. 메모리 관측

아래 값은 경로 분리 이후 **성공 전체 실행**에서 수집한 샘플의 최댓값이다. 캐시 8은 3회, 16은 2회이며 실제 순간 최대 사용량이나 유지 메모리의 정밀 추정이 아니다.

| 지표 | 캐시 8 | 캐시 16 |
| --- | ---: | ---: |
| JVM 힙 사용량의 샘플 최댓값 | 906.8MiB | 953.8MiB |
| JVM RSS의 샘플 최댓값 | 1,359.5MiB | 1,303.3MiB |
| 실험에서 생성한 PostgreSQL 동시 관측 수 | 9개 | 17개 |
| 해당 PostgreSQL 메모리 합계의 샘플 최댓값 | **501.0MiB** | **975.3MiB** |

힙은 약 2초마다, RSS·Docker는 이전 수집이 끝난 뒤 10초 간격으로 관측했다. 기존 QA DB는 실험의 PostgreSQL 합계에서 제외했다. 수치는 캐시 Bean 외에 테스트가 직접 만든 DB 컨테이너도 포함한다. 캐시의 실제 엔트리가 9개 또는 17개였다는 뜻은 아니다.

Docker가 종료 중 컨테이너의 메모리를 `--`로 반환한 표본은 알 수 없는 값으로 처리하고 해당 합계 표본에서 제외했다. 0으로 해석하지 않았다.

PostgreSQL 메모리 관측값은 거의 두 배였다. JVM RSS는 GC·관측 시점 등의 영향을 받으므로 샘플 하나의 대소 관계로 캐시 16이 JVM 메모리까지 덜 쓴다고 결론 내리지 않는다. 실제 Actions runner의 자원 여유는 측정하지 않았다.

## 5. 실패와 추가 확인

### Gradle 리포트 생성 실패

`cache-16-2`는 395.577초 후 EOFException으로 종료됐으며 새 XML이 없다. 테스트 성공 수와 초기화 로그 집계 중 XML에 의존하는 값은 `null`로 정정했다. runtime probe의 캐시 이벤트는 별도 근거로만 유지한다.

같은 cwd에서 Java 21 Gradle daemon의 다른 빌드가 20:48:59–20:55:51 실행된 기록을 보존했다. 우리 실행과 시간이 겹쳤고 공유 binary 결과가 바뀌어 리포트 충돌이 의심되지만, EOF의 직접 원인은 확정하지 않았다. 경로 분리 이후 EOF는 재관찰되지 않았다.

### MCP HTTP 검증 7개 실패

`cache-16-4`는 새 XML에서 649개 중 7개 실패를 확인했다. 모두 `SearchDocumentToolServiceIntegrationTest`의 32개 검증 중 일부였다.

- 실제 MCP 호출에서 기대한 200·401 대신 404를 반환한 검증.
- MCP·LLM 연결 검증에서 COMPLETED 대신 FAILED가 저장된 검증.
- 동시 Workspace 요청 결과에 기대한 본문이 없는 검증.

실패 클래스를 같은 코드로 단독 실행한 결과는 다음과 같다.

| 추가 확인 | 결과 |
| --- | --- |
| 캐시 16·클래스 단독 | 기존 32개 성공 |
| 캐시 8·클래스 단독 | 기존 32개 성공 |
| 캐시 8·마지막 전체 실행 | 기존 649개 성공 |

캐시 16이라는 값만으로 실패가 결정되는 것은 아니며 전체 실행의 선행 상태·서버 생명주기·간헐성 등의 추가 분리가 필요하다. 원인을 확정하거나 해결했다고 주장하지 않는다. 실패를 숨기기 위해 성공 3회가 나올 때까지 반복하지 않았다. 테스트 본문·순서·타임아웃·검증은 바꾸지 않았다.

## 7. 보존한 근거

원시 파일은 `backend/output/ci-715/cache-context-20261015/`에 보존했다. 이 디렉터리는 이번 실험의 요청 산출물이며 제품 빌드에 포함하지 않는다.

- `original-reports/`: 재실행 전 통합 리포트.
- `probe/`, `probe.jar`, `profile.init.gradle`, `measure.py`, `analyze.py`: 관측 및 집계 재현 도구.
- `cache-8-observe`, `cache-16-1`, `cache-8-2`: 경로 분리 전 성공 탐색 실행.
- `cache-16-2`: EOF 실패 원본, 실패 binary, 동시 빌드 근거, stale XML. `summary-unvalidated-original.json`은 정정 전 감사 원본이며 분석에 사용하지 않는다.
- `cache-16-2-retry`, `cache-8-3`, `cache-16-3`, `cache-8-4`, `cache-16-4`, `cache-8-5`: 경로 분리 이후 전체 교차 실행.
- `isolation-mcp-16`, `isolation-mcp-8`: 실패 클래스 단독 실행.
- 각 실행의 `events.tsv`, `resources.jsonl`, `console.log`, `summary.json`, XML·HTML. 실패 실행과 성공 실행을 모두 유지한다.
- `analysis.json`: 성공·실패 목록과 시간 집계 범위. `performance_comparison_ready=false`로 기록했다.

전체 성공 8회는 inventory·실제 클래스 순서·실제 키별 클래스 묶음이 같고, JVM 1개·실제 캐시 8/16·힙 1GiB·컴파일 UP-TO-DATE를 별도 대조했다. 실패한 MCP 전체 실행도 inventory와 순서는 동일했다. 현재 요청에서 commit·push·PR·원격 Issue/Notion 쓰기는 하지 않았다.

작업 종료 검사에서 `git diff --check`는 통과했고 `src`와 `build.gradle`의 변경은 없었다. Persona의 두 보고서 작성 검사는 통과했지만 `workflow finish implement`는 `source-read-runtime-unavailable`로 종료 인증을 완료하지 못했다. 이 도구 상태는 실제 Gradle 테스트 및 실험 관측 결과와 구분한다.

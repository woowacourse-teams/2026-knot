## 관련 Issue

## 한 줄 요약

기능 구현 요청은 입구 스킬 하나가 문서 단계 서브 에이전트를 순서대로 부르고 구현 단계는 기존 FE, BE 하네스로 직접 수행하며, 노션과 Figma를 정본으로 둔다.

## 왜 이 결정이 필요했나

Claude Code와 Codex의 서브 에이전트는 다른 서브 에이전트를 부르거나 사용자에게 묻지 못하고 매번 빈 컨텍스트에서 시작한다. 기존 프론트 하네스는 Agent 도구와 대화형 스킬을 쓴다. 노션과 Figma가 정본이고 저장소 Markdown 복사는 PR 충돌을 만든다.

2026-10-21 두 회의와 10-22 정리본에서 팀은 「○○ 기능 구현해 줘」 한 문장이 문서 갱신부터 PR까지 가는 하네스를 설계했고, 10-22 구현에서 서브 에이전트가 서로 메시지를 주고받을 수 있는지와 구현 단계를 어디서 돌릴지가 문제가 됐다.

결정 동인:

- 사람은 PR에서 한 번만 컨펌하고 중간 질문은 입구가 대신 묻는다.
- Codex와 Claude Code가 같은 Markdown을 공유한다.
- 기존 FE, BE 하네스와 Issue 하네스를 바꾸지 않고 묶는다.
- 노션과 Figma가 정본이며 저장소로 복사하지 않는다.

## 트레이드 오프

- 에이전트 팀으로 서브 에이전트끼리 직접 메시지를 주고받기: 흐름이 유기적이지만 실험 기능이고 비용이 크며 Codex와 공유할 수 없다.
- 문서를 저장소 Markdown으로 복사해 서브 에이전트가 파일을 읽기: 접근은 쉽지만 PR끼리 충돌하고 정본이 둘이 된다.
- 구현 단계도 서브 에이전트로 띄우기: 구조가 균일하지만 서브 에이전트 안에서는 Agent 도구와 대화형 스킬을 쓸 수 없어 기존 프론트 하네스를 그대로 쓸 수 없다.

## 무엇을 결정했나

기능 구현 요청은 입구 스킬 하나가 문서 단계 서브 에이전트를 순서대로 부르고 구현 단계는 기존 FE, BE 하네스로 직접 수행하며, 노션과 Figma를 정본으로 둔다.

허브형 중계는 두 도구의 실제 제약 안에서 돌고, 서브 에이전트가 돌려주는 사실(`flags`)과 정본이라는 두 통로로 단계 사이의 영향을 설명할 수 있으며, 구현을 메인 세션이 하면 기존 하네스를 수정 없이 재사용한다.

2026-10-23 보완(#932): 처음에는 서브 에이전트가 다음 단계를 `next`로 지목했다. 팀 피드백(분기를 AI가 하면 의도대로 안 돌 수 있다)을 받아 서브 에이전트는 사실만 돌려주고 분기는 `harness/feature_pipeline.py next_stage`가 한다. 요청 종류 `fix`, `chore`는 문서 단계를 건너뛴다.

## 결과

- 문서 단계 서브 에이전트 여섯 개와 입구 스킬, 반환 규약이 생긴다.
- 기존 스킬 여섯 개에 이 흐름 안에서만 적용되는 승인 예외 한 줄이 들어간다.
- 서브 에이전트끼리 직접 협상하는 설계는 쓰지 않으므로 FE, BE 계약이 자주 엇갈리면 에이전트 팀을 다시 검토한다.

## 다시 논의해야 할 조건

- Claude Code나 Codex가 서브 에이전트 간 메시지나 서브 에이전트 안의 Agent 도구를 공식 지원할 때
- FE와 BE가 API 계약을 두고 자주 엇갈려 구현 단계에 협상이 필요해질 때
- 노션 MCP 토큰 비용과 Figma 시트 제약 때문에 스크립트가 만드는 읽기 전용 캐시(QA 시트, 기능 요구사항, Figma 화면 수치와 캡처)를 저장소에 둘지 정할 때. 「저장소 Markdown 복사」 트레이드오프는 손으로 베끼는 경우를 전제했고 생성 캐시는 다시 판단한다 (2026-10-23 팀 피드백)

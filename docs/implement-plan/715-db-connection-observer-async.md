# 첫 JDBC 연결에 대한 관측 영향 분리 실험 계획

## 1. 범위와 브랜치

- 결과: [시작 관측의 동기·비동기 비교 결과](../experiments/715-db-connection-observer-async.md)
- 확인일: 2026-10-17

- 선행 결과: [DB 연결 관측 추가 후 전체 통합 테스트 3회 실행 결과](../experiments/715-db-connection-observation.md)

**이번 실험은 컨테이너 시작 직후 수행하는 로그 수집 등록·상태 조회가 첫 JDBC 연결을 늦추는지 확인하는 것이다.** 연결 단계 관측은 유지하고, 시작 시 수집 작업의 실행 방식만 동기·비동기로 비교한다. 제품 기능·API·DB 스키마 변경은 없다.

### 실험 배경

앞선 관측 실행은 전체 649개 테스트가 3회 모두 성공했고, Driver 연결 2,712건에서 timeout이 없었다. 그러나 현재 관측기는 컨테이너 `start()`가 반환되기 전에 로그 파일 생성, Docker 로그 스트림 등록, `inspect`를 실행한다. 이 작업이 첫 연결 시점을 바꿨을 가능성이 남아 있다.

| 기존 관측 지표 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| 컨테이너 준비 관측 → 첫 Driver 호출 중앙값 | 49ms | 45ms | 57ms |
| 위 간격 범위 | 7~296ms | 8~321ms | 8~368ms |
| 가장 긴 Driver 연결 호출 | 81.696ms | 117.106ms | 94.294ms |

준비 관측부터 첫 Driver 호출까지의 간격에는 다른 애플리케이션 작업도 포함된다. 위 값을 순수 관측 비용으로 보거나, 성공한 이유를 관측기의 대기로 확정하지 않는다.

## 2. 비교할 흐름과 실험 가설

> 컨테이너 시작 후 로그 수집 등록·상태 조회를 별도 작업으로 넘기면 첫 JDBC 연결 전에 그 작업을 기다리는 구간이 제거된다. 다만 실제 첫 연결이 얼마나 앞당겨지고 timeout 재현 여부가 달라지는지는 측정해야 한다.

### A — 동기 수집

```text
컨테이너 start() 종료 hook 진입
→ ID·호스트·포트와 공통 경계 기록
→ 로그 파일 생성·Docker 로그 스트림 등록
→ Docker inspect
→ 종료 hook 반환
→ Spring 초기화 계속 진행
→ Flyway/JDBC 연결
```

### B — 비동기 수집

```text
컨테이너 start() 종료 hook 진입
→ ID·호스트·포트와 공통 경계 기록
→ 수집 작업을 대기 없이 제출
→ 종료 hook 반환
→ Spring 초기화 계속 진행 → Flyway/JDBC 연결

별도 worker: 로그 파일 생성·Docker 로그 스트림 등록 → Docker inspect
```

B의 worker는 첫 JDBC 연결 전이나 후 어느 쪽에서도 실행될 수 있다. JDBC를 worker 완료까지 기다리게 하지 않고, 반대로 첫 JDBC 연결 이후로 worker를 강제로 지연시키지도 않는다. 실제 선후 관계를 기록한다.

| 항목 | A·B 공통 조건 |
| --- | --- |
| 연결 관측 | Flyway·DataSource·Driver·SSL/인증/fallback·소켓·원래 예외 보존 |
| 기록 방식 | 기존 동기 `ConnectionObserver.event()`와 비밀번호 가림 유지 |
| 느린 연결 진단 | 기존 5초 watchdog·thread dump·상태 수집 유지 |
| 제거 직전 증거 | 최종 서버 로그·상태 보존 경로 유지. 수집 생명주기 보호도 양쪽에 같은 코드 적용 |
| DB 동작 | 준비 검사·SQL probe·sleep·SSL·timeout·retry 변경 없음 |

기존 event writer의 동기화와 디스크 기록 비용은 이번에 분리하지 않는다. 비동기 worker가 CPU·Docker API·writer lock을 두고 경쟁할 가능성도 남으므로 “관측 비용 전체 제거”라고 표현하지 않는다.

## 3. 기존 코드와 변경할 책임

구현 시 기존 `connection-observation-20261016` 디렉터리를 덮어쓰지 않고 별도 실험 디렉터리에 복사한다. 아래 메서드와 설정은 모두 제안이며 아직 적용하지 않았다.

| 위치·클래스 | 현재 동작 | 변경 제안 |
| --- | --- | --- |
| `ContainerStartAdvice.exit()` | 성공한 `start()` 종료 시 `ready()` 호출 | A·B 공통 hook 진입·반환 직전 경계를 기록 |
| `ContainerCapture.ready()` | 등록, 로그 스트림 시작, inspect까지 호출 스레드에서 수행 | 컨테이너 정보 등록과 수집 작업을 분리. A는 직접 실행, B는 대기 없이 제출 |
| `ContainerCapture.captureStartup()` — 추가 후보 | 없음 | 고정한 ID로 파일 생성·로그 등록·inspect 실행. 요청·실행 시작·완료 시각과 실패 기록 |
| `ServerLogCapture` | callback에서 로그 가림·저장·flush | 기존 저장 동작 유지. 중복 close·중복 stream 방지와 시작/종료 경합 검증 |
| `ContainerCapture.beforeStop()` | 상태 조회, 최종 로그 보존, stream close | 양쪽에 같은 종료 절차 적용. 대기 중 시작 작업 취소·진행 작업의 제한된 정리 후 기존 최종 수집 수행 |
| `ConnectionObserver` | 연결 span·소켓·동기 event·watchdog | 연결 계측 본체 유지. 공통 경계에 실제 발생 시각을 담고 수집 작업과 연결 기록을 구분 |
| 새 실험의 실행기·집계기 | 기존 실행기는 전체 3회 고정, 집계기는 ready/before-stop 상태로 대상 대응 | A·B 모드와 6회 순서를 고정. 지연된 상태 조회와 컨테이너 생존 경계를 분리해 집계 |

### 시작 작업과 종료의 경합 처리

- 제출 시 컨테이너 ID·호스트·포트·작업 ID를 고정한다. worker가 나중에 변경된 Bean 상태를 읽어 다른 대상으로 대응시키지 않게 한다. 공통 등록 경로에는 새 Docker 요청을 넣지 않는다.
- 제안하는 worker 한도는 2개, 대기열은 64개로 고정한다. 무제한 thread·queue를 사용하지 않는다. 이 숫자는 측정 결과가 아닌 시작 설계값이다.
- 대기열 포화 시 호출 스레드에서 대신 실행하는 방식은 사용하지 않는다. 수집 실패를 남기고 해당 실행의 관측 완전성을 미충족으로 처리한다.
- stop 요청 이후 대기 중 작업은 취소하고, 진행 작업은 제한된 정리 절차를 거친다. 수집 정리 대기는 컨테이너당 최대 3초를 제안하며 시작 hook에서는 기다리지 않는다. 종료 정리 시간을 별도로 기록한다.
- Docker 요청에도 종료 한도를 적용할 수 있는지 설치된 client 경로에서 구현 전에 확인한다. `Future.cancel()`만으로 I/O 종료를 보장한다고 가정하지 않는다. 제한 안에 정리되지 않으면 불완전 수집으로 표시하고 후속 측정을 중단한다.
- stop 이후 늦은 worker가 stream을 다시 열거나 상태를 `ready`로 등록하지 못하게 한다. worker 종료와 최종 로그 저장을 확인한 뒤 실험 자원을 정리한다.

### 새로 기록할 시간 경계

모든 경계는 해당 테스트 JVM의 `System.nanoTime()`을 기준으로 한다. JSON 파일에 기록된 순서와 실제 발생 순서는 구분한다. A·B에 동일한 경계 코드를 넣고 하나의 JAR에서 모드만 바꾼다. 따라서 A는 과거 JAR 그대로가 아니라 **기존 동기 동작에 공통 경계 측정을 추가한 대조군**이다.

| 경계 | 의미 |
| --- | --- |
| `T0` | 시작 종료 hook 진입. DB 접속 가능을 증명하는 시점은 아님 |
| `Tsubmit`, `Tworker` | B 작업 제출·실행 시작. 차이로 queue 대기 계산 |
| `TcollectStart`, `TcollectEnd` | 로그 등록·inspect 작업 시작과 완료. 각 작업의 시작·종료도 기록 |
| `ThookEnd` | 시작 hook 반환 직전. marker 기록 후 반환까지의 작은 공통 비용은 남음 |
| `Tjdbc` | 해당 컨테이너의 첫 `Driver.connect` span 시작 시각 |
| `Tstop` | 실제 stop 전 hook 진입 시각. 상태 조회 완료 시각과 구분 |

주 지표는 `ThookEnd − T0`와 `Tjdbc − T0`다. 첫 값은 hook 구간, 두 번째는 다른 초기화 작업까지 포함한 첫 연결 간격이다. 수집 작업 소요·queue 대기, 첫 연결 시 수집 진행 여부, Driver 호출 자체의 소요 시간도 별도 집계한다.

비동기 상태 조회는 “시작 직후 상태”가 아닌 **worker가 실제 조회한 시점의 상태**로 표시한다. 컨테이너 생존 구간은 공통 등록 경계부터 `Tstop`까지로 대응하고, 늦게 기록된 `CONTAINER_STATE`를 생존 시작·끝으로 사용하지 않는다. 같은 포트 재사용과 중복 후보는 미확인으로 표시한다. async JSON 기록 순서로 잘못된 컨테이너에 대응시키지 않는다.

## 4. 저장 기반과 측정 조건

DB 스키마·migration·운영 데이터 변경은 없다. 수집되는 정보는 로컬 파일이며 비밀번호·민감한 URL query·전체 환경변수를 저장하지 않는다.

### 비교 방식

**A·B 각각 전체 통합 테스트 3회, 총 6회를 새로 실행하는 계획**이다. 과거 동기 관측 3회는 참고값으로만 두고 새 A 표본을 대신하지 않는다.

| 실행 순서 | 조건 |
| --- | --- |
| 1 | A1 — 동기 |
| 2 | B1 — 비동기 |
| 3 | B2 — 비동기 |
| 4 | A2 — 동기 |
| 5 | A3 — 동기 |
| 6 | B3 — 비동기 |

인접 쌍은 A1/B1, B2/A2, A3/B3이다. 순서를 미리 고정해 시간 경과·캐시의 영향을 일부 분산한다. 완전한 무작위 대조나 호스트 부하 통제는 아니므로 소표본의 한계는 남는다. 테스트 실패를 새 성공 실행으로 교체하지 않는다.

- 이전 변경 후 고정 runtime, 649개 inventory와 클래스 실행 순서를 대조한다. 현재 소스·자원이 snapshot과 달라졌으면 측정을 시작하지 않고 차이를 먼저 기록한다.
- 실행별 새 테스트 JVM, 힙 1GiB·컨텍스트 캐시 8, 같은 Java·Gradle·DB 이미지·스케줄러 수정과 테스트 검증을 유지한다.
- A·B는 같은 observer JAR·classpath·공통 계측을 사용하고 시작 수집 모드만 다르게 한다. 원본 boundary observer·의존성 JAR도 고정한다.
- 두 모드 준비·컴파일·수집기 사전 검증은 측정 전에 끝낸다. 준비 작업의 UP-TO-DATE를 확인하고 추가 전체 워밍업은 넣지 않는다.
- AC 전원·절전 방지·기존 heartbeat·자원 수집을 같은 방식으로 적용한다. 기존 공유 QA 컨테이너·사용자 프로세스를 임의 종료하지 않는다.
- 독립 실행별 console·XML·HTML·연결·서버 로그·전원·자원 기록과 종료 코드를 보존한다. OS 절전·전원 조건 위반은 표시하고 성공 표본으로 몰래 대체하지 않는다.

새 실행기는 기존 `integrationTest --rerun --no-build-cache`와 고정 runtime·리포트 분리 틀을 재사용하도록 계획한다. **현재 `connection.py cohort`는 이 A·B 비교를 지원하지 않으므로 그대로 실행하지 않는다.** 실험용 새 모드 옵션과 경로를 구현한 뒤 실제 최종 명령을 문서화한다.

| 전체 영향 | 명령 wall/monotonic·XML 시간·종료 정리 시간·CPU/swap/heartbeat·OS 절전 |

실행 3개를 독립 비교 단위로 삼는다. 한 실행의 컨테이너 47개나 Driver 호출 수백 건을 독립적인 장애 실험 표본 수로 세지 않는다. 컨테이너 key·클래스·동일 key의 생성 순번으로 대응시키고, 실패로 뒤쪽 실행 흐름이 달라졌다면 달라진 구간을 분리한다.

컨텍스트 key 32·실제 context 39·PG 47·Flyway 117은 이전 성공 실행의 참고값이다. 새 실행에서도 확인하되 실패 때문에 초기화 횟수가 줄어든 경우 개선으로 계산하지 않는다. 일반적인 연결 호출 수는 풀 동작에 따라 달라질 수 있어 899건 등을 고정 기대값으로 삼지 않는다.

## 5. 구현·검증 순서 — 모두 예정

### 1단계: 시작 hook의 대기 여부를 먼저 검증

인위적인 sleep 시간 비교 대신 수집 작업을 latch로 막는다. A는 수집 작업이 풀릴 때까지 hook을 반환하지 않고, B는 수집 작업이 막혀 있어도 hook을 반환하는지 검증한다. 같은 연결 계측·예외 보존이 유지되는지도 확인한다. 이는 합성 수집기 검증이며 DB 장애 재현 근거가 아니다.

### 2단계: 로그·상태 보존과 종료 경합 검증 후 최소 구현

| 검증 방식 | 시나리오 | 기대 결과 |
| --- | --- | --- |
| 수집기 합성 검증 | 정상 제출·완료 | 컨테이너당 한 번 수집, 경계·파일·최종 완료 기록 |
| 수집기 합성 검증 | queue 포화·Docker 오류·수집 지연 | 원래 테스트 예외·종료 코드 보존, 오류 명시, 호출 스레드 대체 실행 없음 |
| 수집기 합성 검증 | worker 시작 전 stop·진행 중 stop·중복 stop | 늦은 stream 재개·중복 파일·무기한 대기·worker 잔존 없음 |
| 집계 fixture | 첫 Driver 기록 후 startup 상태 기록, 포트 재사용 | 기록 순서가 아니라 ID·발생 시각·생존 구간으로 대응. 모호하면 미확인 |
| 실제 PostgreSQL 최소 검증 | 정상 start·연결·stop | 초기 서버 로그와 최종 로그·상태 보존, 실제 소켓 대응·원래 DB 동작 유지 |
| 실제 PostgreSQL 최소 검증 | 짧은 생명주기로 시작 수집과 stop 경합 | 누락을 숨기지 않고 기록, 최종 증거 보존·자원 종료 확인 |

B의 로그 구독이 늦게 시작되더라도 이미 생성된 초기 서버 로그가 포함되는지 실제 DB에서 확인한다. 최종 로그 보존은 필수다. follow·최종 로그의 차이가 있다면 동시 기록·종료 경계 차이인지 누락인지 설명하고, 필수 자료가 빠졌으면 관측 완전성 미충족으로 판단한다.

이전 `ClosedByInterruptException` 종료 알림은 원시 기록을 보존하고 A·B에 같은 분류 기준을 적용한다. 새 오류가 기존 오류로 오분류되지 않게 작업 ID·컨테이너·시각을 함께 본다.

### 3단계: 전체 A·B 각 3회 실행과 격리 대조

사전 검증이 통과하면 고정 순서 6회를 수행한다. 각 실행에서 전체 성공·실패·오류·스킵, 대상 74개의 활성 트랜잭션·rollback·트랜잭션 밖 전후 7개 테이블 잔여 행 0·공유 context 1을 확인한다. 스케줄러 3개도 따로 확인한다.

테스트 실패는 보존하고 다음 예정 실행은 유지한다. 관측기 누수·필수 로그 유실·실험 조건 위반으로 비교 자체가 깨진 경우에는 중단하고 미완료로 기록한다. 요청된 회수 밖의 자동 대체·재실행은 하지 않는다. 단독 성공으로 전체 실행의 장애를 배제하지 않는다.

이번 범위는 관측 영향 진단이다. 제품 변경에 대한 단위·인수·bootJar 전체 회귀를 추가한 것으로 표현하지 않는다. 추후 커밋이 별도로 요청되면 시작 수집 분리, 실행·집계, 문서 책임을 나눠 실제 diff와 저장소 컨벤션으로 경계를 정한다.

## 6. 판정 기준과 다음 작업

| 관측 결과 | 판단 |
| --- | --- |
| B가 수집 완료를 기다리지 않고 hook을 반환하며 첫 연결 간격도 감소 | 시작 수집이 첫 연결을 지연시켰다는 설명을 지지. 과거 timeout의 근본 원인 증명은 아님 |
| hook 시간은 줄지만 첫 연결 간격은 비슷함 | 대기 경로 제거는 확인. 실제 첫 연결 시점에는 다른 준비 작업·스케줄링 영향이 더 클 가능성 |
| B에서만 기존과 같은 SSL timeout·fallback EOF가 발생 | 시작 타이밍 의존 가능성이 커짐. 새 worker의 자원 경쟁·수집 지연도 함께 검토하며 준비 부족으로 즉시 확정하지 않음 |
| 양쪽에서 연결 실패 발생 | 첫 연결 경계와 서버·자원 기록으로 공통 경로를 좁힘 |
| 양쪽 모두 성공 | 이번 각 3회에서 미재현. 간헐 장애 해결·재현율 0 확정으로 해석하지 않음 |
| B에서 로그 누락·worker 잔존·종료 경합 발생 | 비동기 관측 채택 보류. 테스트 성공 여부와 별개로 관측기 수정 필요 |

완료 시 두 가지 결론을 따로 작성한다.

1. **관측 방식 판단:** B가 시작 경로의 대기를 줄이고 연결 계측·필수 서버 증거·종료 정리를 유지했는가.
2. **기존 장애 판단:** 같은 timeout이 재현됐는가. 어느 단계·대상·서버 상태까지 확인했고 무엇이 여전히 미확정인가.

전체 649개·대상 74개 격리·스케줄러 검증과 관측 완전성이 충족되면 B를 후속 진단용 관측 방식으로 채택할 수 있다. 이것을 개선안 5의 제품 변경 채택이나 GitHub Actions 성능 개선으로 해석하지 않는다. 실패·누락이 있으면 해당 범위와 보류 이유를 남긴다.

계획 작성 당시에는 관측 코드 구현·테스트 실행 전이었다. 이후 승인된 실행에서 동기·비동기 각각 3회를 마쳤으며, A·B 실행별 표·첫 연결 타임라인·실패 원본·관측 품질·판정·한계는 위 별도 결과 문서에 기록했다. 아래 제안과 판정 기준은 계획 당시 내용으로 유지한다. commit·push는 수행하지 않았다.

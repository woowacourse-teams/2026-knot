## 2. 확인한 흐름과 다음에 검증할 흐름

### 기존 로그에서 확인한 시간 순서

아래 시각은 저장된 wall 시각의 KST 표시다. 서로 다른 clock domain 사이의 단방향 네트워크 지연을 계산한 값이 아니다.

| 사건 | 시각·결과 |
| --- | --- |
| 첫 snapshot DB의 양쪽 수집 종료 완료 | 17:57:41.584경 |
| 두 번째 snapshot DB의 양쪽 수집 종료 완료 | 17:59:46.860경 |
| JVM의 마지막 변화 전 표본 | 18:00:23.017, 초기 대비 offset 약 +1.004ms |
| JVM의 첫 큰 변화 표본 | 18:00:23.683, 초기 대비 약 -55.679ms |
| 별도 Python heartbeat의 변화 전·후 | 18:00:22.956에 +0.552ms → 18:00:23.904에 -55.723ms |
| 변화 이후 JVM 기록 | 이후 770개 이벤트에서 큰 음의 offset이 유지됨 |

즉, 변화는 두 번째 수집이 끝나고 **약 36초 이상 뒤**에 처음 관측됐다. 첫 변화의 정확한 발생 시각은 표본 사이 구간이며 특정 순간으로 확정하지 않는다.

### 실행 전체와 실제 수집 구간의 차이

| 범위 | JVM wall/mono offset 범위 |
| --- | ---: |
| C3 전체 | 57.381ms |
| 첫 DB 수집 요청부터 실제 마지막 수집 종료까지의 JVM 표본 | 0.991ms |
| 두 번째 DB의 같은 범위 | 0.990ms |

두 구간은 각각 JVM 표본 99개·108개를 포함했다. 실제 구간별 Python 수신 시각의 offset 범위도 호스트 0.038/0.014ms, 컨테이너 수집 reader 0.013/0.012ms였다. 이는 **호스트에서 기록한 수신 시각**이며 컨테이너 VM 시계 자체의 안정성을 증명하지 않는다. JVM 구간 집계는 기존 wall 시각으로 구간을 잘라 본 보조 분석이므로 새로운 엄격한 완전성 판정을 대신하지 않는다.

현재 구현은 다음과 같이 동작한다.

```text
전체 테스트 종료
→ 전체 connections.jsonl의 wall/mono 쌍 수집
→ 전체 offset 최대−최소 < 10ms 검사
→ 같은 결과를 각 DB session에 저장
→ 이미 끝난 두 session도 불완전 처리
```

코드 위치는 `backend/output/ci-715/connection-delivery/capture.py:328`, `:336`, `:343` 및 `analyze_delivery.py:123`이다.

### 원인 가설 판단

| 가설 | 판단 | 이유·남은 한계 |
| --- | --- | --- |
| 호스트의 wall/monotonic 대응이 실행 후반에 바뀜 | **가장 유력** | 독립 Python과 JVM에서 같은 방향 변화가 지속됨. 어느 clock 또는 서비스가 변화시켰는지는 미확정 |
| Java의 두 시각 조회 사이 일시적 GC·스케줄링 지연 | 단독 설명의 비중 낮음 | 한 이벤트 뒤 복구되지 않고 다른 프로세스에서도 변화가 유지됨. 개별 표본 지연 가능성은 남음 |
| 전체 실행의 경고를 모든 수집 구간에 전파 | **C3 두 구간 판정의 직접 원인으로 확인** | 동일한 전체 clock_pairs를 각 session에 사용 |
| 수집이 첫 연결보다 늦거나 packet drop 발생 | 이번 불완전 판정의 이유가 아님 | 양쪽 준비가 먼저였고 drop·파서 오류·종료 검사는 통과 |
| NTP·수동 시간 변경·특정 macOS 서비스 | 미확정 | 당시 시간 서비스 로그와 동작 주체 증거가 없음 |

`ConnectionObserver.event()`는 wall을 읽은 다음 nanoTime을 읽으며, Python 수집기도 두 시각을 순서대로 읽는다. 두 호출은 원자적 표본이 아니므로 조회 사이 지연과 실제 clock 변화를 한 표본만으로 완전히 구분할 수 없다.

Java nanoTime은 같은 JVM 안의 경과 시간에 사용하며 다른 JVM/Python의 원점을 같다고 가정하지 않는다. Python monotonic은 시스템 시각 갱신에 영향받지 않는 경과 시간 기준이다. [Java 25 System 문서](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime()), [Python time 문서](https://docs.python.org/3/library/time.html#time.monotonic)

### 다음 실험의 제안 흐름

```text
고정된 C1/C2/C3 원본 읽기
→ clock source별 변화 구간 식별
→ container ID·Driver ID로 실제 수집 구간 추출
→ 실행 전체 경고 / 구간 내 clock 일관성 / 증거 부족을 별도로 기록
→ 기존 판정과 나란히 비교
```

후속 분석은 `window_clock_consistent` 같은 보조 결과를 제안한다. 이것을 기존 `capture_complete`와 같은 뜻으로 사용하지 않는다. 구간별로 안정적이어도 물리 소켓 대응이 불명확하면 서버 도달 단계는 계속 미확정이다.

## 3. 코드 책임과 제안

다음은 **구현 제안**이며 이번에는 만들거나 바꾸지 않았다.

| 위치·책임 | 기존 또는 제안 동작 |
| --- | --- |
| 기존 `ConnectionObserver.event()` | wall/mono 원시 기록의 근거. 이번 작은 실험에서는 Java/JAR를 바꾸지 않음 |
| 기존 `DeliveryMonitor.close()`·`clock_stable()` | 전체 실행 flag의 근거. 고정 실험 원본으로 보존 |
| 새 별도 clock 분석기 `readClockSamples()` | 파일과 source 이름을 받아 원본 시각·순서·clock domain을 읽기 전용으로 반환 |
| 제안 `findClockChanges()` | source별 offset 연속성과 독립 기록의 동반 변화·표본 공백을 반환. NTP 원인으로 자동 분류하지 않음 |
| 제안 `auditCaptureWindow()` | container/Driver 경계·수집 시작/종료·해당 clock 표본을 받아 국소 일관성·이상·미확인 및 근거를 반환 |
| 별도 결과 파일 | 원래 판정과 보조 판정을 함께 보존. 기존 C3 manifest·analysis를 덮어쓰지 않음 |

JVM과 Python의 raw monotonic 값을 직접 빼지 않는다. 기존 자료에서는 각 source 내부의 차이와 wall 구간을 대조하고, clock 변경 경계를 가로지르거나 경계·표본이 부족하면 미확인으로 남긴다. 경과 시간 계산은 같은 source의 monotonic 차이를 사용한다.

두 시각 조회를 앞뒤 monotonic으로 감싸 표본 오차를 기록하는 계측은 향후 실제 관측이 필요할 때의 별도 후보로 남긴다. 이 작은 실험에서 live agent·broker 수정까지 범위를 늘리지 않는다.

## 4. 저장과 원본 보존

DB·스키마·Flyway 변경은 없다. 제품 timeout·SSL·retry·캐시·테스트 격리 설정도 변경 대상이 아니다.

- 제안 디렉터리: `backend/output/ci-715/connection-clock-review/`. 현재는 미생성.
- 입력: 고정 C1/C2/C3 원본과 기존 manifest·최종 판정.
- 출력: source별 변화 요약·구간별 보조 분석·기존 판정과의 비교표.
- 원본을 수정하지 않고 분석 전후 hash를 비교한다. C3의 기존 엄격 판정 0/2와 실행기 exit 1은 그대로 보존한다.
- host clock 설정·시간 동기화 서비스·Docker 전역 설정을 조작하지 않는다. 패킷 수집기나 DB를 시작하지 않는다.

## 5. 작은 검증 순서와 실행 상한

### 1단계 — 판정 경계 fixture

실패하는 fixture를 먼저 만들고 필요한 집계만 구현한다.

| 상황 | 기대 결과 |
| --- | --- |
| 수집 종료 후 전체 clock offset 변화 | 실행 전체 경고 유지. 수집 중 변화와 구분 |
| 수집 도중 offset 변화 | 해당 구간 불일치 또는 미확인 |
| 준비·종료 경계 누락, 구간 표본 부족 | 안정적이라고 판정하지 않고 미확인 |
| 한 표본만 이상하고 독립 source는 변화 없음 | 호스트 시간 보정으로 확정하지 않음 |
| 둘 이상의 source에서 지속 변화 | 공통 clock 관계 변화의 근거로 기록. 서비스·원인은 미확정 |
| 서로 다른 monotonic 원점을 가진 입력 | raw 값의 직접 차이로 잘못 연결하지 않음 |
| 같은 시각대의 여러 소켓·프록시 후보 | clock 일관성만으로 연결 정체성을 확정하지 않음 |

### 2단계 — 기존 자료 재생 1묶음

C1·C2·C3를 같은 분석기로 한 번씩 처리해 원래 판정과 비교한다. C3에서는 변화가 대상 수집 뒤에 있다는 것, 구간별 관측 범위, 원본 0/2 유지 여부를 확인한다. 재생은 저장된 자료를 읽는 작업이며 제품 테스트 재실행이 아니다.

### 실행 상한

**이번 후속 실험은 fixture와 기존 자료 재생 1묶음에서 종료한다. 새 전체 통합 0회, 새 DB·패킷 수집 0회다.** 자료 부족이면 그 한계를 기록하고 닫는다. 장애나 clock 변화를 다시 재현할 때까지 반복하지 않는다.

예정 분석기는 아직 없으므로 현재 실행 가능한 명령인 것처럼 제시하지 않는다. 구현에 착수하는 경우에만 별도 코드와 검증 명령을 준비한다.

## 6. 완료 기준과 CI 개선 마무리

### 이 작은 실험의 완료 기준

1. 실행 전체의 환경 경고와 실제 수집 구간의 일관성을 구분한다.
2. 변화가 구간 안에 있거나 증거가 부족하면 미확인으로 남긴다.
3. 기존 판정·원본·격리 증거를 보존하고, C3를 사후 완전 수집으로 교체하지 않는다.
4. 결과 또는 자료 부족을 별도 문서로 기록하고 추가 전체 실행 없이 종료한다.

현재 확인한 직접 원인만으로도 “C3의 관측 gate 실패 때문에 제품 테스트가 실패한 것은 아니다”라고 설명할 수 있다. OS 시간 보정의 정확한 원인과 과거 A3 timeout의 근본 원인은 미확정으로 남긴다.

### 빨리 마무리하기 위한 추천 범위

**시계·네트워크 진단을 끝까지 해결하는 것을 CI 개선 완료의 필수 조건으로 추가하지 않는다.** 검증된 개선안 1·2·4와 스케줄러 수정을 중심으로 최종 비교하고, 전체 성능 이점이 확인되지 않은 개선안 5는 이번 성과 범위에서 제외하는 방향을 추천한다. 아직 후보 코드를 제거하거나 최종 채택 결정을 실행한 것은 아니다.

| 남은 핵심 묶음 | 할 일 | 종료 기준 |
| --- | --- | --- |
| 1. 최종 코드·비교 기준선 확정 | develop 차이를 반영할 방식과 공통 기준선 확정, 채택 1·2·4·스케줄러 중심 정리, 5 제외/보류 판단 | 비교 전후가 같은 제품 변경·workflow·테스트 검증 범위를 사용 |
| 2. 최종 회귀·실제 Actions 비교 | 최종 목록으로 포맷·단위·통합·인수·JAR 확인. 실제 runner·캐시 조건과 실패를 함께 기록 | 기능 검증 통과 및 비교 가능한 CI 자료 확보 |
| 3. 결과·블로그·이력서 정리 | 대상 그룹 효과와 실제 전체 CI 효과를 분리. 장애·보류 이유·한계 명시 | 실제 근거 범위에서 성과 문서 완료 |

인수·SSE 등의 비용 점검은 최종 workflow 단계별 시간에서 남는 병목을 분류하는 데 우선 한정한다. 별도 개선 실험은 큰 병목이 확인될 때 후속 범위로 정한다. 최종 검증에서 간헐 실패가 다시 나면 실패를 보존하고 해당 검증 gate는 미충족으로 남긴다.

최근 로컬 통합 3회는 테스트 명령 시간 합계 약 **9분 31초**였다. 같은 정도라면 전후 6회는 약 19분의 명령 시간이지만, 이번 추천 마무리 경로에 개선안 5의 로컬 전후 6회를 필수로 추가하지 않는다.

실제 Actions의 안정적인 전후 수치를 쓰려면 각 3회, 총 6회를 제안한다. 과거 약 7분/회 기준으로는 순차 명령 시간만 약 42분이며 큐·환경·수정·회귀 시간은 별도다. 과거 평균이나 이 산술값을 앞으로의 소요 시간 보장으로 쓰지 않는다. 단일 Actions 성공은 회귀 확인 자료이고 안정적인 성능 개선율의 근거와 구분한다.

이번에는 분석과 계획 문서 작성, 요청한 현재 브랜치 pull만 수행했다. 구현·테스트/DB/패킷 재실행·develop 병합/rebase·commit·push·Notion 원격 쓰기는 수행하지 않았다.

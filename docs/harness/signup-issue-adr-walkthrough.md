# 회원가입 Issue 하네스 적용 예시

`회원가입 Issue 초안 만들자`라는 요청이 짧은 Issue 초안으로 바뀌는 과정을 보여준다.
실제 대화에서 확인한 결과와 ADR 형식을 설명하기 위한 가상 추가 대화를 구분한다.

## 실제 대화

> 사용자 답변은 실제 대화에서 그대로 옮겼다. Codex 질문은 답변의 맥락이 보이도록
> 짧게 정리했다.

**사용자**

> 회원가입 Issue 초안 만들자.

**Codex**

> 기존 Issue #10을 GitHub OAuth 회원가입 Issue로 보강할까요?

**사용자**

> 네

**Codex**

> 신규 Member는 언제 생성할까요?

**사용자**

> 닉네임 입력을 완료한 뒤에 Member 생성

**Codex**

> 닉네임 중복을 허용할까요?

**사용자**

> 닉네임은 중복을 서용한다.

**Codex**

> 가입 세션이 유효하다면 닉네임 입력 실패 후 OAuth 없이 다시 시도할까요?

**사용자**

> 네

**Codex**

> 가입 세션이 만료되면 어떻게 할까요?

**사용자**

> 가입 세션이 만료되면 다시 시작한다.

**Codex**

> 같은 GitHub 계정에서 회원가입 완료 요청이 동시에 오면 Member를 몇 명 생성할까요?

**사용자**

> 한 명만 생성

**Codex**

> 닉네임은 1~20자의 한글, 영어, `(`, `)`, `_`만 허용하고 공백과 숫자는 막을까요?

**사용자**

> 네

## 실제 대화로 만든 결과

[OAuth 회원가입 Issue 초안](examples/10-oauth-signup-issue-draft.md) 하나를 만든다.

- 기존 템플릿의 `구현 기능 설명`, `TODO`, `메모`만 사용한다.
- 상세 범위, 실패·복구 흐름과 검증 조건은 내부 계약에 남고 Issue에는 펼치지 않는다.
- 실제로 논의한 대안이 확인되지 않았으므로 `메모`는 `없음`이고 ADR을 만들지 않는다.

검증 결과는 `high / pass / render_draft`이며 `remote_write_authorized=false`다. 실제 GitHub
Issue #10과 `backend/docs/adr`은 변경하지 않는다.

## ADR 형식을 보여주기 위한 가상 추가 대화

> 아래 문답은 실제 사용자 답변이 아니다. 하네스가 ADR을 생성할 수 있는 조건과 결과
> 형식을 보여주기 위해 만든 가상 예시다. 팀이 실제로 같은 대안을 논의했다고 확인하기
> 전에는 결정 근거로 사용할 수 없다.

**Codex**

> 어떤 상황 때문에 Member 생성 시점을 선택해야 했나요?

**사용자(가정)**

> OAuth 콜백에서 바로 Member를 만들면 닉네임 화면을 이탈한 불완전 계정이 남고,
> 클라이언트가 GitHub 신원을 다시 보내게 하면 외부 신원을 클라이언트 입력으로 믿게 된다.

**Codex**

> 회의에서 실제로 검토한 대안은 무엇인가요? 없었다면 없다고 답해도 됩니다.

**사용자(가정)**

> 콜백 즉시 Member 생성, 클라이언트가 GitHub 신원과 닉네임 전송, 서버 가입 세션 발급을
> 검토했다.

**Codex**

> 무엇을 선택했고 왜 선택했나요?

**사용자(가정)**

> 서버 가입 세션을 선택했다. 불완전한 Member를 남기지 않고 GitHub 신뢰 경계를 서버에
> 둘 수 있기 때문이다.

**Codex**

> 감수하는 단점과 다시 논의할 조건은 무엇인가요?

**사용자(가정)**

> 가입 세션 상태와 만료 처리가 늘어난다. 다른 OAuth 제공자나 계정 연결, 닉네임 없는
> 가입을 도입하면 다시 논의한다.

이 가상 답변을 팀이 실제 논의 내용이라고 확인했고 장기 영향과 반복 참조 조건까지
충족했다고 가정하면, Issue `메모`에 결정 한 줄과 예정 경로를 추가한다. 구현을 시작할 때
AI는 실제 Issue 번호 `10`을 materializer에 전달한다.
[GitHub OAuth 신원과 Member 지연 생성 ADR 형식 예시](examples/10-github-oauth-member-delayed-creation.md)와
같은 `Proposed` 파일을 작업 브랜치에 만들고 코드와 같은 PR에 포함한다.

## 핵심 구분

- 실제 대화 결과: ADR 없는 짧은 Issue 초안
- 가상 추가 대화 결과: ADR 조건과 문서 형식 시연
- 실제 프로젝트 ADR: 팀이 실제 대안과 선택 이유를 확인한 경우에만 생성
